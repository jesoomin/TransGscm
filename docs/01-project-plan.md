# G-SCM 차세대 전환 Agent — 1~2주차 기획서

> 이 프로젝트의 범위는 **전환 프로그램 1단계 = 서버(Java/XSQL → Spring/MyBatis) 전환**이다. 화면(Nexacro xfdl → React)은 2단계 별도 트랙이며 이번 Agent의 산출물이 아니다. 단계 구분의 근거와 두 단계를 잇는 nctRid 계약은 @docs/05-proposal.md 참고.

## KPI 기준값 (@docs/06-mentor-feedback.md §4 반영)

**보고·제안서에 쓰는 공수 절감 수치는 아래 하나로 통일한다.** 화면 유형별로 자동화 효과가 크게 다르므로 단일 평균값을 확정하지 않고 유형별로 차등 추정한다.

| 화면 유형 | 비중(추정) | 자동화 후 소요 |
|---|---|---|
| 단순 조회/그리드 | 40~50% | 1~2일 (리뷰 중심) |
| 조회+상세+CRUD | 30~40% | 3~4일 |
| 복합 화면·리포트·특수 로직 | 15~20% | 5~7일 |

평균 약 3일 → 수작업 기준 대비 **65~70% 절감**이 목표값이다. **90% 이상은 약속하지 않는다.** 여기에 도구 자체 개발 공수(팀 3~5명 × 4~6개월)와 공통 응답/예외 규약·메시지 코드 표준화 구축 공수를 ROI 계산에 반드시 포함한다.

> **기준선(수작업 공수)은 아직 실측되지 않은 가정이다.** 파일럿 10~20건의 개발자 실투입 시간(사람 개입 시간 포함)을 측정해 확정한다. 그 전까지 이 수치는 목표치이지 실적이 아니다.

**핵심 대리지표**: 컴파일 통과율 · 응답 diff 일치율에 더해 **"사람 수정 라인 비율"**(자동 생성 코드 대비 사람이 손댄 라인 수 비율)을 반드시 함께 추적한다 — 이게 실제 공수 절감률의 가장 직접적인 대리 지표다. `/tracking/conversion-verification.csv`와 `CONV_FILE.HUMAN_EDIT_RATIO`에 화면별로 누적한다.

## 1주차: 역량 및 기술 스택 확인

### 1. 현재 보유 역량
- **Python 숙련도**: 초급~중급 (실무 구현 경험 적음, 프레임워크 기반 Agent 구성·활용 위주)
- **AI/ML 경험**: 전통 ML보다 LLM 기반 Agent 시스템 구축 중심
- **LLM 활용 경험**: 사내 SKHy GaiA LLM 프레임워크로 Analysis/Simulation/Validation Agent 기능 구축
- **RAG/Agent 구현 경험**: 유
  - P-MIX Simulation Agent — Multi-Agent 구조(Analysis/Simulation/Validation) 구현
  - Orchestrator 설계: 자연어 질의 → Agent 할당 → 기능 실행 → 결과 구조화
  - Domain Knowledge: md 파일 구축 → 프롬프트 반영 (경량 프롬프트 주입형)
- **프로젝트 경험**
  - P-MIX Simulation Agent (수행 중) — GaiA 기반 Multi-Agent/Orchestrator 구현
  - G-SCM Nexacro14 + NEXCORE(Spring, PU/FU/DU/XSQL) 개발·유지보수 — **전환 대상 시스템의 실무 담당자**

### 2. 학습 필요 영역

| 구분 | 항목 | 우선순위 |
|---|---|---|
| 재사용(기보유) | Orchestrator/Multi-Agent 설계, 프롬프트 기반 Domain Knowledge 반영 | — |
| **필수** | Python 실무 구현 — 파일 파싱, 코드 생성, 문자열/AST 처리 | 1 |
| **필수** | Java 코드 파싱 — javalang / tree-sitter (AS-IS 원본이 컴파일 불가한 경우가 있어 **오류 복구 파서** 필요) | 1 |
| **필수** | XML 파싱 — `.BIZUNIT` / XSQL(iBatis) 구조 분석 (lxml) | 1 |
| **필수** | 코드 검증 자동화 — Validation Agent에 Maven 빌드 연동 | 2 |
| 대안 | 코드 변환 특화 프롬프트 엔지니어링 — few-shot 설계, 구조화 출력 강제 | 2 |
| 대안 | 리뷰 UI(Streamlit) — 변환 결과 검토 대시보드 | 3 |
| 있으면 좋은 것 | RAG 고도화 — 정적 md 주입 → 벡터 검색 기반 동적 예시 검색 (파일럿 결과가 코퍼스) | 4 |
| 있으면 좋은 것 | API 개발(FastAPI) — 변환 Agent 서비스화 | 4 |

> Python 실무 구현 역량이 최대 리스크이므로, **필수 항목을 "파싱 → 생성 → 검증" 최소 단위 기능 순서로** 좁혀서 학습한다. 서비스화·RAG는 파일럿이 끝나기 전에 착수하지 않는다.

### 3. 기술 스택 (우선순위 구분)

| 구분 | 영역 | 선택 | 비고 |

| **필수** | 검증 | Maven (`mvn compile`) | Java 빌드 검증 |
| **필수** | DB | Oracle (로컬) | 매핑 그래프 적재 + 차등 테스트 실행 |
| **대안** | 오케스트레이션 | 사내 GaiA 우선, 한계 시 LangGraph | 상태 그래프·병렬 분기·조건부 라우팅이 필요해지면 LangGraph |
| **대안** | 리뷰 UI | Streamlit | 로컬 전용 |
| 있으면 좋은 것 | 검색/예시 저장 | FAISS 또는 Chroma | 파일럿 결과물이 코퍼스가 된 이후에 착수 |
| 있으면 좋은 것 | 서비스화 | FastAPI | 파일럿 이후 |
| **필수** | 형상관리 | Git 브랜치/PR | 계층별 단위 커밋 |

### 4. 프로젝트 관심 도메인
- 1순위: 제조/유통(SCM) — G-SCM 담당 업무와 직결
- 2순위: 개발자 생산성/DevTools
- 관심 사유: 1,416개 화면이라는 실제 과제로 학습 내용을 즉시 실무 적용 및 정량 검증 가능

### 5. 8주 목표 설정

**8주 안에 검증 가능한 최소 단위**: 화면 유형별 대표 20~30개의 **서버 로직** 전환. 1,416개 전체를 대상으로 하지 않는다.

| 구분 | 목표 |
|---|---|
| 기술 목표 | "코드 분석 → 계획 수립 → 병렬 생성 → 정적 검증 → 수리" End-to-End 자동 변환 파이프라인 PoC 완성. 결정론적 변환기(iBatis→MyBatis, BizUnit→Api/Service/Store 골격)와 검증기를 **분리된 모듈**로 구축 |
| 비즈니스 목표 | 대상 화면의 서버 로직 1차 자동 변환율 70% 이상, 사람 수정 라인 비율 30% 이하 달성 |
| 성장 목표 | Lv.3 Middle AI 개발자로서 1,416개 화면 규모 실전 적용 역량 증명 |

**최종 데모에서 반드시 보여줄 것**: 폴더를 지정하면 파이프라인이 계획 수립 → 변환 → 검증 → 수리 → 영향도 분석까지 자동 진행되고, 사람이 승인해야만 산출물이 반영되는 전 과정.

## 2주차: 문제 정의 및 서비스 기획

> 상세 제안서는 @docs/05-proposal.md 참고. 이 절은 기획 시점의 문제 정의를 담는다.

### 프로젝트명
G-SCM 차세대 전환 Agent

### 배경 및 문제 정의

**As-Is**
- 프론트: Nexacro14(Dataset 기반 UI) / 백엔드: NEXCORE(SK그룹 표준 Spring 프레임워크, BizUnit 단위 개발)
- NEXCORE 통신 구조: Nexacro Dataset ↔ UIAdapter가 직렬화 → nctRid 단일 진입점으로 P→F→D BizUnit 순차 호출 → D BizUnit이 XSQL(iBatis) 실행
- 전환 대상(1단계): 화면 1,416개에 대응하는 **P/F/D BizUnit + XSQL** → Spring/MyBatis
- 화면-서비스 매핑(nctRid)이 문자열 규칙과 불일치 → 화면마다 소스 추적 필요
- 솔루션(패키지 제품) 기반 → 프레임워크 종속으로 확장성 제약

**Pain Point**
- 화면마다 P/F/D/XSQL 4종 파일을 사람이 추적·분석하는 선행 작업이 반복 발생
- 1,416개 화면 규모의 반복 작업 — 패턴이 동일한데도 미자동화
- 개발자별 이원화 → Controller 응답 형태·예외 처리·Mapper 작성 방식의 구조 편차
- AS-IS 원본 자체에 결함(컴파일 불가, XML 태그 불일치, SQL 문법 오류)이 섞여 있어, 전환 중에야 뒤늦게 발견됨

**기회 요인**
- PU/FU/DU/XSQL의 명확한 계층·네이밍 컨벤션 → 파싱/템플릿화 용이
- iBatis→MyBatis 문법 변환 → 규칙 기반 자동화 친화적 (LLM 불필요)
- BizUnit 시그니처 → Api/Service/Store 골격도 결정론적 생성 가능
- nctRid 단일 진입점 + 고정 Dataset 포맷 → 차등 테스트가 깔끔하게 성립

### 핵심 인사이트: 재사용 vs 신규개발

- **바꿔야 할 건 업무 로직이 아니라 프레임워크 종속 계층이다** — F/D BizUnit의 계산·분기·SQL은 NEXCORE와 무관하게 유효한 자산이고, 실제로 교체해야 하는 건 UIAdapter의 Dataset 직렬화, nctRid 라우팅, P 계층 진입점, 그리고 iBatis 문법이다.
- **교체 대상(신규 개발)**: UIAdapter·디스패처·P BizUnit → REST Controller(`{화면}Api`) / iBatis → MyBatis
- **포팅 대상(로직 유지)**: F BizUnit(계산·분기 그대로) → `{화면}Service` / D BizUnit + XSQL(쿼리 로직 그대로) → `{화면}Store` + `Mapper.xml`
- **변경 없음**: DB 스키마

### 목표 사용자
- G-SCM 전환 프로젝트 투입 백엔드 개발자 (사내·외주)
- 변환 결과 검토·승인 PL/PM, QA 담당자

### 프로젝트 목표

**정성적 목표**
- 목표1: 반복적인 서버 로직 전환 작업 자동화
- 목표2: 전환 코드의 구조적 일관성 확보 (개발자별 편차 최소화)
- 목표3: 사내 AI 기술 내재화 및 재사용 자산화 (검증 루프를 변환기와 분리해 타 전환 프로젝트 재활용)

**정량적 목표(KPI)** — 측정 정의 포함. 상세는 @docs/05-proposal.md

| 지표 | 목표 | 측정 방법 | 현재 |
|---|---|---|---|
| nctRid 매핑 자동 확정률 | 80%+ | `NCTRID_MAP.NCTRID_SOURCE = CONFIRMED_BIZUNIT` 비율 | 100% (150/150) |
| 1차 자동변환 커버리지 | 70%+ | 생성 코드의 `mvn compile` 통과율 | 규칙 기반 생성물 1건 외 전부 통과 |
| 사람 수정 라인 비율 | 30% 이하 | `CONV_FILE.HUMAN_EDIT_RATIO` | 미측정(리뷰 완료 화면 0건) |
| 화면당 서버 전환 공수 절감 | 65~70% | 파일럿 10~20건 실투입 시간 실측 | 미측정(기준선 미확정) |

### 핵심 기능 정의
1. **AS-IS 소스 자동 분석기** — P/F/D BizUnit·XSQL 파싱 → 화면↔nctRid↔BizUnit↔XSQL 매핑 그래프를 DB로 구축
2. **변환 계획 수립** — 화면별로 대상 fragment·예상 산출물·LLM 호출 대상·트랙 판단 근거를 파일로 고정한 뒤 코드 생성 시작
3. **결정론적 변환기** — iBatis→MyBatis Mapper.xml, `{화면}Api`/`Service`/`Store` 골격, `.BIZUNIT` → DTO 생성 (LLM 미사용)
4. **LLM 포팅기** — F BizUnit 내부 업무 로직만 Service 메서드 본문으로 포팅. 콜그래프에서 뽑은 콜리 계약을 프롬프트에 주입
5. **자동 검증·리뷰 리포트** — 정적 검증, 품질 스캔, `mvn compile`, 차등 테스트, 영향도 분석 대시보드, 화면별 인수인계 문서

### 기대 효과
- **근거**: 전면 재작성이 아니라 프레임워크 종속 계층만 교체하고 검증된 F/D 로직은 포팅 → 절감폭 확보
- 업무 효율화: 화면별 소스 추적 작업 제거, 골격·SQL·DTO 생성 자동화
- 품질 향상: 동일 템플릿·동일 검증기로 개발자 간 편차 감소, 원본 결함을 전환 전에 자동 검출
- 확장성: nctRid 계약 유지로 2단계 UI 트랙이 백엔드를 다시 손대지 않고 진행 가능

### 범위 및 제약사항
- **In Scope**: P/F/D BizUnit + XSQL → Api/Service/Store/Dto/Mapper.xml 자동 변환, nctRid 계약 유지, DB 스키마 유지 전제 iBatis→MyBatis 변환, 정적/빌드/차등 검증, 영향도 분석
- **Out of Scope**: 화면(xfdl→React) 전환(2단계 별도 트랙), DB 스키마 변경, 신규 기능 추가, 무인 자동배포(리뷰 필수), DCOT998류 공통/배치 BizUnit
- **제약사항**
  - nctRid 매핑 자동 추출이 선행되어야 함
  - `.BIZUNIT` XML의 `<fields/>`가 비어 있는 경우가 많아 코드 실사용값 역추출 필요
  - P BizUnit이 순수 진입점인지 화면별 검증 로직이 섞여있는지 확인 필요
  - 소스코드 외부 LLM 전송 보안 정책 확인 필요
  - 공통 응답/예외 규약 미확정 — 확정 전까지 생성 템플릿에 주입하지 않음
