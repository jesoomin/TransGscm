# 2주차 — 문제 정의 및 서비스 기획

**프로젝트**: G-SCM 차세대 전환 Agent
**범위**: 전환 프로그램 **1단계 = 서버(Java/XSQL → Spring/MyBatis) 전환**

---

## 1. 개요

Nexacro14 + NEXCORE로 구축된 G-SCM의 서버 계층(화면 1,416개에 대응하는 P/F/D BizUnit + XSQL)을 Spring/MyBatis 구조로 자동 전환하는 AI Agent를 만든다. 기존 트랜잭션 계약(nctRid)을 유지해, 이후 2단계에서 만들어질 React 화면이 이 API를 그대로 호출할 수 있게 한다.

## 2. 문제 정의

### As-Is
- 프론트 Nexacro14(Dataset 기반) / 백엔드 NEXCORE(SK그룹 표준 Spring, BizUnit 단위 개발)
- 요청 흐름: Nexacro Dataset → UIAdapter 직렬화 → **nctRid 단일 진입점** → P→F→D BizUnit 순차 호출 → D BizUnit이 XSQL(iBatis) 실행
- 화면-서비스 매핑(nctRid)이 문자열 규칙과 불일치 → **화면마다 사람이 소스를 추적**
- 솔루션(패키지 제품) 기반 프레임워크 종속 → 확장성 제약

### Pain Point

| 구분 | 내용 | 근거 |
|---|---|---|
| 시간 | 화면마다 P/F/D/XSQL 4종 파일을 추적·분석하는 선행 작업 반복 | 실무 경험. nctRid ↔ BizUnit 대응이 명명 규칙만으로 결정되지 않음 |
| 비용 | 1,416개 화면 규모 반복 작업이 미자동화 | 패턴은 동일한데 화면 수만큼 중복 |
| 품질 | 개발자별로 Controller 응답 형태·예외 처리·Mapper 작성 방식 이원화 | 유지보수 중 확인 |
| 리스크 | **AS-IS 원본 자체에 결함이 섞여 있음** | 확보한 PLA047 세트에서 확인: Java 중괄호 누락(컴파일 불가), `.BIZUNIT` XML 태그 불일치, XSQL 내 SQL 문법 오류 |

마지막 항목이 중요하다. **전환 도구가 "정상 원본"을 전제하면 첫 화면에서 멈춘다.** 원본 결함을 정상 입력의 일부로 취급하는 설계가 필요하다.

### 기회 요인 (왜 AI로 풀 수 있는가)

| 요인 | 의미 |
|---|---|
| P/F/D/XSQL의 강제된 계층·네이밍 컨벤션 | 정적 분석으로 전체 그래프 구축 가능 |
| iBatis → MyBatis는 **문법 치환** | 규칙 기반 100% 자동화 대상. LLM 불필요 |
| BizUnit 시그니처 → Api/Service/Store 골격 | 결정론적 생성 가능 |
| LLM 필요 영역이 **F BizUnit 내부 로직**으로 한정 | 비용·환각 통제 가능 |
| nctRid 단일 진입점 + 고정 응답 포맷 | **차등 테스트가 깔끔하게 성립** |

## 3. 목표 사용자

| 사용자 | 역할 | 이 도구로 하는 일 |
|---|---|---|
| 전환 투입 백엔드 개발자 (사내·외주) | 화면별 서버 로직 전환 실무 | 폴더 지정 → 파이프라인 실행 → 자동 생성물 검토 → 수동 보완 필요 지점만 처리 |
| PL / PM | 진척·품질 관리 | 화면별 변환 상태·이슈·위험도 확인, 승인 게이트에서 저장 승인 |
| QA | 결과 검증 | 정적 검증·차등 테스트 결과, 화면별 인수인계 문서로 확인 |

## 4. 8주 범위 vs 장기 비전

| 구분 | 8주 PoC (이번) | 장기 비전 |
|---|---|---|
| 대상 규모 | 유형별 대표 **20~30화면** | 1,416화면 전체 |
| 계층 | 서버(1단계)만 | 서버 + 화면(2단계) |
| 검증 | 정적 검증 + 빌드 + SQL 계층 차등 테스트 | HTTP 레벨 차등 테스트, 운영 트래픽 섀도잉 |
| 지식 재사용 | 변환 규칙·프롬프트 자산화 | RAG 코퍼스 기반 유사 화면 few-shot |
| 배포 | 로컬 도구 + 사람 승인 | 서비스화(FastAPI), CI 연동 |

**8주 안에 하지 않는 것**: UI 전환, RAG, 서비스화, 운영 배포, DB 스키마 변경, 무인 자동 커밋.

## 5. 핵심 가설 (검증 대상 3개)

| # | 가설 | 검증 방법 | 성공 기준 |
|---|---|---|---|
| **H1** | nctRid 매핑 그래프를 **선행 정적 분석**으로 구축하면 화면별 소스 추적 병목이 사라진다 | 화면↔nctRid↔BizUnit↔XSQL 그래프를 DB로 구축 → 임의 메서드의 영향 화면을 역추적해 정답과 대조 | 자동 확정률 80%+, 역추적 결과가 수동 확인 결과와 일치 |
| **H2** | **결정론적 변환이 대부분을 커버**하고 LLM은 좁은 영역에만 필요하다 | 화면당 LLM 호출 대상 메서드 비율 측정 + 규칙 기반 생성물의 실제 컴파일 여부 | LLM 대상 30% 이하, 규칙 기반 생성물 컴파일 통과 95%+ |
| **H3** | **정적 검증만으로 변환 정확성을 보증할 수 있다** | 정적 검증 통과 코드에 실행 기반 동등성 검증을 시도 | 실행 결과가 AS-IS와 일치 |

> H3은 반증 가능성이 큰 가설로 의도적으로 세웠다. 참이면 검증 비용이 크게 줄고, 거짓이면 **검증 전략 전체를 재설계해야 한다**는 뜻이므로 어느 쪽이든 8주 안에 알아야 할 값이다.

## 6. 성공 지표 (다층)

단일 지표로 성공을 판단하지 않는다. 변환 파이프라인은 **"구조가 생성됐나 → 컴파일되나 → 동작이 같나 → 사람이 얼마나 고쳤나"** 순서로 층이 다르고, 각 층이 통과해도 다음 층은 별개다.

| 층 | 지표 | 목표 | 측정 방법 |
|---|---|---|---|
| L1 구조 | nctRid 매핑 자동 확정률 | 80%+ | 자동 확정 nctRid / 전체 nctRid |
| L1 구조 | 골격 생성 성공률 | 95%+ | 생성 실패한 화면 수 / 전체 |
| L2 문법 | 컴파일 통과율 | 95%+ | `mvn compile` 실패 파일 수 |
| L2 문법 | 정적 검증 통과율 | 90%+ | 계층 간 참조·중괄호·매퍼 id 검사 통과 비율 |
| **L3 기능** | **응답 diff 일치율** | 파일럿에서 기준 수립 | 동일 입력을 AS-IS/TO-BE에 실행 후 정규화 비교 |
| **L4 공수** | **사람 수정 라인 비율** | 30% 이하 | 자동 생성 라인 대비 리뷰 중 수정 라인 |
| L4 공수 | 화면당 전환 공수 절감률 | 65~70% | 파일럿 10~20건 개발자 실투입 시간(사람 개입 시간 **포함**) |

**측정 규칙 (모호성 제거)**
- *화면 유형 분류 기준*: 트랜잭션(nctRid) 개수 + D 메서드 수 + 동적 SQL 태그 유무로 자동 분류
- *샘플 수*: 유형별 4~5개, 총 20~30개
- *"전환 전후 작업"의 정의*: AS-IS 소스 확보 시점부터 TO-BE 코드가 리뷰 승인될 때까지. **소스 추적·리뷰·수정 시간을 모두 포함**한다
- *사람 개입 시간 포함 여부*: **포함한다.** 자동 생성 시간만 재면 실제 절감률이 과대평가된다

> **공수 절감률에 90% 이상을 약속하지 않는다.** 도구 개발 공수(팀 3~5명 × 4~6개월)와 공통 규약 확정 공수를 ROI에 포함해야 하며, 65%를 약속하고 75%를 내는 편이 다음 단계를 연다.

## 7. 핵심 기능

| # | 기능 | 방식 | 산출물 |
|---|---|---|---|
| 1 | AS-IS 소스 분석기 / nctRid 매핑 그래프 | **규칙 기반** | 화면↔nctRid↔BizUnit↔XSQL 그래프 (DB 4개 테이블) |
| 2 | 변환 계획 수립 (Planner) | **규칙 기반** | 화면별 계획 파일 — 대상 조각, 예상 산출물, LLM 호출 대상, 트랙 판단 근거 |
| 3 | 결정론적 변환기 | **규칙 기반** | iBatis→MyBatis Mapper, Api/Service/Store 골격, DTO |
| 4 | LLM 포팅기 (Translator) | LLM (좁은 범위) | F BizUnit 업무 로직 → Service 메서드 본문 |
| 5 | 검증기 (Validator) — **변환기와 분리** | 규칙 기반 | 정적 검증, 품질 스캔, 빌드 검증, 차등 테스트 |
| 6 | 검증-수리 루프 | LLM (라운드 상한) | 검증 실패를 피드백으로 재생성 |
| 7 | 영향도 분석 | 규칙 기반 | 미사용/중복/오류 함수, 위험도, 역방향 영향도 |
| 8 | 인수인계 문서 생성 | 규칙 기반 | 화면별 "미변환 사유 + 수동 처리 가이드" |

**절대 자동화하지 않는 것**: 공통 응답/예외 처리 규약. 화면마다 에이전트가 제각각 만들면 **현재의 "개발자별 이원화" 문제가 그대로 재현**된다. 사람이 먼저 확정하고 에이전트에 강제 컨텍스트로 주입하는 순서를 지킨다.

## 8. 리스크 및 대응 (1:1)

| # | 리스크 | 영향 | 대응 |
|---|---|---|---|
| R1 | nctRid 매핑 자동 추출 실패 | 에이전트가 코드베이스를 헤매며 환각 | 선행 정적 분석으로 그래프를 DB에 구축. 실패분만 사람이 채움 |
| R2 | AS-IS 원본 자체가 깨져 있음 | 깨진 원본 위에 "그럴듯한" 변환 생성 | 원본을 **정정하지 않고 보존**하되, 계획 단계에서 결함을 검출·표시하고 재설계 후보로 신호 |
| R3 | 문법은 통과하나 기능이 다름 | 전환 후 운영 장애 | 차등 테스트를 변환기보다 **먼저** 구축 |
| R4 | LLM 호출 비용이 화면 수에 비례해 폭증 | 전체 확장 시 비현실적 비용 | 결정론적 변환에 LLM 미사용. 포팅 대상을 명시적으로 표시된 메서드로만 한정 |
| R5 | 에이전트가 화면마다 다른 공통 규약 생성 | 이원화 문제 재현 | 공통 규약은 사람이 먼저 확정. 확정 전까지 템플릿에 주입 금지 |
| R6 | 파일럿 유형 편중 | 다른 유형에서 품질 급락 | 구조적 클러스터링 후 유형별 대표 4~5개씩 선정 |
| R7 | 검토 없이 결과가 반영됨 | 품질 사고 | 저장 전 **승인 게이트** 고정 |

| 비즈니스 목표 측정 방식을 구체화하라 (화면 유형 분류 기준, 샘플 수, 전환 전후 작업 정의, 사람 개입 시간 포함 여부) | §6에 **측정 규칙**을 별도로 명시. 사람 개입 시간 **포함**을 명문화 |

| Python 역량 리스크 → 필요한 단위 기능 우선순위 | 1주차 §2를 우선순위 1~4로 재정렬. "파싱 → 생성 → 검증" 최소 단위로 축소 |
| 핵심 결과물 / 최소 검증 단위 / 핵심 지표 2~3개를 명확히 | 1주차 §5에 데모 결과물 1개, 최소 단위(20~30화면), 핵심 지표 3개로 답변 |
