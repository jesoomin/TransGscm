# 1주차 — 역량 및 기술 스택 확인

**프로젝트**: G-SCM 차세대 전환 Agent
**범위**: 전환 프로그램 **1단계 = 서버(Java/XSQL → Spring/MyBatis) 전환**

---

## 0. 범위의 전제 (모든 주차 공통)

G-SCM 차세대 전환은 화면(UI)과 서버(백엔드)를 같은 시점에 바꾸지 않는다.

| 단계 | 대상 | 이번 Agent | 사유 |
|---|---|---|---|
| **1단계** | 서버 (P/F/D BizUnit + XSQL → Spring/MyBatis) | **O** | 업무 로직·SQL이 이미 검증된 자산이라 "재작성"이 아닌 "포팅"이 성립. 계층·네이밍이 강제돼 정적 분석이 가능 |
| **2단계** | 화면 (Nexacro xfdl → React) | X (별도 트랙) | UI는 디자인 확정 시점이 서버보다 늦다. 미확정 디자인을 자동 변환하면 두 번 만들게 됨 |

두 단계는 **nctRid 계약**으로 이어진다. 1단계는 `nctRid 1개 = REST 엔드포인트 1개` 대응을 유지하므로, 2단계 React 화면은 1단계가 만든 API를 그대로 호출한다(Strangler Fig).

## 1. 현재 보유 역량

| 항목 | 수준 | 근거 |
|---|---|---|
| Python 숙련도 | **초급~중급** | 프레임워크 기반 Agent 구성·활용 위주. 직접 구현 경험은 적음 |
| AI/ML 경험 | LLM Agent 중심 | 전통 ML보다 LLM 기반 Agent 시스템 구축 경험 |
| LLM 활용 | 유 | 사내 GaiA LLM 프레임워크로 Analysis/Simulation/Validation Agent 구축 |
| RAG/Agent 구현 | 유 | P-MIX Simulation Agent — Multi-Agent 구조 + Orchestrator 설계(자연어 질의 → Agent 할당 → 실행 → 결과 구조화), Domain Knowledge를 md로 구축해 프롬프트 주입 |
| **도메인 지식** | **상** | G-SCM Nexacro14 + NEXCORE(PU/FU/DU/XSQL) **개발·유지보수 실무 담당자** |

> 도메인 지식이 이 프로젝트의 최대 강점이다. 전환 대상 시스템을 직접 운영해 온 사람이 도구를 만들기 때문에, "nctRid가 문자열 규칙과 불일치해 화면마다 소스를 추적해야 한다" 같은 실제 병목을 문서가 아니라 경험으로 알고 있다.

## 2. 학습 필요 영역 (우선순위 구분)

| 우선순위 | 항목 | 필요 이유 |
|---|---|---|
| **1 (필수)** | Python 실무 구현 — 파일 파싱, 코드 생성, 문자열/AST 처리 | 파이프라인 전 구간의 기반 |
| **1 (필수)** | Java 코드 파싱 — tree-sitter | **오류 복구 파서가 필요하다.** AS-IS 원본이 컴파일 안 되는 경우가 실제로 있어(확보한 PLA047 세트에서 확인) 엄격한 파서는 그 파일에서 멈춘다 |
| **1 (필수)** | XML 파싱 — lxml | `.BIZUNIT`(입출력 메타), XSQL(iBatis) 구조 분석 |
| **2 (필수)** | 빌드 검증 자동화 — Maven 연동 | "변환됐다"를 주장하려면 실제로 컴파일돼야 함 |
| 2 (대안) | 코드 변환 프롬프트 엔지니어링 — few-shot, 구조화 출력 강제 | LLM 포팅 구간 품질 |
| 3 (대안) | 리뷰 UI — Streamlit | 변환 결과 검토 대시보드 |
| 4 (있으면 좋음) | RAG 고도화 — FAISS/Chroma | 파일럿 결과물이 코퍼스가 된 **이후** |
| 4 (있으면 좋음) | FastAPI 서비스화 | 파일럿 이후 |

**리스크 대응**: Python 실무 역량이 최대 리스크이므로 필수 항목을 **"파싱 → 생성 → 검증" 최소 단위 기능**으로 좁혀 학습한다. 서비스화·RAG는 파일럿 완료 전까지 착수하지 않는다.

## 3. 기술 스택 (필수 / 대안 / 있으면 좋은 것)

| 구분 | 영역 | 선택 | 비고 |
|---|---|---|---|
| **필수** | Java 파싱 | tree-sitter | 오류 복구 파싱 |
| **필수** | XML 파싱 | lxml | `.BIZUNIT`, XSQL |
| **필수** | LLM 호출 | **사내 LLM Gateway** (Azure OpenAI 호환) | 소스 외부 전송 보안 정책 대응 |
| **필수** | 빌드 검증 | Maven (`mvn compile`) | |
| **필수** | DB | Oracle (로컬) | 매핑 그래프 적재 + 차등 테스트 실행 |
| **필수** | 형상관리 | Git 브랜치/PR | 계층별 단위 커밋 |
| 대안 | 오케스트레이션 | 사내 GaiA 우선 → 한계 시 LangGraph | 상태 그래프·병렬 분기·조건부 라우팅이 필요해지면 전환 |
| 대안 | 리뷰 UI | Streamlit | 로컬 전용 |
| 있으면 좋음 | 벡터 검색 | FAISS / Chroma | 파일럿 이후 |
| 있으면 좋음 | 서비스화 | FastAPI | 파일럿 이후 |

> **범위 밖**: ESLint/tsc/AG-Grid 등 프론트엔드 검증·라이브러리는 2단계 UI 트랙의 도구다.

## 4. 프로젝트 관심 도메인
- 1순위: 제조/유통(SCM) — 담당 업무와 직결
- 2순위: 개발자 생산성 / DevTools
- 사유: 1,416개 화면이라는 실제 과제로 학습 내용을 즉시 실무 적용하고 정량 검증 가능

## 5. 8주 목표 설정

### 8주 안에 검증 가능한 최소 단위
**화면 유형별 대표 20~30개의 서버 로직 전환.** 1,416개 전체를 대상으로 하지 않는다.

### 최종 데모에서 반드시 보여줄 핵심 결과물
> 폴더를 지정하면 **계획 수립 → 규칙 기반 변환 → LLM 포팅 → 정적 검증 → 수리 → 영향도 분석**까지 자동 진행되고, **사람이 승인해야만** 산출물이 반영되는 전 과정.

### 성공 판단 핵심 지표 3개
| # | 지표 | 목표 | 측정 방법 |
|---|---|---|---|
| 1 | nctRid 매핑 자동 확정률 | 80% 이상 | 자동 확정된 nctRid 수 / 전체 nctRid 수 |
| 2 | 1차 자동변환 커버리지 | 70% 이상 | 생성 코드의 `mvn compile` 통과율 |
| 3 | 사람 수정 라인 비율 | 30% 이하 | 자동 생성 라인 대비 리뷰 중 수정 라인 |

### 목표
| 구분 | 내용 |
|---|---|
| 기술 목표 | "분석 → 계획 → 생성 → 검증 → 수리" End-to-End 파이프라인 PoC. **변환기와 검증기를 분리된 모듈로** 구축 |
| 비즈니스 목표 | 대상 화면 서버 로직 1차 자동 변환율 70%+, 사람 수정 라인 비율 30% 이하 |
| 성장 목표 | Lv.3 Middle AI 개발자로서 1,416개 화면 규모 실전 적용 역량 증명 |

## 자기 평가 — 이번 주 가장 큰 불확실성

**"Python 초급~중급인 사람이 8주 안에 코드 변환 파이프라인을 만들 수 있는가"** 가 이 계획의 최대 리스크다. 이에 대한 대응은 야심을 키우는 게 아니라 **범위를 좁히는 것**이다:
1. 결정론적으로 풀리는 변환(문법 치환, 시그니처 매핑)에는 LLM을 쓰지 않는다 → 구현 난이도와 비용을 동시에 낮춤
2. 1,416개가 아니라 유형별 20~30개로 시작한다
3. UI 전환을 1단계에 넣지 않는다 → 검증 방법이 전혀 다른 두 문제를 동시에 풀지 않음
