## 슬라이드 1 — 프로젝트 개요 (2분)

### 문제 정의 (한 문장)

> **화면-서비스 매핑(nctRid)이 명명 규칙과 일치하지 않아, 서버 로직을 전환하려면 화면마다 사람이 P/F/D/XSQL 4종 파일을 직접 추적해야 한다.**

**비즈니스 임팩트 (1줄)**
> 전환 대상이 1,416개 화면이라 이 추적 작업이 1,416회 반복되며, 원본에 섞인 결함은 전환 도중에야 발견된다.

*(작성 가이드의 "나쁜 예 = 솔루션을 설명" 회피: 만든 것이 아니라 겪는 문제를 먼저 진술)*

### 핵심 기능 — Agent 구성 흐름

```
Planner            →  Translator(규칙)   →  Translator(LLM)   →  Validator      →  Repairer
계획을 파일로 고정      iBatis→MyBatis         업무 로직만 포팅       변환기와 분리      검증 실패 피드백
LLM 미사용             골격·DTO 생성          콜리 계약 주입         정적·빌드·차등     라운드 상한
                                                                        ↓
                                                            Analyzer(영향도) → 사람 승인 게이트
```

**기술 스택**: LangGraph (StateGraph / Send 병렬 / 조건부 사이클) · tree-sitter (오류 복구 Java 파싱) · 사내 LLM Gateway (Azure OpenAI 호환) · Oracle (매핑 그래프) · Maven (빌드 검증) · Streamlit (리뷰 UI)

### 핵심 성과 (실측 3개)

| 기준 | 지표 | 수치 |
|---|---|---|
| ① **정확도** | 전환 성공률 (5화면) | **산출물 25/25종 · 정적 검증 29/30건 (96.7%)** |
| ② **자동화율** | 결정론 처리 비중 | 포팅 28건 중 **13건을 규칙으로 회피(46%)**, 낭비 호출 **5건→1건(80%↓)** |
| ③ **사용자 체감** | **리뷰 대상 축소율** | 생성 1,783줄 중 사람이 정독할 곳 **→ 71.8% 감소** |

**종합 스코어카드: 82.9점 / 100** (전환 성공률 39.2/40 · 사용자 체감 18.5/30 · 탐지 정확성 25.2/30)
미측정 항목(기능 동등성·사람 수정 라인)은 **0점 처리도 만점 처리도 하지 않고 분모에서 제외**.

> 파일럿 범위는 **5화면**으로 확정. 30화면 세트는 정답키 대조(정적 분석) 전용이며, 두 수치를 섞지 않는다.
> 매핑 자동 확정 100%는 `legacy-u-pla001-050` 세트 기준 — 세트를 반드시 병기.

### Key Message

> **결정론적으로 풀리는 변환에서 LLM을 걷어내고, 남은 좁은 영역에만 LLM을 쓰는 경계 설계로 — LLM 호출을 80% 줄이면서 생성 코드가 실제 컴파일을 통과하는 전환 파이프라인을 만들었습니다.**

### 시스템 아키텍처 다이어그램 (좌측 영역)

### 핵심 기술 선택 이유 3가지

**① LangGraph StateGraph — 단순 순차 스크립트로는 표현할 수 없는 4가지가 동시에 필요했다**

| 필요 | 이유 |
|---|---|
| 조건부 분기 | "포팅할 메서드가 있는가", "BLOCKER가 남았는가"로 경로가 갈림 |
| `Send` 병렬 fan-out | 화면 × 메서드 조합을 동시 처리 — 5화면 15건을 약 12초에 |
| reducer 기반 fan-in | 병렬 분기가 같은 필드에 써도 안전하게 병합 |
| **사이클** | 검증 실패 → 수리 → 재검증. 단방향 DAG로는 표현 불가 |

> **의도적으로 쓰지 않은 것 — 자율 탐색형 에이전트.** 1,416회 반복되는 작업에서는 모델이 매번 도구를 고르는 비용이 효용을 넘고, 불필요한 탐색 자체가 환각의 원인이다. 그래서 노드와 간선을 전부 코드로 고정했다. **자율성을 못 만든 게 아니라 이 문제에 맞지 않아 버린 선택**이다.

**② Self-Correction 루프 — 변환기와 분리된 검증·수리 (MatchFixAgent / ACToR 패턴)**

검증기가 낸 BLOCKER를 프롬프트에 피드백해 **해당 메서드만** 재생성한다. 설계 제약 3가지:
- 대상은 **LLM이 포팅한 메서드의 BLOCKER만** — 규칙 기반 생성물은 제외(LLM이 고칠 문제가 아님)
- **라운드 상한** — 무한 재분석은 자율 탐색이 되어버린다
- 예산 소진 시 **포기하고 사유를 남긴다** — 조용히 성공한 척하지 않는다

검증 자산이 변환기와 분리돼 있어 **변환기를 바꿔도 살아남고, 다른 전환 프로젝트에 검증 루프만 이식**할 수 있다.

**③ Tree-of-Thoughts — 단, 평가자가 LLM이 아니다**

수리 시 서로 다른 방침(`최소수정`/`계약우선`)으로 후보를 **병렬 생성**하고, 후보마다 실제로 splice한 사본에 **검증기를 돌려 잔여 BLOCKER 수로 채점**해 하나를 고른다. 일반적인 ToT는 모델이 자기 가지를 자기가 평가해 신뢰도가 낮은데, 이 프로젝트에는 **결정론적 검증기**가 이미 있어 그 약점을 피한다.
*(실측: 이번 사례는 두 후보 모두 0건이라 결과가 바뀌지 않았다 — 확인에 그쳤음을 그대로 보고)*

**④ MCP — 읽기 전용 조회로만 한정**

| 대상 | MCP 노출 | 이유 |
|---|---|---|
| 변환 실행 | **안 함** | 승인 게이트 우회 경로를 열지 않는다 |
| 분석 조회 | **함** | 부작용 없는 결정론적 그래프 조회 |

MCP를 "자율성 부여"가 아니라 **"사람이 쓰는 조회 창구"** 로 쓴 설계 결정이다.

**⑤ 의존성 계약 주입 — AlphaTrans (FSE 2025, arXiv:2410.24117)**

AlphaTrans는 조각마다 콜러/콜리·입출력 타입을 메타데이터로 뽑아 콜그래프 역순으로 번역한다. 이 프로젝트는 5-fragment 분해·역순 변환·콜그래프를 **이미 갖고 있었고, 빠진 건 "그 메타데이터를 실제로 프롬프트에 넣는 것"** 하나였다. 콜그래프에서 뽑은 실제 Store 메서드명을 주입해 LLM이 이름을 추측하지 못하게 고정한다.

> **논문 인용 시 유의**: AlphaTrans 실측은 **문법 96.40% vs 테스트 통과 25.14%**. 이 간극이 그대로 우리 리스크이며, 슬라이드 3의 난제로 이어진다.

## 슬라이드 3 — 핵심 기술 과제 (4분) ★심사 집중 슬라이드

### 핵심 난제 (Hurdle) — 왜 기존 방법으로 안 되는가

> **"컴파일이 되니까 변환이 됐다"는 판정이 성립하지 않는다.**

정적 검증(문법·참조 검사)만으로 파이프라인을 돌리면 다음이 전부 **통과**로 나온다:
- LLM 포팅이 **전량 실패**해 스텁만 남은 코드 → 컴파일은 된다(런타임에만 예외)
- 존재하지 않는 데이터 메서드를 호출하는 코드 → 계층 간 참조 검사 없이는 안 잡힌다
- 원본 자체의 SQL 문법 오류 → 문법 변환기는 통과시킨다

즉 **"검사하지 않은 것"과 "통과한 것"을 구분하지 못하는 게 진짜 장벽**이었다. AlphaTrans가 보고한 문법 96.40% vs 기능 25.14%의 간극이 정확히 이 지점이다.

### 엔지니어링 접근

**(1) 판정 체계를 6종으로 표준화하고 `SKIPPED`를 `PASS`와 분리**
`PASS / WARNING / BLOCKER / FAIL / SKIPPED / APPROVED`. 도구·DB·문서가 전부 이 용어만 쓴다. **`SKIPPED`를 `PASS`로 집계하지 않는다**는 규칙 하나가 "미지원인데 통과로 보이는" 착시를 없앴다.

**(2) 추론 과정을 구조화 로그로 외부화 → 도구가 자기 자신을 검사하게 만듦**

```
[ 13.0s] │  BLOCK    PLA087 [CROSS_LAYER_REF] UNRESOLVED_STORE_CALL @ fPLA087QrySelectMainList:82
[ 13.0s] ┌─ STAGE 5/7  REFLECT  자기 수정 게이트 — 라운드 0/2 사용
[ 13.0s] │  REFLECT  수리 대상 1건 확정 → 라운드 1 진입
[ 16.3s] │  PASS     결합(fan-in) 완료 — 1건을 Service에 반영
[ 16.3s] ┌─ STAGE 4/7  VALIDATE  정적 검증 (수리 1라운드 후 재검증)
[ 16.3s] │  BLOCK    검증 결과 — BLOCKER 1건 · WARNING 0건     ← 2건에서 1건으로
```

**(3) 정답키 기반 자체 벤치마크로 탐지 성능을 수치화** — 정답을 아는 30화면 세트(결함 10건 / 중복 330행)로 재현율과 오탐을 매번 같은 값으로 측정.

### 결과 및 성과 (수치)

**① 자기 수정 루프가 실제로 결함을 해결 — 원인 규명 후 before/after**

| | 수정 전 | 수정 후 |
|---|---|---|
| 주입 결함(존재하지 않는 메서드 호출) | 2라운드 소진 후 **악화·포기** | **1라운드 해결** |
| 수리 프롬프트 | 546자 (**코드 미포함**) | 2,165자 (코드+실재 메서드 목록) |
| 잔여 BLOCKER | 2건 | **1건** |

> **근본 원인**: 수리 프롬프트가 AS-IS 전용 파서로 TO-BE 코드를 읽으려 해 "현재 코드"가 **빈 문자열**로 나갔다. 모델은 보이지도 않는 코드를 고치라는 요청을 받고 이름을 지어냈다(`dPLA08710 → fPLA087QrySelectMainList → fPLA087QrySelectMain`). **목 테스트는 프롬프트와 무관하게 고정 코드를 반환해 이 결함을 잡지 못했다.**

**② 비용 — 결정론/LLM 경계 설계의 효과**

| 항목 | 값 |
|---|---|
| 재시도 루프의 무효 호출 제거 | 화면당 **5건 → 1건 (80%↓)** |
| 규칙 기반으로 회피한 포팅 | 15건 중 **13건 (46% 결정론 처리)** |
| 5화면 End-to-End | 25파일 생성, **약 16초** |

**③ 탐지 성능 — 정답키 대조**

| 측정 | 결과 |
|---|---|
| 원본 결함 탐지 | **10/10 (100%), 오탐 0건** *(탐지기 보강 전 5/10)* — 전 분류 만점 |
| 중복 탐지 (Type-1 → Type-2) | 재현율 **50% → 100%**, 단 오탐 **0% → 48%** |

> Type-2 정규화는 재현율을 2배로 올리는 대신 오탐을 만든다. **어느 한쪽이 정답이 아니라 재현율↔정밀도 트레이드오프**이므로 두 수치를 함께 보고한다.

### 성장 가능성 — 실패에서 배운 것

**가설 H3 "정적 검증만으로 정확성을 보증할 수 있다" 는 반증됐다.**

반증되지 않았다면 "정적 검증 통과 = 전환 완료"라는 전제로 1,416화면에 확장했을 것이고, 그 오류는 운영에서 드러났을 것이다. 이 반증이 바꾼 것:
- 성공 지표를 **L1 구조 / L2 문법 / L3 기능 / L4 공수** 4층으로 분리, L2 통과를 완료로 인정하지 않음
- 다음 단계 1순위가 "수리 루프 고도화"가 아니라 **"포팅 결과를 실행할 수단 확보"** 로 바뀜

**미달 지표를 미달로 보고한다**: 기능 동등성(실행 환경 부재), 사람 수정 라인 비율(리뷰 완료 화면 0건). **추정치를 채우지 않았다.**

## 발표 시 유의사항

| 항목 | 내용 |
|---|---|
| 시간 배분 | 개요 2분 / 아키텍처 4분 / 기술과제 4분 — **아키텍처에서 늘어지는 경우가 가장 많음** |
| 수치 표기 | 실측값만. 세트가 다르면 **어느 세트 기준인지 반드시 병기** |
| ToT/MCP 질문이 나오면 | 쓰지 않았다고 답하고 **왜 버렸는지**를 설명(반복 작업에서 자율 탐색은 비용>효용). 대신 Plan-then-Execute·Self-Correction·의존성 주입을 적용했고 **논문 근거가 있다**고 연결 |
| 가장 강한 카드 | 슬라이드 3의 **before/after 표** — 원인 규명 → 수정 → 재측정이 한 화면에 있음 |
