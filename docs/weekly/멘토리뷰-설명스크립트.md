## 2. 개발 기준 — 무엇을 어떻게 만들었나 (5분)

### 2.1 결정론/LLM 경계가 이 프로젝트의 설계 결정 전부다

> "LLM이 코드를 변환한다"고 말하면 **"1,416개 화면을 LLM이 짜면 환각은요?"**가 바로 옵니다.
> 저희 답은 이겁니다 —

```
XSQL  ──[규칙]──▶ Mapper.xml        문법 치환만. LLM 안 씀
D     ──[규칙]──▶ Store             메서드 시그니처 → 골격
F     ──[규칙]──▶ Service 골격 ─[LLM]─▶ 본문     계산·분기만 LLM
P     ──[규칙]──▶ Api 골격    ─[LLM]─▶ 본문     오케스트레이션이 있을 때만
```

**정확히 말할 것**: 결정론 처리 비중은 **46%**(포팅 대상 46건 중 21건)다. 80%가 아니다.
그리고 **LLM이 채우는 곳은 Service 본문만이 아니다** — Api 본문도 채운다(§3.1 참고).
이 두 가지를 부풀려 말하면 코드를 열었을 때 바로 어긋난다.

### 2.2 자기 수정 루프 — LLM이 서술하는 게 아니라 코드가 판정한다

시연에서 터미널 로그를 보여줄 부분이다.

```
STAGE 4/7  VALIDATE  정적 검증
  BLOCK  PLA087 [CROSS_LAYER_REF] UNRESOLVED_STORE_CALL @ fPLA087QrySelectMainList:93
STAGE 5/7  REFLECT  자기 수정 게이트 — 라운드 0/2 사용
  REFLECT  수리 대상 확정 → 라운드 1 진입
  TOOL     LLM Gateway  수리 후보 [최소수정]  · 프롬프트 2,498자
  TOOL     LLM Gateway  수리 후보 [계약우선]  · 프롬프트 2,555자
  REFLECT  후보 [최소수정] 채점 — 잔여 BLOCKER 0건   ← 검증기가 채점(LLM 자기평가 아님)
  DECIDE   [최소수정] 채택
```

**설명 포인트 2개**:
1. **Tree-of-Thoughts인데 평가자가 LLM이 아니다.** 보통 ToT는 모델이 자기 가지를 자기가
   채점해 신뢰도가 낮다. 여기는 후보마다 **실제로 코드에 반영한 사본을 만들어 정적 검증기를
   돌리고**, 그 메서드에 귀속된 BLOCKER 수로 채점한다.
2. **로그는 모델이 쓴 문장이 아니다.** `agents/reasoning_log.py`의 원칙은 "없는 추론을 지어내지
   않는다" — 코드가 이미 내린 분기 결정을 그 시점의 실제 값으로 받아 적는다.

> **예상 질문**: "프롬프트로 로그 포맷을 강제하면 더 그럴듯하지 않나요?"
> **답**: 그러면 **모델이 추론을 연출**하게 됩니다. "이 문구는 시스템 판정인가요, 모델이 쓴
> 건가요?"라는 질문에 지금은 "판정입니다"라고 답할 수 있는데, 그 답을 잃습니다.

### 2.3 공통 함수 — 무엇이 공통인지 추측하지 않고 측정했다

화면 30개가 `fAuthCheck`/`fCommonCodeQry`/`fHistoryQry`를 **똑같이** 갖고 있다. 그대로 옮기면
30벌 사본이 30벌이 된다.

**판정 방법**: 중복 탐지의 정규화 단계를 재사용해 **어느 단계에서 하나로 수렴하는지** 본다.

| 수렴 단계 | 뜻 | 판정 |
|---|---|---|
| EXACT | 글자 그대로 같다 | 공통화 |
| SCREEN | 화면 ID만 치환하면 같다 | 공통화 |
| LITERAL 이하 | 리터럴까지 지워야 같아진다 | **안 함** — 다른 로직일 수 있다 |

**이 안전선이 실제로 일했다**: 공통 이력 조회 SQL은 겉보기에 같지만 도메인 코드 리터럴이 달라
5그룹으로 갈린다. 합쳤으면 5개 도메인이 한 쿼리를 쓸 뻔했다.

**한 번 더 걸렀다**: 그 SQL을 부르는 *함수*는 본문이 30화면 EXACT 동일해서(한 줄짜리니 당연히)
확정 목록에 넣었었다. `check_registry()`가 **"함수는 그 SQL까지 공통이어야 공통화할 수 있다"**를
강제해 걸러냈다.

> **부수 성과**: `fCommonCodeQry`는 29화면이 한 덩어리인데 **1화면만 갈라진다** — 그 화면이
> 데이터 조회 대신 함수 조회 API를 부르는 원본 결함(정답키에 심어진 것)이기 때문이다.
> **"이거 같은 함수 맞아?"라고 물었더니 결함이 나왔다.** 별도 결함 탐지기가 같은 화면을
> 독립적으로 지목해서 두 관점이 서로를 교차 검증한다.

### 2.4 조회 전용 가정 — 드러내기에서 구현까지

원래 변환기는 **조회(SELECT)만** 다뤘다. 확보한 원본이 조회 전용이었기 때문이다.

- **1단계(샘플 없음)**: 지원을 만들지 않고 **미지원을 이름 붙여 드러냈다**. 본 적 없는 패턴에
  규칙을 짜는 건 "확인 안 된 규칙 추측 금지" 위반이다.
- **2단계(샘플 확보, 이번 주)**: 실제 CRUD 화면이 들어왔다 — 한 화면에 insert 7·update 5·
  delete 1·프로시저 3. 막고 있던 조건이 사라져서 구현했다.

> **함정 하나 — 실행 종류는 Java가 아니라 XSQL이 정한다.** 이 코드베이스는 UPDATE 문도
> `dbInsert("U001", ...)`로 호출한다. Java 동사를 믿었으면 **UPDATE에 insert()를 걸었을 것**이다.

| | 구현 전 | 구현 후 |
|---|---|---|
| Store 호출 | 전부 `selectOne` 26건 | selectOne 17 · insert 4 · **update 4** · delete 1 |
| `TODO_확인필요` 참조 | 다수 | **0건** |
| Mapper id 매핑 | select만 | 26개 중 **20개** |

**프로시저 3건은 여전히 미지원**이다. 1단계의 드러내기 장치가 그대로 잡아준다 —
**드러내기는 지원의 임시 대체물이 아니라 범위 밖을 계속 지키는 상시 장치**다.

## 3. 평가지표 기준 — 무엇을 어떻게 쟀나 (7분)

### 3.1 이번 회차 최대 성과: 안 보던 계층을 재자 결함이 나왔다

**Api(HTTP/직렬화) 계층을 처음 측정했다.** 결과 **0/9**.

| 케이스 | AS-IS | TO-BE(수정 전) |
|---|---|---|
| 목록 조회(권한 없음) | `@msg=W0024` | `AUTH_YN=N` |
| 목록 조회(1행) | `@msg=I0016; MAIN_LIST#1` | `AUTH_YN=Y` |
| 이력 조회(1행) | `@msg=I0016; HIST_LIST#1` | `AUTH_LIST#1;CODE_LIST#1;…` (전부 새어 나감) |

생성된 Api가 `return ResponseEntity.ok(service.fAuthCheck(request));` **한 줄**이었다. 본문에서
처음 만나는 F 호출 하나만 위임하고 나머지를 버린다. 권한 게이트도, 결과 메시지도, 어느
레코드셋을 돌려줄지도 전부 사라진 상태였고 — **정적 검증은 전부 통과했다.**

> **이게 AlphaTrans가 보고한 문법 96.4% vs 기능 25.1% 간극이 저희 파이프라인에서 재현된
> 것입니다.** 그리고 원인은 **표본 1건짜리 가정**이었습니다. 아키텍처 문서에 "P는 순수
> 위임"이라고 적혀 있었고 근거는 화면 하나였는데, 30화면 전수로 보니 **30/30에서 거짓**이었습니다
> (권한 게이트 30/30, 결과 메시지 호출 195건, 레코드셋 선별 165건).

**고친 결과: 페이로드 0/9 → 9/9 (100%).**

**엄격 일치는 여전히 0/9이고 이건 의도한 상태다.** 남은 차이가 전부 결과 메시지 코드인데,
이걸 담을 TO-BE 응답 규약이 **아직 확정되지 않았다**. 규약 없이 키를 지어내는 건 멘토 §2가
경고한 바로 그것이라, 생성기가 자리를 비워두고 BLOCKER를 올린다. 하네스도 **페이로드 일치와
메시지 일치를 나눠 보고**해서 "우리가 못 옮긴 것"과 "아직 아무도 정하지 않은 것"을 섞지 않는다.

> **부수 성과**: 응답 규약의 열린 질문 중 "경고/안내 코드가 예외인가 메시지인가"는 실사용
> 사례가 없어 확인 불가였는데, 이번에 찾았다 — 응답 객체에 설정한 뒤 **던지지 않고 그대로
> 반환**한다. 메서드 이름부터 `setOk...`다. **성공 응답의 안내 메시지**이고 30/30이 이 패턴이다.
> 담을 자리를 정하는 건 여전히 사람 몫이지만, **무엇을 담아야 하는지는 이제 추측이 아니다.**

### 3.2 두 번째 성과: "100%"의 분모가 3/5였다

Api 계층을 고치고 검증하다 발견했다. 하네스가 AS-IS와 TO-BE 함수를 **이름으로** 짝짓는데,
규칙 기반 단순 위임은 생성 시 이름이 바뀐다. 그래서 그 함수들이 **비교에서 통째로 빠졌다.**
한 화면은 F 함수가 5개인데 3개만 재고 "F 계층 100%"라고 보고하고 있었다.

**빠진 둘이 하필 문제 있는 쪽이었다.**

```
공통코드 조회   AS-IS  CODE_LIST#1
                TO-BE  AUTH_LIST#1;CODE_LIST#1;DETAIL_LIST#1;HIST_LIST#1;MAIN_LIST#1
```

원본은 레코드셋 **하나만** 꺼내는데 결과 Map을 통째로 되돌려주고 있었다. **"규칙 기반이라
안전하다"고 말해 온 경로에서 나온 결함**이라 더 뼈아프다. 탐지기는 이미 레코드셋 이름을 알고
있었고 그냥 버리고 있었다.

**F 계층 27/27(3/5 함수) → 48/48(5/5 함수).** 같은 100%지만 **분모가 진짜다.**

### 3.3 점수가 88.2에서 80.9로 내려갔다 — 이걸 먼저 말한다

> **되돌리지 않았습니다.** 도구가 나빠져서가 아니라 **안 재던 것을 재기 시작해서**입니다.
> ① Api 계층을 처음 쟀고 ② 결정론 처리 비중의 분모가 틀렸던 걸 고쳤습니다(P 메서드를
> "규칙으로 처리했다"고 세고 있었는데 실제로는 아무것도 변환하지 않고 있었습니다).
> **측정 범위를 넓히면 점수는 내려갑니다. 그 방향이 맞다고 봤습니다.**

| 축 | 배점 | 획득 | 비고 |
|---|---|---|---|
| A. 전환 성공률 | 30 | 29.40 | 산출물 25/25, 정적 검증 29/30 |
| B. 사용자 체감 | 25 | 19.82 | 결정론 46%가 깎는 요인 |
| C. 탐지 정확성 | 20 | 16.67 | 결함 10/10, 중복 F1 66.7% |
| D. 기능 동등성 | 25 | 15.00 | **Api 0점이 그대로 반영됨** |
| **합계** | **100** | **80.89** | |

**미측정은 분모에서 뺀다**(0점도 만점도 아니다). 단 **Api 0%는 미측정이 아니라 측정된
실패**라 그대로 0점을 줬다 — 남은 차이가 "우리가 아직 못 정한 규약" 때문이라 해도 후하게
주지 않는다.

### 3.4 스스로 깎은 지표 — 신뢰의 근거로 쓴다

| 지표 | 처음 | 정정 후 | 왜 |
|---|---|---|---|
| 리뷰 대상 축소율 | 99.7% | **87.6%** | LLM 포팅 라인은 이슈가 없어도 사람이 다 읽어야 한다 |
| 중복 탐지 F1 | 68% | **66.7%** | 채점 분모에 존재하지 않는 이름이 섞여 부풀려져 있었다 |
| 결정론 처리 비중 | 75% | **46%** | P 메서드를 규칙 처리로 세고 있었는데 변환을 안 하고 있었다 |
| 종합 점수 | 89.7 | **80.9** | 위 누적 + Api 계층 측정 |

> **이 표가 이 프로젝트에서 가장 중요한 슬라이드일 수 있습니다.** 유리한 정의를 버리고
> 방어 가능한 정의를 택할 때마다 점수가 내려갔고, 그걸 전부 기록에 남겼습니다.

## 4. 예상 질문과 답 (준비된 것만)

| 질문 | 답 | 근거 |
|---|---|---|
| "차등 테스트가 실제로 도나요?" | SQL 계층은 로컬 Oracle에 양쪽 실행해 비교합니다. **레거시 서버 vs 신규 서버 HTTP 왕복은 못 합니다** — NEXCORE 런타임이 없습니다. 대신 최소 스텁으로 AS-IS를 **실제로 실행**해 비교합니다 | `diff_test.py`·`equivalence_test.py` |
| "RAG는요?" | **의도적 미도입**입니다. 멘토 §J에서 LLM이 6번, RAG는 그 이후고 파일럿 결과물이 코퍼스가 되어야 성립합니다. 저장소에 벡터 DB 흔적 0건인 건 순서입니다 | 멘토 §J·§I |
| "LLM이 다 짜면 환각은?" | LLM은 골격이 100% 확정된 뒤 **빈 본문만** 채웁니다. 결정론 처리 46%이고, 호출 대상 이름은 콜그래프에서 뽑아 프롬프트에 **주입**해 지어내지 못하게 합니다 | `_callee_note` |
| "화면 5개로 뭘 말할 수 있나요?" | **통계적 주장은 안 합니다.** 파일럿 목표는 "유형별 변환 레시피와 실측 공수 확보"이고, 탐지 성능만 30화면 정답키로 별도 채점합니다 | 멘토 §5 |
| "공수 절감률은?" | **미측정입니다.** 기준선(사람이 손으로 하는 화면당 공수)을 실측한 적이 없습니다. 대리 지표로 사람 수정 라인 비율 0.20%를 보고하되 **AI 리뷰어 1차 기준 하한값**이라고 명시합니다 | 멘토 §H |
| "왜 점수가 내려갔나요?" | §3.3 그대로 답한다 | — |

### 답하지 말아야 할 것 (모르는 것은 모른다고)

- **"공수 65~70% 절감됩니다"** ❌ — 기준선 미실측. 약속하지 않는다(멘토 §4).
- **"기능 정확도 95%입니다"** ❌ — 계층별로 나눠 말한다. F 100%, Api 페이로드 100%, Api 엄격 0%.
- **"1,416개 화면에 바로 적용 가능합니다"** ❌ — 파일럿 5화면 + 탐지 30화면이 전부다.
