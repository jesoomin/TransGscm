# 4주차 — 기술 설계 및 아키텍처

**프로젝트**: G-SCM 차세대 전환 Agent
**범위**: 전환 프로그램 **1단계 = 서버(Java/XSQL → Spring/MyBatis) 전환**

## 1. AS-IS → TO-BE 매핑 (확정)

`docs/07-tobe-structure.xlsx`(AS_IS/TO-BE 시트)로 확정된 실제 구조다. **추측이 아니라 실제 화면 1건(PLA047) 기준으로 확인된 값**이다 — 다만 *1건 기준*이라는 단서가 나중에 실제로 문제가 됐다(아래 §1.1).

| AS-IS | TO-BE | 역할 | 변환 방식 |
|---|---|---|---|
| UIAdapter + nctRid 디스패처 + P BizUnit | `{화면}Api` (Controller) | REST 엔드포인트. **nctRid 1개 = 엔드포인트 1개** 유지 | **순수 위임이면 규칙 기반 / 오케스트레이션이 있으면 LLM** |
| F BizUnit | `{화면}Service` | 업무 로직 포팅. 프레임워크 의존만 제거, 계산·분기는 그대로 | **LLM** |
| D BizUnit | `{화면}Store` | 데이터 접근 포팅 | 규칙 기반 |
| `{화면}.XSQL` (iBatis) | `{화면}Mapper.xml` (MyBatis) | 문법만 변환 | 규칙 기반 |
| `.BIZUNIT` XML | `{화면}Dto` | 입출력 스키마. 비어 있으면 코드 실사용값에서 역추출 | 규칙 기반 |
| 하드코딩 메시지 코드 | `errors.properties` / `errors_en.properties` | 국제화 대비 외부화 (신규 산출물) | 규칙 기반 |
| DB 스키마 | **변경 없음** | — | — |

> **설계 의도**: nctRid를 범용 CRUD API로 재설계하지 않고 1:1로 유지한다. 재설계하면 2단계 UI 트랙이 어떤 API를 부를지 다시 정해야 하고, 차등 테스트의 비교 기준(동일 입력 → 동일 응답)도 무너진다.

### 1.1 표본 1건으로 세운 가정이 틀렸던 곳 — P 계층 (2026-09-05 정정)

이 표는 원래 P → Api를 **규칙 기반**으로 적어뒀다. 근거는 PLA047 한 화면이 순수 위임이었다는
것이고, 그래서 생성기도 `return ResponseEntity.ok(service.fXxx(request));` 한 줄을 만들었다.

30화면 코퍼스를 전수 확인하니 그 가정이 **30/30에서 거짓**이었다.

| 확인 항목 | 실측 |
|---|---|
| 권한 게이트(`AUTH_YN` 확인 후 조기 반환)를 가진 P 파일 | **30 / 30** |
| `setOkResultMessage` 호출 | **195건** |
| `getRecordSet`으로 반환할 레코드셋을 골라 담는 코드 | **165건** |

즉 P는 진입점이 아니라 **여러 F를 순서대로 부르고 분기하는 오케스트레이션 계층**이다. 위임
한 줄로 만들면 그 로직이 통째로 사라지는데, **정적 검증은 전부 통과한다** — 문법적으로는
완벽히 올바른 코드이기 때문이다.

**지금 구조**: `skeleton_gen.detect_p_orchestration()`이 P 메서드를 둘로 가른다.

```
P 메서드
 ├─ 순수 위임 (F 호출 1건, 분기 없음, 메시지 없음)  → 규칙 기반 한 줄  (변경 없음)
 └─ 오케스트레이션 보유                              → Api PORT 스텁 → LLM 포팅
    (권한 게이트 · 결과 메시지 · 레코드셋 선별)         + Api 전용 프롬프트
```

포팅 레인이 `Service.java`로 하드코딩돼 있던 것도 **대상 파일 기준으로 일반화**했다 —
F는 Service로, P는 Api로 결과가 들어간다.

## 2. 결정론적 변환 / LLM 변환의 경계

**이 경계를 잘못 그으면 비용은 쓰고 품질은 안 나온다.** 이 프로젝트의 가장 중요한 설계 결정이다.

### 100% 규칙 기반 (LLM 사용 금지)

| 대상 | 변환 규칙 |
|---|---|
| iBatis → MyBatis | `#var#`→`#{var}`, `$var$`→`${var}`, `<isEqual>/<isNotEqual>`→`<if>`, `<isNotEmpty>`+`<iterate>`→`<if>`+`<foreach>`, `<dynamic prepend>`→`<where>` |
| BizUnit 메서드 시그니처 → Api/Service/Store 골격 | 클래스·메서드 이름, 파라미터 자리, 계층 간 위임 호출 |
| 화면 간 공통 메서드 → 공통 클래스 위임 | 본문이 화면 간 동일한 것만 (`config/common-methods.json`에서 사람이 확정한 목록) |
| `.BIZUNIT` 필드(또는 역추출한 필드) → DTO | 필드명·타입 매핑 |
| D 메서드 → Mapper statement id | `dbSelect("S00N", ...)` 호출에서 id 추출 |

### LLM 필요

| 대상 | 이유 |
|---|---|
| **P BizUnit의 오케스트레이션 → Api 메서드 본문** | 여러 F 호출 순서, 권한 게이트 조기 반환, 결과 유무 분기, 반환할 레코드셋 선별 (순수 위임 P는 여전히 규칙 기반) |
| F BizUnit 내부 계산·분기 로직 → Service 메서드 본문 | 기계적 1:1 치환이 불가능. 특히 프레임워크 전용 API 호출부 |
| `.BIZUNIT` 필드가 비어 있을 때 스키마 추론 | 코드 실사용 패턴 해석 필요 |
| 메시지 코드 → 메시지 문구 정리 | 문맥 필요 |

### 절대 자동화 금지
공통 응답/예외 처리 규약, 공통 Mapper/Store 패턴. **사람이 먼저 확정한 뒤 에이전트에 강제 컨텍스트로 주입**한다. 이 순서를 어기면 1,416개 화면에 1,416가지 변형이 생겨 현재의 "개발자별 이원화" 문제가 그대로 재현된다.

## 3. 파이프라인 아키텍처

### 3.1 왜 상태 그래프(LangGraph)인가

초기에는 사내 GaiA를 우선 검토했으나, 이 문제에는 아래 4가지가 동시에 필요해 상태 그래프 오케스트레이션을 채택했다.

| 요구 | 필요 이유 |
|---|---|
| **조건부 분기** | "포팅할 함수가 있는가", "검증 실패가 남았는가"에 따라 경로가 갈림 |
| **병렬 디스패치** | 화면 × 함수 조합을 동시에 처리해야 실용적 속도가 나옴 |
| **상태 병합(reducer)** | 병렬 분기가 같은 필드에 쓰므로 안전한 병합 규칙 필요 |
| **순환(사이클)** | 검증 실패 → 수리 → 재검증 루프. 단방향 파이프라인으로는 표현 불가 |

> **자율 탐색형 에이전트는 만들지 않는다.** 1,416회 반복되는 작업에는 자유 탐색보다 **고정된 파이프라인**이 낫다. 탐색 비용 대비 효용이 낮고, 불필요한 탐색 자체가 환각의 원인이다. 그래서 그래프의 노드와 간선은 전부 코드로 고정돼 있고, 모델이 다음 도구를 스스로 고르지 않는다.

### 3.2 파이프라인 구조

```
                       ┌──────────────────────────────────────┐
                       │  ① 계획 수립 (LLM 미사용)             │
                       │     화면별 계획 파일을 먼저 고정       │
                       └──────────────┬───────────────────────┘
                                      ▼
                       ┌──────────────────────────────────────┐
                       │  ② 규칙 기반 변환 (LLM 미사용)        │
                       │     Api/Store/Dto 골격 + Mapper       │
                       └──────────────┬───────────────────────┘
                                      ▼  (화면×함수 병렬 디스패치)
                       ┌──────────────────────────────────────┐
                       │  ③ LLM 포팅 → ④ 결과 결합             │
                       └──────────────┬───────────────────────┘
                                      ▼
                       ┌──────────────────────────────────────┐
                       │  ⑤ 정적 검증                          │
                       └──────────────┬───────────────────────┘
                                      ▼
                              ┌───────────────┐
                              │  수리 게이트   │
                              └──┬─────────┬──┘
                    BLOCKER 있음 │         │ 없음 / 예산 소진
                    (라운드 상한) │         │
                                 └────►③   ▼
                       ┌──────────────────────────────────────┐
                       │  ⑥ 품질·취약점 스캔                   │
                       │  ⑦ 참고용 대안 제안 (opt-in)          │
                       └──────────────┬───────────────────────┘
                                      ▼
                       ┌──────────────────────────────────────┐
                       │  ⑧ 임시 사본에 겹쳐쓰기 →             │
                       │     전체 교차 분석 + 빌드 검증         │
                       └──────────────┬───────────────────────┘
                                      ▼
                       ╔══════════════════════════════════════╗
                       ║   사람 승인 게이트 (필수)             ║
                       ╚══════════════┬═══════════════════════╝
                                      ▼
                             실제 산출물 + DB 반영
```

**핵심 설계 결정 3가지**

| # | 결정 | 근거 |
|---|---|---|
| D1 | **계획을 코드 생성보다 먼저 파일로 고정** | 계획이 있어야 리뷰·재현·재실행이 가능하다. 계획 파일은 LLM을 쓰지 않고 정적 분석만으로 만들어, 변환 결과에 의존하지 않고 **변환 전에** 존재할 수 있다 |
| D2 | **승인 전에는 실제 산출물 폴더를 건드리지 않는다** | 교차 분석·빌드 검증은 디스크의 파일을 읽어야 하므로 저장이 선행돼야 하는데, "사람 리뷰 없는 자동 반영 금지" 원칙과 충돌한다. **임시 사본에 겹쳐 쓰고 끝나면 항상 삭제**하는 방식으로 둘 다 지켰다 |
| D3 | **수리 루프에 라운드 상한을 둔다** | 무한 재분석은 자율 탐색이 되어 버린다. 상한을 넘으면 포기하고 사유를 남긴다 |

### 3.3 변환기 / 검증기 분리

변환기(Translator)와 검증기(Validator)를 **별도 모듈**로 둔다. 검증 로직이 변환 로직에 섞이면 변환기를 바꿀 때마다 검증 자산도 같이 깨진다. 분리해 두면 **검증·수리 루프만 다른 전환 프로젝트에 재사용**할 수 있다.

| 모듈 | 책임 | LLM |
|---|---|---|
| Planner | 무엇을 만들지 계획 | X |
| Translator (규칙) | 골격·Mapper·DTO 생성 | X |
| Translator (LLM) | 업무 로직 포팅 | O |
| Validator | 정적 검증, 빌드, 차등 테스트 | X |
| Repairer | 검증 실패 피드백 재생성 | O (상한) |
| Analyzer | 영향도·중복·미사용 분석 | X |

## 4. 변환 순서: 콜그래프 역순

**XSQL → Store → Service → Api** 순으로 진행한다. 하위 계층(SQL/데이터 접근)이 확정돼야 상위 계층 시그니처가 흔들리지 않는다. Api를 먼저 잡고 Store를 나중에 끼워 맞추지 않는다.

또한 화면 하나를 통째로 LLM에 넣지 않고 **5개 조각**(`.BIZUNIT` / P Java / F Java / D Java / XSQL)으로 나눠 처리한다. 조각 단위로 검증·리뷰가 가능해야 하기 때문이다.

## 5. 데이터 설계 — 매핑 그래프

| 테이블 | 행의 의미 | 주요 컬럼 |
|---|---|---|
| `CONV_FILE` | AS-IS 파일 1개 | 화면ID, 계층, 경로, 빌드 판정, 차등 테스트 판정, 사람 수정 라인 비율 |
| `CONV_METHOD` | 파일 안의 함수 1개 | AS-IS/TO-BE 이름, 본문 해시, 매퍼 statement id, **변환 방식**, 트랜잭션 |
| `CONV_METHOD_CALL` | 호출 관계 1개 (caller → callee) | 콜그래프의 간선 |
| `CONV_ISSUE` | 이슈 1건 | 유형, 심각도(BLOCKER/WARNING/INFO), 줄번호, **소속 함수**, 탐지 주체 |
| `NCTRID_MAP` | 트랜잭션 1개의 평탄화 매핑 | 화면ID, 트랜잭션ID, **출처 구분**, P/F/D 함수, 파일 식별자 |

**설계 포인트**
- `CONV_ISSUE.METHOD_ID`로 이슈를 **파일이 아니라 함수 단위**까지 연결한다. 이게 있어야 "어느 함수가 문제인가"를 집계할 수 있고, 수리 루프가 대상을 정확히 고를 수 있다.
- `NCTRID_MAP.NCTRID_SOURCE`로 **확정값인지 대체 규칙으로 채운 값인지** 구분한다. 출처를 숨기지 않는 게 이 프로젝트의 원칙이다.
- `CONV_METHOD.BODY_HASH`로 화면 경계를 넘는 **중복 함수**를 찾는다.

## 6. 검증 전략 — 차등 테스트

**"변환된다"와 "맞다"는 다른 문제다.** 문법 정확도가 높아도 기능적 정확성은 별개다.

```
동일 입력 → [AS-IS 경로] → 응답 ┐
                                ├→ 정규화 후 diff → 판정
동일 입력 → [TO-BE 경로] → 응답 ┘
```

AS-IS가 단일 진입점(nctRid)에 고정 응답 포맷을 쓰기 때문에 이 비교가 깔끔하게 성립한다. **이 하네스를 변환기보다 먼저 구축한다.**

### 참고 지표 (선행 연구)

| 연구 | 문법 정확도 | 기능 동등성 | 시사점 |
|---|---|---|---|
| AlphaTrans (FSE 2025, arXiv:2410.24117) | **96.40%** | 컴파일 27.03% / **테스트 통과 25.14%** | 의존성 인식 번역만으로는 기능 정확도가 따라오지 않는다 |

> 이 간극(96% vs 25%)이 그대로 우리 리스크다. 그래서 정적 검증 통과를 완료로 인정하지 않고, 별도의 기능 검증 층(L3)을 성공 지표에 둔다.

## 7. 기술 선택 근거

| 선택 | 대안 | 채택 이유 |
|---|---|---|
| **tree-sitter** (Java 파싱) | javalang, JavaParser | **오류 복구 파싱.** AS-IS 원본이 컴파일 안 되는 경우가 실제로 있어, 엄격한 파서는 그 파일에서 멈춘다 |
| **경량 파서 조합** | CodeQL 등 무거운 정적분석기 | 언어별 전용 파서 3종(XML/Java/SQL)이면 충분. 도입·학습 비용이 훨씬 낮다 |
| **상태 그래프 오케스트레이션** | 순차 스크립트 | 조건부 분기·병렬·사이클이 동시에 필요 (§3.1) |
| **사내 LLM Gateway** | 외부 LLM API 직접 호출 | 소스코드 외부 전송 보안 정책 대응 |
| **규칙 엔진 우선** | 전 구간 LLM | 비용·재현성·품질 모두 규칙이 유리한 영역이 대부분 |
| **자체 벤치마크** | 공개 벤치마크 | 이 도메인 전용 문제라 공개 벤치마크가 없음 |

## 8. 안전 설계 (가드레일)

| 가드레일 | 동작 |
|---|---|
| 승인 게이트 | 사람이 승인하기 전에는 결과물 폴더·DB에 아무것도 쓰지 않음 |
| 임시 사본 격리 | 승인 전 검증은 임시 사본에서 수행하고 종료 시 **항상** 삭제 |
| 생성 필드 대조 | LLM이 원본에 없는 필드를 만들어내면 자동 차단(BLOCKER) |
| 미지원 케이스 명시 | 추측으로 코드를 만들지 않고 미지원으로 표시 + 처리 안내 주석 |
| 원본 결함 보존 | 원본 버그를 임의로 고치지 않고 보존 + 별도 표시 |
| 테스트 데이터 정리 | 차등 테스트용 데이터는 식별 가능한 태그를 달고 `finally`에서 항상 삭제 |
| 자격증명 분리 | DB·게이트웨이 키는 환경 파일에만 두고 형상관리에서 제외 |

## 반영 사항 (3주차 피드백 대응)

| 3주차 지적 | 반영 내용 |
|---|---|
| 입력 예시 / 기대 출력 / 성공 기준이 비어 있음 | 3주차 문서의 모든 시나리오(SC-001~004)에 세 항목을 표로 채움 |
| 사용자 시나리오에 내부 구현 파일명이 과다 노출 | 시나리오를 **사용자 행동과 화면에 보이는 것** 중심으로 재작성. 내부 모듈명은 4주차(설계 문서)로 이동 |
| 예외 흐름 부족 | 각 시나리오에 예외 흐름 표(E1~E7)를 신설 |
| 판정 체계 표준화 필요 (WARNING/FAIL/BLOCKER/APPROVED 정의) | 3주차 §1에 **판정 표준 6종**(PASS/WARNING/BLOCKER/FAIL/SKIPPED/APPROVED) + 적용 규칙 4개 신설. 도구·DB·문서가 모두 이 용어만 사용 |
| 8주 범위와 장기 비전의 경계 | 2주차 §4 표로 분리 완료. 4주차 설계도 1단계 범위만 다룸 |
