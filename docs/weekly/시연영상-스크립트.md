# 시연 영상 스크립트 (5분)

> **제출 규격**: 5분 이내(초과분 평가 제외), MP4, `[사번]_[성명]_시연영상.mp4`, 500MB 이하.
>
> **가이드가 못 박은 배점 신호**
> - *"UI에서 처리 결과만 보여주는 경우 → 기술 구현 확인이 어려워 평가에 불리"*
> - *"핵심 로그가 담긴 터미널/콘솔 화면은 반드시 포함"*
> - *"Agent의 추론 과정이 보여지는 로그로 증명해야 기술 깊이를 평가받을 수 있다"*
> - 5분 중 **1:30~3:30(40%)** 이 "Planning / Self-Correction 단계 확대"
>
> **소스를 제출하지 않는다.** 화면에 보이는 로그가 유일한 증거다. 콘솔이 주인공, UI는 30초 이내 보조.

## 1. 이 영상이 증명할 것

| # | 증명 대상 | 근거로 쓸 화면 |
|---|---|---|
| 1 | Agent가 **스스로 계획을 세운다** | STAGE 1 `PLAN` / `DECIDE` |
| 2 | **계획이 도구 호출을 지휘한다** — 모델이 고르지 않는다 | STAGE 3 `PLAN` |
| 3 | 모델이 **자기 판단 근거를 남긴다** | `THINK` (모델 자신의 문장) |
| 4 | **실패를 스스로 고치고, 못 고칠 것은 넘긴다** | STAGE 5 `REFLECT` / `DECIDE` |
| 5 | 결과가 **정답과 맞는지 수치로** 증명된다 | 정답키 대조 + 실행 요약 |

---

## 2. 두 개의 소스 세트 — 왜 나눠 쓰는가

시연에 세트가 둘 나온다. **섞어 쓰면 틀린 주장이 되므로** 영상에서도 말로 구분한다.

| 세트 | 정체 | 이 영상에서의 역할 |
|---|---|---|
| **실제 전환 대상** (PLA045~050, 6화면) | 운영 소스 트리의 경영분석 화면 | "무엇을 전환하는가" |
| **정답키 평가 세트** (PLA087~100, 5화면) | 결함을 의도적으로 주입하고 **정답키를 함께 제공**하는 채점용 | "제대로 잡아냈는가" |

> **왜 평가 세트가 필요한가**: 실제 전환 대상에는 정답이 없다. 탐지·교정 성능을 *증명*하려면
> 정답이 확정된 세트가 있어야 한다. 이 한 줄을 0:20 지점에 넣는다.

## 3. 녹화 전 점검

| # | 항목 | 확인 |
|---|---|---|
| 1 | 터미널 UTF-8 | `chcp 65001` — cp949면 로그가 중단된다 |
| 2 | 폭 100컬럼 이상, 글꼴 14pt 이상 | 로그 줄이 접히면 못 읽는다 |
| 3 | 색상 | 안 나오면 `GSCM_LOG_COLOR=1` |
| 4 | 리허설 (LLM 미호출) | `--dry-run`으로 전 구간 재현 |
| 5 | 실행 시간 | 5화면 **약 40초** — 배속 없이 담긴다 |
| 6 | Streamlit 미리 띄우기 | 부팅 대기는 잘라낸다 |
| 7 | 화면 정리 | `.env` / API 키 / DB 접속정보 노출 금지 |

**명령**

```
# 리허설 — LLM 호출 없이 계획~검증 경로 그대로
python -m agents.run_pipeline <평가 세트> \
    --screens PLA087,PLA089,PLA093,PLA096,PLA100 --no-ai-recommend --dry-run

# 본 녹화
python -m agents.run_pipeline <평가 세트> \
    --screens PLA087,PLA089,PLA093,PLA096,PLA100 --no-ai-recommend

# 성과 수치
python -m agents.benchmark <샘플폴더> --answer-dir <정답키폴더>
```

#### (b) 모델이 남긴 근거 — THINK — 1:50~2:15

```
│  PASS     PLA087.fPLA087QrySelectMainList 응답 수신 (1,204자 · 3.4초)
│  THINK    PLA087.fPLA087QrySelectMainList — 모델이 밝힌 근거
│           "NEXCORE IDataSet/IRecordSet 의존을 Map 기반으로 치환하고 데이터 접근 호출을

│             선언만 되고 사용되지 않음. / FIXME(원본 버그): if 블록 닫힘 중괄호 누락."
```

> 변경 근거를 남기도록 요구하고, 그걸 콘솔로 되돌려 출력합니다. 근거가 없으면 지어내지 않고
> 아무것도 출력하지 않습니다.

> "**검증기는 변환기와 분리돼 있습니다.** 만든 쪽이 스스로 채점하지 않게 하려는 설계입니다.
> 정답키에 심어둔 결함을 포함해 10건을 잡았습니다."

#### (d) 자가 교정 게이트의 판단 — 2:40~3:10 ← **가장 확대할 곳**

```
┌─ STAGE 5/8  REFLECT  자가 교정 게이트 — 회차 0/2 사용
│  REFLECT  수리 대상 9건 확정 → 회차 1 진입
│           ↳ 검증 실패 메시지를 프롬프트에 피드백해 해당 메서드만 재생성한다
│  REFLECT  후보 [최소수정] 채점 — 잔여 BLOCKER 0건
│  REFLECT  후보 [계약우선] 채점 — 잔여 BLOCKER 0건
│  DECIDE   수리 후보 2개 → [최소수정] 채택  ↳ 잔여 BLOCKER 0건으로 최소
```

> "여기가 핵심입니다. BLOCKER **10건 중 9건만** 수리 대상으로 골랐습니다.
> XML 태그 누락은 **규칙 기반 산출물이라 LLM이 고칠 문제가 아니므로 의도적으로 제외**하고
> 사람에게 넘깁니다. Agent가 **'내가 고칠 것'과 '사람이 봐야 할 것'을 구분**합니다.
>
> 그리고 후보를 방침이 다르게 여러 갈래로 만든 뒤 **검증기가 채점해서** 고릅니다.
> 일반적인 Tree-of-Thoughts는 모델이 자기 가지를 자기가 평가하는데,
> 여기서는 **평가자가 규칙 기반 검증기**입니다. 그래서 이름을 Validator-driven
> Self-Correction이라고 붙였습니다."

> 1회차 만에 9건이 해소돼 BLOCKER가 10건에서 1건으로 줄었습니다.

> 탐지기 범주를 넓혀** 100%가 됐습니다. 정답키를 보고 개별 규칙을 맞추면 측정 도구가 아니라
> 끼워 맞춤이 되므로, 만점이 과적합인지 **다른 세트에 교차 검증**했더니 이 프로젝트가 처음부터
> 써온 원본에서 여태 보고되지 않은 실제 결함을 찾아냈습니다.
>
> 전환 자체는 **80.9점**입니다. 직전 88.2에서 내려왔는데, 도구가 나빠져서가 아니라
> **안 재던 두 축을 재기 시작**했기 때문입니다. 측정 범위를 넓힐수록 지표가 실제에 가까워집니다.
>
> 이 프로젝트에서 가장 중요한 결과는 **'정적 검증만으로 정확성을 보증할 수 있다'는 가설이
> 반증됐다**는 것입니다. 실행 수단이 없다는 전제를 의심해 최소 실행 Harness를 만들었더니,
> 정적 검증을 통과한 코드가 실행에서는 33%만 일치했고, 원인을 고쳐 100%가 됐습니다.
> 다음 단계 1순위는 그 실행 범위를 넓히는 것입니다."
