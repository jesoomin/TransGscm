# 시연 영상 스크립트 (5분)

> 제출 가이드 기준: **5분 이내**(초과분은 평가 제외), MP4, 파일명 `[사번]_[성명]_시연영상.mp4`, 최대 500MB.
> 가이드가 명시한 배점 신호:
> - **"나쁜 예: UI에서 처리 결과만 보여주는 경우 → 기술 구현 확인이 어려워 평가에 불리"**
> - **"핵심 로그가 담긴 터미널/콘솔 화면은 반드시 포함"**
> - **"Agent의 추론 과정이 보여지는 로그로 증명해야 기술 깊이를 평가받을 수 있다"**
> - 5분 중 **1:30~3:30 (40%)** 이 "Planning / Self-Correction 단계 확대"
>
> → **콘솔 추론 로그가 주인공이고 UI는 보조**로 구성한다.

---

## 시연 시나리오 (한 문장)

> **결함이 의도적으로 심어진 레거시 화면 5개를 투입해, Agent가 계획을 세우고 → 규칙과 LLM을 나눠 처리하고 → 검증에서 실패를 잡아 → 스스로 고치고 → 못 고치는 것은 사람에게 넘기는 과정을, 정답키 대조 수치로 증명한다.**

> 오늘 보실 것은 결과 화면이 아니라, **Agent가 단계마다 무엇을 왜 그렇게 판단했는지의 추론 로그**입니다."

**보여줄 것**: `ls` 로 P/F/D java + xsql 파일, 정답키 CSV 한 줄

### 0:30 ~ 1:30 — Agent 실행 & Planning (60초)

**명령** (화면에 그대로 입력)
```
python -m agents.run_pipeline PLA081-110_migration_sample \
    --screens PLA087,PLA089,PLA093,PLA096,PLA100 --no-ai-recommend
```

**강조할 로그 — STAGE 1 (계획)**
```
┌─ STAGE 1/7  PLAN  변환 계획 수립 — 대상 화면 5건 (LLM 미사용, 정적 분석)
│  DECIDE   PLA087.fPLA087QrySelectMainList → LLM 포팅
│           ↳ 계산·분기가 있어 기계적 1:1 치환 불가 — 결정론적 규칙으로 못 만듦
│  DECIDE   PLA087.fCommonCodeQry → 규칙 기반 생성 (LLM 호출 안 함)
│           ↳ 단순 위임 패턴 — store 호출 1건으로 결정론적 생성 가능
│  BLOCK    PLA089: AS-IS 원본이 그대로는 컴파일 안 됨
│  PLAN     LLM 호출 예산 확정: 7건
│           ↳ 21/46건(46%)을 규칙으로 처리 → LLM 호출 회피
└─ 계획 고정 완료 — tracking/conversion-plans/ 에 5건 기록
```

**내레이션 (핵심 3가지)**
> "① **코드를 만들기 전에 계획을 파일로 고정**합니다. 이 단계엔 LLM을 쓰지 않습니다.
> ② 메서드마다 **규칙으로 할지 LLM에 보낼지 판단하고 그 근거를 남깁니다** — 46%를 규칙으로 처리해 LLM 호출 자체를 회피합니다.
> ③ 원본이 컴파일되지 않는 화면은 **변환 전에** 잡아냅니다."

**편집**: 이 구간은 실행이 0.1초라 **정지 프레임 + 화살표**로 3곳을 짚는다.

### 1:30 ~ 3:30 — 핵심 구간: 의존성 주입 → 검증 → **자기 수정** (120초) ★

**(a) 의존성 계약 주입 — 1:30~2:00**
```
┌─ STAGE 3/7  TOOL  LLM 포팅 — 7건 병렬 디스패치 (fan-out)
│  CONTEXT  PLA087.fPLA087QrySelectMainList ← 피호출자 계약 1건 주입: dPLA08710
│           ↳ 콜그래프에서 뽑은 실제 Store 메서드명 — LLM이 이름을 추측하지 않게 고정
│             (AlphaTrans 방식: 조각마다 콜러/콜리 메타데이터를 함께 전달)
```
> "포팅 전에 **콜그래프에서 뽑은 실제 호출 대상을 프롬프트에 주입**합니다. AlphaTrans 논문이 조각별 콜러/콜리 메타데이터를 넘기는 것과 같은 방식입니다. LLM이 메서드 이름을 지어내지 못하게 막는 장치입니다."

**(b) 검증이 결함을 잡는 순간 — 2:00~2:30**
```
┌─ STAGE 4/7  VALIDATE  정적 검증 — 변환기와 분리된 검증기
│  BLOCK    PLA087 [CROSS_LAYER_REF] UNRESOLVED_STORE_CALL @ fPLA087QrySelectMainList:82
│           ↳ 82행: Service가 호출하는 store.dPLA08710(...)가 Store에 정의돼 있지 않습니다.
│  BLOCK    PLA096 [MAPPER_XML] XML_PARSE_ERROR @ Pla096Mapper.xml:80
│  BLOCK    검증 결과 — BLOCKER 2건 · WARNING 0건
```
> "**정답키에 심어둔 결함 2건을 정확히 잡았습니다.** 하나는 존재하지 않는 메서드 호출, 하나는 XML 태그 누락입니다."

**(c) 자기 수정 게이트의 판단 — 2:30~3:00** ← **가장 확대해서 보여줄 곳**
```
┌─ STAGE 5/7  REFLECT  자기 수정 게이트 — 라운드 0/2 사용
│  REFLECT  수리 대상 1건 확정 → 라운드 1 진입
│           ↳ 검증 실패 메시지를 프롬프트에 피드백해 해당 메서드만 재생성한다
│             (MatchFixAgent/ACToR 패턴: 검증·수리를 변환기와 분리)
│  REPAIR   PLA087.fPLA087QrySelectMainList 재생성 요청
│  TOOL     LLM Gateway(PLA087.fPLA087QrySelectMainList)
│           ↳ 수리 재생성 · 프롬프트 2,165자 · 오류 피드백 주입: ...
```
> "여기가 핵심입니다. BLOCKER 2건 중 **1건만 수리 대상으로 골랐습니다.**
> XML 태그 누락은 **규칙 기반 생성물이라 LLM이 고칠 문제가 아니므로 의도적으로 제외**했습니다.
> Agent가 **'내가 고칠 것'과 '사람이 봐야 할 것'을 구분**합니다."

**(d) 수리 성공 확인 — 3:00~3:30**
```
│  PASS     결합(fan-in) 완료 — 1건을 Service에 반영
┌─ STAGE 4/7  VALIDATE  정적 검증 (수리 1라운드 후 재검증)
│  BLOCK    검증 결과 — BLOCKER 1건 · WARNING 0건        ← 2건 → 1건
┌─ STAGE 5/7  REFLECT  자기 수정 게이트 — 라운드 1/2 사용
│  REFLECT  수리 불필요 → 다음 단계로 진행
```
> "**1라운드 만에 해결돼 BLOCKER가 2건에서 1건으로 줄었습니다.**"

**여기서 화면을 둘로 나눠 정답과 대조합니다** — 검증 통과만으로는 "올바른 수정"을 증명하지 못하기 때문입니다.

| 왼쪽: 정답키 CSV (`error_injection_answer_key`) | 오른쪽: 수리된 `Pla087Service.java` |
|---|---|
| `E5 … 존재하지 않는 dPLA08710(...) 호출` | `// AI 수정: …` |
| `정상 메서드명은 dPLA08701` | `store.dPLA08701(...)` |

> "정답키에 **정상 메서드명은 dPLA08701**이라고 적혀 있고, 수리된 코드가 정확히 그 이름을 씁니다. 검증만 통과한 게 아니라 **정답과 일치**합니다."

> "남은 1건은 사람이 봐야 할 원본 결함이고, 라운드에는 **상한이 있습니다** — 무한 재시도는 자율 탐색이 되어버리므로 예산을 넘기면 포기하고 사유를 남깁니다."

**(e) ToT — 후보를 검증기로 채점 (여유 있으면 20초)**
```
│  TOOL     LLM Gateway(...)  ↳ 수리 후보 [최소수정]
│  TOOL     LLM Gateway(...)  ↳ 수리 후보 [계약우선]
│  REFLECT  후보 [최소수정] 채점 — 잔여 BLOCKER 0건
│           ↳ 검증기로 실제 splice 후 측정(LLM 자기평가 아님)
│  DECIDE   수리 후보 2개 → [최소수정] 채택  ↳ 잔여 BLOCKER 0건으로 최소
```
> "후보를 여러 갈래로 만들고 **검증기로 채점해서** 고릅니다. 일반적인 Tree-of-Thoughts는 모델이 자기 가지를 자기가 평가하는데, 여기서는 **평가자가 결정론적 검증기**입니다."
> *(이번 사례는 두 후보가 동점이라 결과가 바뀌진 않았습니다 — 그 사실도 그대로 말합니다.)*

### 4:30 ~ 5:00 — 성과 요약 (30초)

**화면**: 벤치마크 실행 결과 또는 요약 슬라이드

```
[1] 원본 결함 탐지 — 재현율 10/10 (100%), 오탐 0건   [탐지기 보강 전: 5/10]
[2] 중복 함수 탐지 — Type-2 정규화: 209/210 (100%)  [정규화 전: 105/210 (50%)]
[3] 전환 스코어카드 — 80.9점 / 100
[4] 기능 동등성  — F 48/48 · Api 페이로드 9/9 (화면 3/5 실행)
      A 29.4/30 · B 21.1/25 · C 16.7/20 · D 기능동등성 21.0/25
```

**마무리 내레이션**
> "정답키가 있는 30화면 벤치마크로 측정한 결과입니다.
> 원본 결함은 **10건 전부 탐지, 오탐 0건**입니다. 처음엔 5건이었는데, **놓친 5건의 유형을 보고 탐지기를 추가**해 100%가 됐습니다.
> 만점이 과적합인지 확인하려고 **다른 소스 세트에 교차 검증**했더니, 이 프로젝트가 처음부터 써온 원본에서 **여태 보고되지 않은 실제 결함**을 찾아냈습니다.
> 전환 자체는 **80.9점**입니다. 그중 **기능 동등성은 이번에 처음 측정했습니다** — "실행할 수단이 없다"던 전제가 틀렸고, 최소 실행 환경을 만들자 정적 검증을 통과한 코드가 실행에서는 33%만 일치했습니다. 원인을 고쳐 100%가 됐고, 그 과정에서 컴파일조차 안 되던 결함 3건도 함께 드러났습니다.
> 다만 **화면 3/5만 실행 가능**했습니다(나머지는 AS-IS 원본이 깨져 있음). 100%를 전체 검증으로 읽지 않도록 커버리지를 따로 보고합니다.
> 그리고 이 프로젝트에서 가장 중요한 결과는, **'정적 검증만으로 정확성을 보증할 수 있다'는 가설이 반증됐다**는 것입니다. 다음 단계 1순위는 포팅 결과를 실제로 실행할 수단을 확보하는 것입니다."

## 리스크와 대비

| 리스크 | 대비 |
|---|---|
| 녹화 중 LLM Gateway 장애 | `--dry-run`으로 계획~검증 구간은 그대로 재현 가능. 성공 케이스는 **미리 녹화해 둔 클립**을 준비 |
| 수리 루프가 발동하지 않음 | PLA087은 결함이 심어져 있어 **재현 가능**. 실패 시 `--repair-rounds 2` 유지하고 재실행 |
| 5분 초과 | 4:30~5:00 성과 요약을 정지 슬라이드로 대체해 15초 절약 |
| 로그가 화면 폭을 넘어 접힘 | 터미널 폭 100컬럼 이상 + `--no-color`로 폭 절약 가능 |
