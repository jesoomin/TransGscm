# 평가 지표 매트릭스

**대상**: G-SCM 차세대 전환 Agent (1단계 — 서버 전환)
**측정 범위**: 파일럿 **5화면**(PLA087·089·093·096·100) + 정답키 세트 30화면
**산출**: `python -m agents.scorecard <폴더> --screens ...` / `python -m agents.benchmark <샘플> --answer-dir <정답키>`

## 0. 이 매트릭스를 읽는 규칙

| 규칙 | 내용 |
|---|---|
| **세트 병기** | 모든 수치에 어느 소스 세트 기준인지 표기한다. 섞으면 잘못된 주장이 된다 |
| **미측정 처리** | 0점 처리도, 만점 처리도 하지 않는다. **분모에서 제외**하고 미측정임을 명시 |
| **SKIPPED ≠ PASS** | 검사하지 않은 것을 통과로 집계하지 않는다 |
| **재현 가능성** | 모든 수치는 명령 한 줄로 재산출된다. LLM 판단이 섞인 수치는 없다 |

**소스 세트**

| 세트 | 구성 | `.bizunit` | 정답키 | 용도 |

| **C** `C:/project/gscm/workspace`(PLA045~050) | 실제 CRUD 포함 6화면, 1도메인 | **없음** | **없음** | A/B축 재평가(2026-09-09) — §1.5 참고. `멘토리뷰-설명스크립트.md`엔 이미 이름이 있었으나 이 매트릭스엔 실측치가 없었다(정정) |

> **재현 가능성 확인(2026-09-09)**: 이 리포지토리의 현재 로컬 체크아웃에는 세트 B(`PLA081-110_migration_sample`)가 없다(세트 A `sample_data/legacy-u-pla001-050/`만 존재). 즉 위 "재현 가능성" 규칙이 말하는 "명령 한 줄로 재산출"이 **이 환경에서 지금 당장은 안 된다** — 세트 B 폴더를 다시 준비해야 `agents/benchmark.py`/`agents/scorecard.py`를 재실행해 이 문서의 수치를 검증할 수 있다. 이번 세션에서 실제로 고친 두 버그(원본 XML 닫는 따옴표 자동교정, DML verb 판정 화이트리스트 제거 — 세트 A의 CRUD 화면에서 발견)가 세트 B의 C1(원본 결함 재현율)·A2(정적 검증 통과율) 점수에 영향을 주는지는 **세트 B가 다시 확보돼야 검증 가능**하다(이론상 세트 B에 같은 종류의 닫는 따옴표 결함이 정답키 항목으로 심어져 있었다면, 이제는 자동 교정되어 "탐지"가 아니라 "수정"으로 처리되므로 C1 재현율이 달라질 수 있다 — 확인 전까지는 위험 신호로만 남긴다).

## 1. 종합 스코어카드 — **80.9점 / 100**

| 축 | 배점 | 획득 | 달성률 |
|---|---|---|---|
| **A. 전환 성공률** | 30 | **29.40** | 98.0% |
| **B. 사용자 체감** | 25 | **19.82** | 79.3% |
| **C. 탐지 정확성** | 20 | **16.67** | 83.4% |
| **D. 기능 동등성** | 25 | **15.00** | 60.0% |
| **합계** | **100** | **80.89** | **80.9%** |

> **배점을 재조정했다(2026-09-05).** L3(기능 동등성)를 실제로 측정할 수 있게 되면서 D축을 신설하고 A 40→30 · B 30→25 · C 30→20으로 낮췄다. 근거: 이 프로젝트의 핵심 가설 H3이 "정적 검증만으로는 정확성을 보증할 수 없다"였고 AlphaTrans도 문법 96% vs 기능 25%를 보고한 만큼, **"동작이 같은가"는 "컴파일되는가"보다 무게가 커야 한다.** 탐지 정확성은 부수 가치라 가장 많이 낮췄다. 재조정으로 점수는 89.7 → **88.2로 내려갔다**(D축 커버리지가 60%라서).

> **다시 내려갔다: 88.2 → 80.9 (2026-09-05 후반).** 두 가지를 새로 재기 시작해서다.
> ① **Api(HTTP/직렬화) 계층을 처음 측정했다.** 그전까지 D축은 F 계층만 봤고, Api는 "아무도
> 검증하지 않은 층"으로 남아 있었다. 재보니 생성된 Api가 P 계층의 오케스트레이션(권한 게이트·
> 결과 메시지·레코드셋 선별)을 통째로 버리고 있었다 — 정적 검증은 전부 통과하는 코드였다.
> ② **결정론 처리 비중의 분모가 틀렸다.** P 메서드를 "규칙 기반 처리"로 세고 있었는데 사실은
> 아무 것도 변환하지 않고 있었다. 실제 포팅 대상에 넣자 75% → 46%가 됐다.
> **점수가 내려간 건 도구가 나빠져서가 아니라 측정 범위가 넓어져서다.** 안 재던 것을 재기
> 시작하면 점수는 내려간다 — 그 방향이 맞다고 보고 되돌리지 않았다.

**배점 근거**: A는 도구의 존재 이유(산출물이 안 나오면 나머지가 무의미) / B는 공수 절감의 대리 지표 / C는 정답키로 채점 가능한 부수 가치 / **D는 "맞게 옮겼는가"라는 최종 질문**.

## 1.5. 세트 C 재평가(2026-09-09) — 실제 CRUD 구조로 A/B축을 다시 쟀다

**계기**: 사용자가 "평가지표로 다시 평가해달라"고 요청. 위 §1 점수는 전부 세트 B(`PLA081-110`
30화면 5도메인) 기준인데, 이 로컬 체크아웃엔 세트 B 원본이 없어(§0 재현성 노트 참고) 그대로는
재산출이 불가능했다. 대신 이번 세션에서 실제로 작업한 세트 C(`C:/project/gscm/workspace`,
PLA045~050 6화면 - 진짜 CRUD/프로시저 포함, 1유형 복제가 아닌 실제 서로 다른 6개 화면)로
`python -m agents.scorecard "C:/project/gscm/workspace" --screens PLA045,...,PLA050`을 돌려
A/B축만 재측정했다.

**무엇이 실제로 재측정됐고 무엇이 예전 값 그대로인지(중요)**: `agents/scorecard.py`는
`--benchmark`/`--equivalence` 인자가 없으면 **항상** `tracking/benchmark-081-110.json`
(2026-09-05 생성)과 `tracking/equivalence-5screens.json`(2026-09-08 생성)이라는 고정 파일을
읽는다 - `folder` 인자와 무관하다. 즉:
- **A·B축은 세트 C 기준으로 오늘 진짜 재측정됐다.**
- **C·D축은 세트 B/세트 B 5화면 파일럿의 예전 값을 그대로 다시 보여준 것**이다(세트 C에는
  정답키도, 실행 동등성 테스트 결과도 없어 재산출할 수 없다 - §0 "미측정 처리" 규칙대로
  세트 C의 C/D는 공란으로 둔다).

| 축 | 세트 B(§1, 2026-09-05) | 세트 C(2026-09-09) | 비고 |
|---|---|---|---|
| A. 전환 성공률 | 29.40/30 (98.0%) | **30.00/30 (100.0%)** | 세트 C는 산출물 30/30종·정적 검증 36/36건 전부 통과 |
| B. 사용자 체감(측정분만) | 19.82/25\* | **12.57/18**(사람 수정 비율 미측정 - 세트 C엔 저장 스냅샷이 아직 없음) | 아래 참고 |
| C. 탐지 정확성 | 16.67/20 | *(세트 C 정답키 없음 - 미측정)* | §1의 값 그대로 |
| D. 기능 동등성 | 15.00/25 | *(세트 C 실행 동등성 테스트 미실시 - 미측정)* | §1의 값 그대로(세트 B 5화면 기준) |

\* 세트 B의 B축은 25점 만점(사람 수정 수용률 7점 포함, 값 0.20%), 세트 C는 그 축이
미측정이라 분모 자체가 18점으로 줄어든다 - 두 숫자를 직접 빼거나 비율만으로 비교하면 안 된다.

**세트 C에서 드러난 것 — 결정론 처리 비중이 낮아졌다(45.6% → 40.0%), 이건 퇴보가 아니라 더
어려운 표본을 처음으로 재서 나온 정직한 값이다.** 세트 B의 5화면 파일럿(PLA087·089·093·096·
100)은 전부 "조회+상세" 유형 1종이었다. 세트 C(PLA045~050)는 실제 CRUD(insert/update/delete)·
프로시저 호출·D 계층 다중 statement(§03-kickoff-plan.md 2026-09-09)까지 섞여 있어 LLM 포팅이
필요한 비중이 구조적으로 더 높다 - **파일럿 유형 다양성이 낮아서 실제보다 좋아 보였을 가능성을
세트 C가 처음으로 확인해준 셈이다.** `docs/03-kickoff-plan.md`가 "정당하게 막혀 있는 것"으로
분류했던 §5(파일럿 유형 다양성)를 완전히는 아니어도 이번에 부분적으로(1유형→CRUD 포함 구조로)
해소했다.

**리뷰 대상 축소율은 오히려 세트 B보다 높다(87.6% → 88.8%)** - 얼핏 모순으로 보이지만, 이 지표는
"LLM 포팅 *비율*"이 아니라 "생성된 전체 코드 중 사람이 정독해야 할 *줄 수 비율*"이라 규칙 기반
생성(Api/Dto/Mapper 골격 등)이 차지하는 절대 물량이 커지면(세트 C는 화면 수가 적어도 화면당
CRUD statement 수가 많아 골격 코드 자체가 더 많다) 같이 오를 수 있다. 두 지표가 서로 다른 것을
재는 만큼 방향이 반대로 움직일 수 있다는 뜻이며, 이 자체도 세트 하나만으로 일반화하면 안 된다는
근거다(§7 한계 5번 참고).

**PLA081-110(세트 B)이 재확보되면**: `python -m agents.benchmark`/`agents.equivalence_test`를
세트 C에도 돌려 C·D축까지 채우고, 오늘 고친 XML 따옴표 자동교정이 세트 B의 C1 점수에 영향을
주는지(§0 재현성 노트 참고)도 함께 확인해야 한다.

> **C2를 EXACT 티어로만 채점하는 이유.** NORMALIZED 티어(화면 ID 정규화)는 정답키가 «고유»라 표시한 30건 중 **29건**을 후보로 올린다. 그런데 원본을 대조해보면 `fPLA081QrySelectDetail`과 `fPLA087QrySelectDetail`은 화면 ID를 치환하면 **차이가 0**이다 — 텍스트로는 명백한 Type-2 클론이고, 정답키의 «고유»는 *업무 관점의 고유성*을 뜻한다. 어느 쪽이 맞다고 우기지 않고, **정규화를 전혀 하지 않는 EXACT 티어만 채점에 쓴다** — 이러면 티어 정의를 바꿔서 점수를 올릴 수 없다. 참고로 보수적 F1은 6%, 티어인지 F1은 100%로 극단이 갈리며, 그 사이 어디에 선을 긋느냐가 곧 «중복»의 정의를 정하는 일이다.

> **이전 68%는 틀린 값이었다.** 채점기가 정답키의 `QrySelectDetail` 항목을 `d{화면}QrySelectDetail`로 펼쳤는데 D 계층의 실제 이름은 `dPLA08102` 형태다 — **존재하지 않는 이름 30건이 분모에 섞여** 오탐률이 절반으로 희석돼 있었다. 실재하는 메서드만 세도록 고쳤다.

> 100%로 보인다. 실제로 그 상태였다 — 생성된 Api가 `service.fAuthCheck(request)` 한 줄이라 원본의
> 권한 게이트와 결과 메시지가 사라져 있었고, F 계층 100% 뒤에 완전히 가려져 있었다. 층을 나눠
> 세우자마자 Api 0%가 드러났다.
>
> **Api 0%가 무엇을 뜻하는지는 나눠 읽어야 한다.** 페이로드(반환하는 레코드셋)는 고친 뒤
> **9/9 일치**한다. 남은 차이는 전부 결과 메시지 코드(`@msg=I0016` 등)이고, 이걸 TO-BE 응답에
> 어떤 키로 실을지는 **아직 확정되지 않은 공통 규약**이다(docs/09 열린 질문 2번 — 이번에 실사용
> 근거를 찾아 "W/I는 예외가 아니라 성공 응답의 안내 메시지"까지는 확정했지만, 담을 자리를 정하는
> 건 사람 몫이다). 규약 없이 임의의 키를 만들지 않기로 해서 생성기가 그 자리를 비워뒀고, 그래서
> 엄격 일치는 0%다. **점수는 엄격 일치로 매긴다** — 우리가 못 정했다는 이유로 후하게 주지 않는다.
>
> **Api 계층은 1화면(9케이스)만 측정됐다.** 나머지 4화면은 AS-IS P/F 원본에 주입 결함이 있어
> 컴파일되지 않는다. 배점 6점이 표본 1화면에 걸려 있다는 뜻이므로, 이 항목은 다른 항목보다
> 신뢰구간이 넓다.

> **일치율과 커버리지를 따로 잡는 이유.** 실행된 케이스만으로 100%가 나와도 실행하지 못한 화면이 있으면 "전부 검증됐다"가 아니다. 한 수치로 합치면 부분 검증이 전체 검증처럼 보인다 — 리뷰 축소율에서 이미 한 번 겪은 실수라 같은 형태를 반복하지 않는다. 실행하지 못한 2화면은 **AS-IS 원본이 컴파일되지 않아서**(주입 결함)이지 도구의 실패가 아니다.

## 7. 한계 (이 매트릭스가 말하지 않는 것)

1. **기능 동등성은 부분 측정이다.** F 계층 일치율은 48/48(100%)이지만 **화면 3/5만 실행 가능**했고(나머지는 AS-IS 원본이 컴파일 불가), 캔드 데이터는 합성값이라 운영 데이터 분포를 대표하지 않는다. **Api 계층은 1화면(9케이스)만 측정됐다** — 배점 6점이 표본 1건에 걸려 있다. 서블릿/Jackson을 거치는 진짜 HTTP 왕복은 여전히 미검증이다(메서드 호출 수준까지만 비교했다).
2. **사람 수정 0.20%는 리뷰가 찾은 결함 수와 다르다.** 이번 리뷰가 찾은 결함 3건 중 2건(엔드포인트 경로 충돌, 단순 위임의 레코드셋 누수)은 산출물이 아니라 **생성기를 고쳐** 해소해서 수정 라인으로 잡히지 않는다. 게다가 AI 리뷰어 1차 기준이라 사람 개발자 리뷰로는 더 올라간다 — 하한값의 하한값으로 읽어야 한다.
2. **파일럿이 5화면이다.** 통계적 신뢰구간을 말할 규모가 아니다.
3. **배점 가중치(40/30/30)는 설계 판단이다.** 근거는 밝혔으나 유일한 정답은 아니다.
4. **세트 B는 합성 데이터다.** 실제 운영 소스의 결함 분포와 다를 수 있다.
5. **중복 탐지 EXACT 재현율이 50%다.** 정규화 없이 잡을 수 있는 한계이며, 이를 올리려면 정규화가 아닌 다른 방법(구조 기반 비교 등)이 필요하다.
