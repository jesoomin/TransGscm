## 1. 개요

Nexacro14 + NEXCORE로 구축된 G-SCM의 **서버 계층**(화면 1,416개에 대응하는 P/F/D BizUnit + XSQL)을 Spring/MyBatis 구조로 자동 전환하는 파이프라인이다. 폴더를 지정하면 **계획 수립 → 규칙 기반 변환 → LLM 포팅 → 정적 검증 → 자기 수정 → 품질 스캔 → 교차 분석·빌드 검증**까지 자동 진행되고, **사람이 승인해야만** 결과가 반영된다.

핵심 설계는 하나다: **결정론적으로 풀리는 변환에는 LLM을 쓰지 않는다.** 그 결과 화면당 LLM 호출을 최소로 억제하면서도 생성 코드가 실제 컴파일을 통과한다.

## 2. 문제 정의

> **화면-서비스 매핑(nctRid)이 명명 규칙과 일치하지 않아, 서버 로직을 전환하려면 화면마다 사람이 P/F/D/XSQL 4종 파일을 직접 추적해야 한다.** 1,416개 화면 규모에서 이 추적 작업이 반복 발생하고, 개발자별로 응답 형태·예외 처리가 이원화되며, 원본 자체에 섞인 결함(컴파일 불가, SQL 문법 오류)은 전환 도중에야 발견된다.

| 구분 | 내용 |
|---|---|
| 시간 | 화면마다 4종 파일 추적·분석이 선행 작업으로 반복 |
| 비용 | 패턴이 동일한데 화면 수만큼 중복 작업 |
| 품질 | 개발자별 이원화 → 구조 편차 |
| 리스크 | **원본 자체에 결함이 섞여 있음** — 확보한 실제 소스에서 Java 중괄호 누락(컴파일 불가), XML 태그 불일치, SQL 문법 오류를 확인 |

마지막 항목이 설계를 좌우했다. **전환 도구가 "정상 원본"을 전제하면 첫 화면에서 멈춘다.** 원본 결함을 정상 입력의 일부로 취급해야 한다.

## 4. 8주 범위 vs 장기 비전

| 구분 | 8주 PoC (이번) | 장기 비전 |
|---|---|---|
| 계층 | **1단계 서버만** | 1단계 + 2단계 화면(React) |
| 규모 | 유형별 대표 **20~30화면** | 1,416화면 |
| 검증 | 정적 검증 + 빌드 + SQL 계층 차등 테스트 | HTTP 레벨 차등 테스트, 운영 트래픽 섀도잉 |
| 배포 | 로컬 도구 + 사람 승인 | 서비스화, CI 연동 |

**전환 프로그램은 처음부터 2단계다.** 1단계(서버)와 2단계(화면)는 확정 시점과 검증 방법이 달라 같은 시점에 바꾸지 않는다. 두 단계는 **nctRid 계약**으로 이어진다 — 1단계가 `nctRid 1개 = 엔드포인트 1개`를 유지하므로, 2단계 React 화면은 1단계가 만든 API를 그대로 호출한다(Strangler Fig).

**8주 안에 하지 않는 것**: UI 전환, RAG, 서비스화, 운영 배포, DB 스키마 변경, 무인 자동 커밋.

## 5. 핵심 가설과 검증 결과

| # | 가설 | 결과 | 근거 |
|---|---|---|---|
| **H1** | nctRid 매핑 그래프를 **선행 정적 분석**으로 구축하면 화면별 소스 추적 병목이 사라진다 | **검증됨** | 세트 A에서 nctRid **150/150 자동 확정**. 역방향 영향도 추적이 2홉까지 정확히 도달 |
| **H2** | **결정론적 변환이 대부분을 커버**하고 LLM은 좁은 영역만 필요하다 | **검증됨** | 5화면 실행에서 포팅 대상 15건 중 **13건을 규칙으로 회피(46%)**. 규칙 기반 생성물은 실제 `mvn compile` 통과 |
| **H3** | **정적 검증만으로 변환 정확성을 보증할 수 있다** | **반증됨** | 정적 검증은 문법 층만 개선. 기능 동등성은 포팅 코드를 **실행할 수단이 없어** 확인 불가 |

> **H3의 반증이 이 PoC의 가장 큰 성과다.** 반증되지 않았다면 "정적 검증 통과 = 전환 완료"라는 전제로 1,416화면에 확장했을 것이고, 그 오류는 운영에서 드러났을 것이다. 참고로 AlphaTrans(FSE 2025)의 실측은 **문법 96.40% vs 테스트 통과 25.14%** 로, 같은 구조의 간극을 보고한다.

## 6. 성공 지표 (다층)

단일 지표로 성공을 판단하지 않는다. **"구조가 생성됐나 → 컴파일되나 → 동작이 같나 → 사람이 얼마나 고쳤나"** 는 층이 다르고, 각 층이 통과해도 다음 층은 별개다.

| 층 | 지표 | 목표 | **실적** | 판정 |
|---|---|---|---|---|
| L1 구조 | nctRid 자동 확정률 | 80%+ | **150/150 (100%)** — 세트 A | 초과 |
| L1 구조 | 골격 생성 성공률 | 95%+ | 대상 화면 전건 생성 | 달성 |
| L2 문법 | 컴파일 통과율 | 95%+ | **실패 1건 외 전부 통과**(실패는 의도된 원본 버그 보존) | 달성 |
| L2 문법 | 정적 검증 통과율 | 90%+ | 5화면 25파일 중 잔여 BLOCKER 1건 | 달성 |
| L2 문법 | LLM 의존 최소화 | 30% 이하 | **포팅 15건 중 13건을 규칙으로 회피** | 근접 |
| **L3 기능** | 응답 diff 일치율 | 기준 수립 | **SQL 계층 1건 PASS, 상위 계층 미검증** | **미달** |
| **L4 공수** | 사람 수정 라인 비율 | 30% 이하 | **미측정** | **미달** |
| L4 공수 | 화면당 공수 절감률 | **65~70%** | **미측정**(기준선 미실측) | **미달** |

**측정 규칙 (모호성 제거)**
- *화면 유형 분류*: 트랜잭션 개수 + D 메서드 수 + 동적 SQL 태그 유무로 자동 분류
- *샘플 수*: 유형별 4~5개, 총 20~30개
- *"전환 전후 작업"의 정의*: AS-IS 소스 확보 시점부터 TO-BE 코드가 리뷰 승인될 때까지. **소스 추적·리뷰·수정 시간 전부 포함**
- *사람 개입 시간*: **포함한다.** 자동 생성 시간만 재면 절감률이 과대평가된다
- *어느 세트 기준인지 반드시 함께 적는다* (§8 참고)

**미달 3건에 추정치를 채우지 않았다.** L3는 포팅 코드를 실행할 환경이 없어 8주 안의 노력으로 메울 수 있는 항목이 아니고, L4는 사람이 리뷰한 화면이 0건이라 측정 시점이 오지 않았다.

## 7. 핵심 기능과 판정 체계

### 파이프라인

```
① 계획 수립(규칙) → ② 규칙 기반 변환 → ③ LLM 포팅(병렬) → ④ 정적 검증
                                              ↑                    ↓
                                              └── ⑤ 자기 수정 게이트 ──┘  (라운드 상한)
                                                        ↓ 통과/예산소진
                            ⑥ 품질 스캔 → ⑦ 교차분석·빌드검증(임시 사본)
                                                        ↓
                                          ╔═══ 사람 승인 게이트 ═══╗
                                                        ↓
                                              실제 산출물 + DB 반영
```

| 기능 | 방식 | 비고 |
|---|---|---|
| nctRid 매핑 그래프 | 규칙 | 화면↔트랜잭션↔함수↔SQL |
| 변환 계획 파일 고정 | 규칙 | **코드 생성 전**에 무엇을 만들지 확정 |
| 결정론적 변환기 | 규칙 | iBatis→MyBatis, 골격, DTO |
| LLM 포팅 | LLM | 업무 로직만. **콜그래프 피호출자 계약 주입** |
| 검증기 (변환기와 분리) | 규칙 | 정적 검증·품질 스캔·빌드·차등 테스트 |
| 자기 수정 루프 | LLM (상한) | 검증 실패를 프롬프트에 피드백 |
| 영향도 분석 | 규칙 | 미사용·중복·오류 함수, 역방향 blast radius |
| 인수인계 문서 | 규칙 | 미변환 사유 + 수동 처리 가이드 |

### 판정 체계 표준

| 판정 | 의미 | 저장 가능 |
|---|---|---|
| **PASS** | 통과 | 가능 |
| **WARNING** | 동작하나 사람이 확인할 사항 | 가능(승인자 판단) |
| **BLOCKER** | 이 상태로는 정상 동작 보장 불가 | **불가** |
| **FAIL** | 검사 자체가 실패 | **불가** |
| **SKIPPED** | 도구 미지원이라 검사하지 않음 | 가능(미검증 표기) |
| **APPROVED** | 사람이 검토·승인 | — |

**규칙**: ① `SKIPPED`를 `PASS`로 집계하지 않는다 ② BLOCKER가 하나라도 있으면 완료가 아니다 ③ `APPROVED`는 자동 부여되지 않는다 ④ 원본 결함은 `ORIGINAL_BUG`으로 도구의 실패와 구분한다.

### 가드레일

| 가드레일 | 막는 것 |
|---|---|
| 승인 게이트 | 검토 없는 반영 — 승인 전엔 산출물·DB에 아무것도 쓰지 않음 |
| 임시 사본 격리 | 승인 전 검증은 임시 사본에서, 종료 시 **항상** 삭제 |
| 생성 식별자 대조 | LLM이 원본에 없는 필드를 만들면 **자동 차단** |
| 미지원 케이스 명시 | 본 적 없는 패턴에 규칙을 만들지 않고 미지원으로 표시 |
| 원본 결함 보존 | 임의 수정 금지, 별도 표시 |
| 수리 라운드 상한 | 무한 루프 / 자율 탐색화 |
| 테스트 데이터 정리 | 식별 태그 + `finally` 삭제 + 잔여 0건 재확인 |

### 고급 기법 적용 — ToT / MCP

**Tree-of-Thoughts — 수리 후보 다중 생성 + 결정론적 채점**

일반적인 ToT의 약점은 **모델이 자기 가지를 자기가 평가**한다는 것이다. 이 프로젝트에는 이미 **결정론적 검증기**가 있으므로 그 약점을 피할 수 있다:

1. BLOCKER 1건마다 서로 다른 방침(`최소수정` / `계약우선`)으로 **후보 N개를 병렬 생성**
2. 후보마다 실제로 Service에 splice한 **사본**을 만들어 `validate_screen()` 실행
3. 그 메서드에 귀속된 **잔여 BLOCKER 수로 채점**, 동점이면 원본에서 덜 벗어난 쪽 선택
4. 채택·탈락 근거를 로그에 남김

수리는 드물게 발생하므로(5화면에 1건) 추가 호출 비용이 작다. **실측에서는 두 후보 모두 0건이라 결과가 바뀌지 않았다** — 가지치기가 이번엔 수정을 *확인*했을 뿐 개선하진 않았다. 후보가 갈릴 때 효과가 나는 구조이며, 이 사실을 그대로 보고한다.

**MCP — 읽기 전용 조회 창구로 한정**

MCP의 핵심 가치는 모델이 도구를 동적으로 고르는 것인데, 그건 "자율 탐색형 에이전트를 만들지 않는다"는 원칙과 정면으로 충돌한다. 그래서 **표면을 갈랐다**:

| 대상 | MCP 노출 | 이유 |
|---|---|---|
| 변환 실행 | **안 함** | 승인 게이트를 우회할 경로를 열지 않는다 |
| 분석 조회 | **함** | 부작용이 없는 결정론적 그래프 조회. 답에 근거를 붙일 수 있다 |

노출 도구 4종(영향도 역추적 / 미사용 함수 / 중복 함수 / 트랜잭션 매핑)은 전부 조회이며, 모든 응답에 한계 문구를 함께 실어 보낸다. 실 DB 검증 완료(영향 함수 2건, 미사용 후보 51건, 중복 6그룹).

> 즉 MCP를 "에이전트에게 자율성을 준다"가 아니라 **"사람이 쓰는 조회 창구를 표준 프로토콜로 연다"** 로 썼다.

## 8. 검증 결과 (실측)

### 8.1 자체 벤치마크 — 정답키 대조

멘토가 요구한 "내부 벤치마크"를 구축했다. 그동안 탐지 기능은 "돌려보니 N건 나왔다"까지만 말할 수 있었다 — **정답을 몰라 그 N건이 맞는지, 놓친 게 몇 건인지 말할 수 없었다.**

**세트 B (30화면 × 5도메인, 정답키 포함)**

**① 원본 결함 탐지 — 10건 중 10건 (100%), 오탐 0건** *(탐지기 보강 전: 5/10)*

| 분류 | 결과 | 놓친 것 |
|---|---|---|
| XSQL_SYNTAX | **2/2** | — |
| XSQL_LOGIC | **1/1** | — |
| JAVA_REFERENCE | **2/2** | — |
| JAVA_SYNTAX | **4/4** | — |
| JAVA_LOGIC | **1/1** | — |

**놓친 5건의 *유형*을 보고 탐지기 5종을 추가해 100%가 됐다.** 정답키를 보고 개별 규칙을 맞춘 게 아니라 탐지기 **범주**를 넓혔고, 후보 중 오탐 54건이 난 것은 폐기했다. 만점이 과적합인지 확인하려 **다른 세트에 교차 검증**한 결과, 이 프로젝트가 처음부터 써온 원본에서 **여태 보고되지 않은 실제 결함**(파라미터명 누락, 계층 조회 오용)을 찾아냈다 — 과적합이 아니라는 근거다.

**② 중복 함수 탐지 — 정규화 수준에 따른 실제 트레이드오프**

| 방식 | 완전중복 재현율 | 고유 오탐 |
|---|---|---|
| Type-1 (본문 원문 해시) | 105/210 (**50%**) | 0/60 (**0%**) |
| Type-2 (화면 ID 정규화) | 209/210 (**100%**) | 29/60 (**48%**) |

Type-1이 정확히 절반에서 멈추고 놓친 게 전부 `f*`인 게 단서였다 — F 메서드는 본문에 자기 D 클래스명을 담아 복붙된 로직도 해시가 갈린다. **어느 한쪽이 정답이 아니라 재현율↔정밀도 트레이드오프**이므로 두 수치를 항상 함께 보고한다.

### 8.2 전환 스코어카드 — 5화면 기준 **82.9점 / 100**

> **파일럿 범위를 5화면으로 확정했다.** 30화면은 정답키 대조(정적 분석) 전용이고, **변환 파이프라인을 통과시킨 것은 5화면**이다. 두 수치를 섞지 않는다.

기존 성과 수치(매핑 확정률·LLM 호출 감소·탐지율)는 전부 **"도구가 잘 돈다"** 는 얘기였지 **"전환이 됐다"** 가 아니었다. 전환 Agent인데 전환 성공률이 없었고, "개발자가 얼마나 편해졌나"를 말하는 지표도 없었다. 두 구멍을 지표로 메우고 점수화했다.

| 축 | 항목 | 배점 | 실측 | 점수 |
|---|---|---|---|---|
| **A. 전환 성공률** | 산출물 생성률 | 15 | **100.0%** (25/25종) | 15.00 |
| | 정적 검증 통과율 | 25 | **96.7%** (29/30건) | 24.17 |
| **B. 사용자 체감** | 리뷰 대상 축소율 | 18 | **73.6%** | 13.24 |
| | 결정론 처리 비중 | 12 | **46.4%** | 5.57 |
| **C. 탐지 정확성** | 원본 결함 재현율 | 15 | **50.0%** | 7.50 |
| | 중복 탐지 F1 | 15 | **68.0%** | 10.20 |
| | | **합계** | | **82.87 / 100** |

**배점 근거**: A 40점(도구의 존재 이유 — 산출물이 안 나오거나 안 컴파일되면 나머지는 의미 없다) / B 30점(공수 절감의 대리 지표) / C 30점(정답키로 채점 가능한 부수 가치).

**미측정은 0점이 아니라 분모에서 제외한다.** 못 잰 것을 0점으로 깎으면 "낮은 점수"가 되고, 만점으로 치면 거짓이 된다. 기능 동등성(L3)과 사람 수정 라인 비율(L4)은 여전히 미측정이며, **이 점수는 L1~L2 층과 그 대리 지표에 대한 것이지 "전환이 기능적으로 맞다"는 뜻이 아니다.**

**리뷰 대상 축소율을 스스로 깎은 기록**: 처음엔 "이슈가 귀속된 줄"만 세어 1,783줄 중 6줄, **축소율 99.7%** 가 나왔다. 이건 과장이다 — **LLM이 포팅한 메서드는 이슈가 없어도 사람이 전부 읽어야 한다**(우리 인수인계 문서도 그렇게 뽑아준다). LLM 포팅 라인(468줄)을 리뷰 대상에 포함해 다시 재니 **471줄 / 73.6%** 가 됐고 총점도 80.4 → **75.7**로 내려갔다. 유리한 정의를 버리고 방어 가능한 정의를 택했다.

### 8.3 5화면 End-to-End 실행 (실 LLM)

| 항목 | 값 |
|---|---|
| 처리 화면 / 생성 파일 | 5건 / 25종 |
| LLM 포팅 호출 | **15건** (규칙 기반으로 **13건 회피**, 결정론 처리 46%) |
| 자기 수정 라운드 | **1회 — 주입 결함을 실제로 해결** |
| 잔여 BLOCKER | 1건 (XSQL 태그 누락 — 규칙 기반 산출물이라 **의도적으로 수리 제외**) |
| 소요 | 약 16초 |

**자기 수정이 실제로 동작한 사례**: 세트 B에 심어진 결함 중 하나는 존재하지 않는 데이터 메서드를 호출하는 것이다. 파이프라인이 이를 `UNRESOLVED_STORE_CALL` BLOCKER로 잡아 → 오류 메시지와 실재하는 메서드 목록을 프롬프트에 피드백 → **1라운드 만에 해결**했다. 반면 XSQL 태그 누락은 규칙 기반 산출물이라 수리 대상에서 제외하고 사람에게 넘겼다 — 에이전트가 **"내가 고칠 것"과 "사람이 봐야 할 것"을 구분**한다.

> **1번을 1번으로 둔 이유**: 수리 루프를 아무리 고도화해도 개선되는 건 이미 높은 문법 층이다. 낮은 기능 층을 건드리려면 실행 수단이 있어야 한다. **가장 큰 병목에 자원을 쓴다.**
