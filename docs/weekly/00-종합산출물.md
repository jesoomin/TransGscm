## 1. 개요

Nexacro14 + NEXCORE로 구축된 G-SCM의 **서버 계층**(화면 1,416개에 대응하는 P/F/D BizUnit + XSQL)을 Spring/MyBatis 구조로 자동 전환하는 파이프라인이다. 폴더를 지정하면 **계획 수립 → 규칙 기반 변환 → LLM 포팅 → 정적 검증 → 자기 수정 → 품질 스캔 → 교차 분석·빌드 검증**까지 자동 진행되고, **사람이 승인해야만** 결과가 반영된다.

핵심 설계는 하나다: **결정론적으로 풀리는 변환에는 LLM을 쓰지 않는다.** 그 결과 화면당 LLM 호출을 최소로 억제하면서도 생성 코드가 실제 컴파일을 통과한다.

## 2. 문제 정의

> **화면-서비스 매핑(nctRid)이 명명 규칙과 일치하지 않아, 서버 로직을 전환하려면 화면마다 사람이 P/F/D/XSQL 4종 파일을 직접 추적해야 한다.** 1,416개 화면 규모에서 이 추적 작업이 반복 발생하고, 개발자별로 응답 형태·예외 처리가 이원화되며, 원본 자체에 섞인 결함(컴파일 불가, SQL 문법 오류)은 전환 도중에야 발견된다.

| 구분 | 내용 |
|---|---|
| 시간 | 화면마다 4종 파일 추적·분석이 선행 작업으로 반복 |
| 비용 | 패턴이 동일한데 화면 수만큼 중복 작업 |
| 품질 | 개발자별 이원화 → 구조 편차 |
| 리스크 | **원본 자체에 결함이 섞여 있음** — 확보한 실제 소스에서 Java 중괄호 누락(컴파일 불가), XML 태그 불일치, SQL 문법 오류를 확인 |

마지막 항목이 설계를 좌우했다. **전환 도구가 "정상 원본"을 전제하면 첫 화면에서 멈춘다.** 원본 결함을 정상 입력의 일부로 취급해야 한다.

## 4. 8주 범위 vs 장기 비전

| 구분 | 8주 PoC (이번) | 장기 비전 |
|---|---|---|
| 계층 | **1단계 서버만** | 1단계 + 2단계 화면(React) |
| 규모 | 유형별 대표 **20~30화면** | 1,416화면 |
| 검증 | 정적 검증 + 빌드 + SQL 계층 차등 테스트 | HTTP 레벨 차등 테스트, 운영 트래픽 섀도잉 |
| 배포 | 로컬 도구 + 사람 승인 | 서비스화, CI 연동 |

**전환 프로그램은 처음부터 2단계다.** 1단계(서버)와 2단계(화면)는 확정 시점과 검증 방법이 달라 같은 시점에 바꾸지 않는다. 두 단계는 **nctRid 계약**으로 이어진다 — 1단계가 `nctRid 1개 = 엔드포인트 1개`를 유지하므로, 2단계 React 화면은 1단계가 만든 API를 그대로 호출한다(Strangler Fig).

**8주 안에 하지 않는 것**: UI 전환, RAG, 서비스화, 운영 배포, DB 스키마 변경, 무인 자동 커밋.

## 5. 핵심 가설과 검증 결과

| # | 가설 | 결과 | 근거 |
|---|---|---|---|
| **H1** | nctRid 매핑 그래프를 **선행 정적 분석**으로 구축하면 화면별 소스 추적 병목이 사라진다 | **검증됨** | 세트 A에서 nctRid **150/150 자동 확정**. 역방향 영향도 추적이 2홉까지 정확히 도달 |
| **H2** | **결정론적 변환이 대부분을 커버**하고 LLM은 좁은 영역만 필요하다 | **검증됨** | 배관 패턴 규칙을 추가해 포팅 대상 46건 중 **21건을 규칙으로 회피(46%)**. 남은 7건은 분기·계산이 있거나 원본이 깨진 것뿐 |
| **H3** | **정적 검증만으로 변환 정확성을 보증할 수 있다** | **반증됨 — 추론이 아니라 실증으로** | 최소 실행 환경을 만들어 AS-IS/TO-BE를 돌려보니, **정적 검증을 전부 통과한 코드가 27건 중 9건만 일치(33%)** 했다. 원인을 고쳐 100%가 됐다 |

> **H3의 반증이 이 PoC의 가장 큰 성과다.** 처음엔 "실행할 수단이 없다"는 이유로 미측정이었는데, 그 전제 자체가 틀렸다 — 필요한 건 애플리케이션 기동이 아니라 F 메서드를 부를 최소 환경이었고 AS-IS가 쓰는 NEXCORE API는 10개 남짓의 닫힌 집합이었다. 하네스를 만들어 돌리자 **정적 검증을 통과한 코드가 실행에서는 33%만 일치**했고, 원인(배관 규칙이 Store 반환값을 통째로 담아 원본의 `getRecordSet(name)` 추출 단계를 빠뜨림)을 고쳐 100%가 됐다. AlphaTrans(FSE 2025)가 보고한 **문법 96.40% vs 테스트 통과 25.14%** 의 간극을 우리 코드에서 직접 재현하고 닫은 셈이다.

## 6. 성공 지표 (다층)

단일 지표로 성공을 판단하지 않는다. **"구조가 생성됐나 → 컴파일되나 → 동작이 같나 → 사람이 얼마나 고쳤나"** 는 층이 다르고, 각 층이 통과해도 다음 층은 별개다.

| 층 | 지표 | 목표 | **실적** | 판정 |
|---|---|---|---|---|
| L1 구조 | nctRid 자동 확정률 | 80%+ | **150/150 (100%)** — 세트 A | 초과 |
| L1 구조 | 골격 생성 성공률 | 95%+ | 대상 화면 전건 생성 | 달성 |
| L2 문법 | 컴파일 통과율 | 95%+ | **실패 1건 외 전부 통과**(실패는 의도된 원본 버그 보존) | 달성 |
| L2 문법 | 정적 검증 통과율 | 90%+ | 5화면 25파일 중 잔여 BLOCKER 1건 | 달성 |
| L2 문법 | LLM 의존 최소화 | 30% 이하 | **포팅 28건 중 21건을 규칙으로 회피(75%)** | 달성 |
| **L3 기능** | 실행 결과 일치율 | 기준 수립 | **F 계층 48/48 일치(100%)** — 단 화면 3/5만 실행 가능 | **부분 달성** |
| **L3 기능** | SQL 계층 diff | — | S001 PASS · 동적태그 SKIPPED · 원본결함 2건 검출 | 부분 |
| **L4 공수** | 사람 수정 라인 비율 | 30% 이하 | **0.20%** (생성 1,960줄 중 4줄) — AI 리뷰어 1차 기준 | **달성(하한값)** |
| L4 공수 | 화면당 공수 절감률 | **65~70%** | **미측정**(기준선 미실측) | **미달** |

**측정 규칙 (모호성 제거)**
- *화면 유형 분류*: 트랜잭션 개수 + D 메서드 수 + 동적 SQL 태그 유무로 자동 분류
- *샘플 수*: 유형별 4~5개, 총 20~30개
- *"전환 전후 작업"의 정의*: AS-IS 소스 확보 시점부터 TO-BE 코드가 리뷰 승인될 때까지. **소스 추적·리뷰·수정 시간 전부 포함**
- *사람 개입 시간*: **포함한다.** 자동 생성 시간만 재면 절감률이 과대평가된다
- *어느 세트 기준인지 반드시 함께 적는다* (§8 참고)

**미측정으로 남은 것은 화면당 공수 절감률 하나다** — 기준선(수작업 공수)이 실측되지 않아 파일럿에서 확정한다. 여기에 추정치를 채우지 않았다.

> **L3·L4는 이번에 측정 수단을 만들어 해소했다.** L3는 "실행할 수단이 없다"는 전제가 틀렸음을 확인하고 최소 실행 하네스를 만들었고(§8.5), L4는 스냅샷 대비 diff로 측정했다. 다만 **L3는 커버리지 60%(3/5화면), L4는 AI 리뷰어 1차 기준 하한값**이라 둘 다 완결이 아니다.

## 7. 핵심 기능과 판정 체계

### 파이프라인

```
① 계획 수립(규칙) → ② 규칙 기반 변환 → ③ LLM 포팅(병렬) → ④ 정적 검증
                                              ↑                    ↓
                                              └── ⑤ 자기 수정 게이트 ──┘  (라운드 상한)
                                                        ↓ 통과/예산소진
                            ⑥ 품질 스캔 → ⑦ 교차분석·빌드검증(임시 사본)
                                                        ↓
                                          ╔═══ 사람 승인 게이트 ═══╗
                                                        ↓
                                              실제 산출물 + DB 반영
```

| 기능 | 방식 | 비고 |
|---|---|---|
| nctRid 매핑 그래프 | 규칙 | 화면↔트랜잭션↔함수↔SQL |
| 변환 계획 파일 고정 | 규칙 | **코드 생성 전**에 무엇을 만들지 확정 |
| 결정론적 변환기 | 규칙 | iBatis→MyBatis, 골격, DTO |
| LLM 포팅 | LLM | 업무 로직만. **콜그래프 피호출자 계약 주입** |
| 검증기 (변환기와 분리) | 규칙 | 정적 검증·품질 스캔·빌드·차등 테스트 |
| 자기 수정 루프 | LLM (상한) | 검증 실패를 프롬프트에 피드백 |
| 영향도 분석 | 규칙 | 미사용·중복·오류 함수, 역방향 blast radius |
| 인수인계 문서 | 규칙 | 미변환 사유 + 수동 처리 가이드 |

### 판정 체계 표준

| 판정 | 의미 | 저장 가능 |
|---|---|---|
| **PASS** | 통과 | 가능 |
| **WARNING** | 동작하나 사람이 확인할 사항 | 가능(승인자 판단) |
| **BLOCKER** | 이 상태로는 정상 동작 보장 불가 | **불가** |
| **FAIL** | 검사 자체가 실패 | **불가** |
| **SKIPPED** | 도구 미지원이라 검사하지 않음 | 가능(미검증 표기) |
| **APPROVED** | 사람이 검토·승인 | — |

**규칙**: ① `SKIPPED`를 `PASS`로 집계하지 않는다 ② BLOCKER가 하나라도 있으면 완료가 아니다 ③ `APPROVED`는 자동 부여되지 않는다 ④ 원본 결함은 `ORIGINAL_BUG`으로 도구의 실패와 구분한다.

### 가드레일

| 가드레일 | 막는 것 |
|---|---|
| 승인 게이트 | 검토 없는 반영 — 승인 전엔 산출물·DB에 아무것도 쓰지 않음 |
| 임시 사본 격리 | 승인 전 검증은 임시 사본에서, 종료 시 **항상** 삭제 |
| 생성 식별자 대조 | LLM이 원본에 없는 필드를 만들면 **자동 차단** |
| 미지원 케이스 명시 | 본 적 없는 패턴에 규칙을 만들지 않고 미지원으로 표시 |
| 원본 결함 보존 | 임의 수정 금지, 별도 표시 |
| 수리 라운드 상한 | 무한 루프 / 자율 탐색화 |
| 테스트 데이터 정리 | 식별 태그 + `finally` 삭제 + 잔여 0건 재확인 |

### 고급 기법 적용 — ToT / MCP

**Tree-of-Thoughts — 수리 후보 다중 생성 + 결정론적 채점**

일반적인 ToT의 약점은 **모델이 자기 가지를 자기가 평가**한다는 것이다. 이 프로젝트에는 이미 **결정론적 검증기**가 있으므로 그 약점을 피할 수 있다:

1. BLOCKER 1건마다 서로 다른 방침(`최소수정` / `계약우선`)으로 **후보 N개를 병렬 생성**
2. 후보마다 실제로 Service에 splice한 **사본**을 만들어 `validate_screen()` 실행
3. 그 메서드에 귀속된 **잔여 BLOCKER 수로 채점**, 동점이면 원본에서 덜 벗어난 쪽 선택
4. 채택·탈락 근거를 로그에 남김

수리는 드물게 발생하므로(5화면에 1건) 추가 호출 비용이 작다. **실측에서는 두 후보 모두 0건이라 결과가 바뀌지 않았다** — 가지치기가 이번엔 수정을 *확인*했을 뿐 개선하진 않았다. 후보가 갈릴 때 효과가 나는 구조이며, 이 사실을 그대로 보고한다.

**MCP — 읽기 전용 조회 창구로 한정**

MCP의 핵심 가치는 모델이 도구를 동적으로 고르는 것인데, 그건 "자율 탐색형 에이전트를 만들지 않는다"는 원칙과 정면으로 충돌한다. 그래서 **표면을 갈랐다**:

| 대상 | MCP 노출 | 이유 |
|---|---|---|
| 변환 실행 | **안 함** | 승인 게이트를 우회할 경로를 열지 않는다 |
| 분석 조회 | **함** | 부작용이 없는 결정론적 그래프 조회. 답에 근거를 붙일 수 있다 |

노출 도구 4종(영향도 역추적 / 미사용 함수 / 중복 함수 / 트랜잭션 매핑)은 전부 조회이며, 모든 응답에 한계 문구를 함께 실어 보낸다.

**실제 MCP 클라이언트로 연결해 검증했다**(`python -m agents.mcp_smoketest`) — stdio로 서버 프로세스를 띄우고 클라이언트 세션에서 `list_tools`/`call_tool`을 프로토콜 너머로 주고받아 4종 전부 응답을 확인했다. 이 과정에서 설치된 SDK가 mcp 2.x라 1.x 방식(`Server` + 데코레이터)으로는 서버가 뜨지도 않는다는 걸 발견해 `MCPServer` 기반으로 고쳤다 — **"만들었다"와 "붙여봤다"는 다르다.**

> 즉 MCP를 "에이전트에게 자율성을 준다"가 아니라 **"사람이 쓰는 조회 창구를 표준 프로토콜로 연다"** 로 썼다.

## 8. 검증 결과 (실측)

### 8.1 자체 벤치마크 — 정답키 대조

멘토가 요구한 "내부 벤치마크"를 구축했다. 그동안 탐지 기능은 "돌려보니 N건 나왔다"까지만 말할 수 있었다 — **정답을 몰라 그 N건이 맞는지, 놓친 게 몇 건인지 말할 수 없었다.**

**세트 B (30화면 × 5도메인, 정답키 포함)**

**① 원본 결함 탐지 — 10건 중 10건 (100%), 오탐 0건** *(탐지기 보강 전: 5/10)*

| 분류 | 결과 | 놓친 것 |
|---|---|---|
| XSQL_SYNTAX | **2/2** | — |
| XSQL_LOGIC | **1/1** | — |
| JAVA_REFERENCE | **2/2** | — |
| JAVA_SYNTAX | **4/4** | — |
| JAVA_LOGIC | **1/1** | — |

**놓친 5건의 *유형*을 보고 탐지기 5종을 추가해 100%가 됐다.** 정답키를 보고 개별 규칙을 맞춘 게 아니라 탐지기 **범주**를 넓혔고, 후보 중 오탐 54건이 난 것은 폐기했다. 만점이 과적합인지 확인하려 **다른 세트에 교차 검증**한 결과, 이 프로젝트가 처음부터 써온 원본에서 **여태 보고되지 않은 실제 결함**(파라미터명 누락, 계층 조회 오용)을 찾아냈다 — 과적합이 아니라는 근거다.

**② 중복 함수 탐지 — 정규화 수준에 따른 실제 트레이드오프**

| 방식 | 완전중복 재현율 | 고유 오탐 |
|---|---|---|
| Type-1 (본문 원문 해시) | 105/210 (**50%**) | 0/60 (**0%**) |
| Type-2 (화면 ID 정규화) | 209/210 (**100%**) | 29/60 (**48%**) |

Type-1이 정확히 절반에서 멈추고 놓친 게 전부 `f*`인 게 단서였다 — F 메서드는 본문에 자기 D 클래스명을 담아 복붙된 로직도 해시가 갈린다. **어느 한쪽이 정답이 아니라 재현율↔정밀도 트레이드오프**이므로 두 수치를 항상 함께 보고한다.

### 8.2 전환 스코어카드 — 5화면 기준 **80.9점 / 100**

> **파일럿 범위를 5화면으로 확정했다.** 30화면은 정답키 대조(정적 분석) 전용이고, **변환 파이프라인을 통과시킨 것은 5화면**이다. 두 수치를 섞지 않는다.

기존 성과 수치(매핑 확정률·LLM 호출 감소·탐지율)는 전부 **"도구가 잘 돈다"** 는 얘기였지 **"전환이 됐다"** 가 아니었다. 전환 Agent인데 전환 성공률이 없었고, "개발자가 얼마나 편해졌나"를 말하는 지표도 없었다. 두 구멍을 지표로 메우고 점수화했다.

| 축 | 항목 | 배점 | 실측 | 점수 |
|---|---|---|---|---|
| **A. 전환 성공률** | 산출물 생성률 | 12 | **100.0%** (25/25종) | 12.00 |
| | 정적 검증 통과율 | 18 | **96.7%** (29/30건) | 17.40 |
| **B. 사용자 체감** | 리뷰 대상 축소율 | 11 | **87.3%** | 9.60 |
| | 결정론 처리 비중 | 7 | **45.6%** (21/46건) | 3.20 |
| | 사람 수정 수용률 | 7 | **99.8%** (수정 0.20%) | 6.99 |
| **C. 탐지 정확성** | 원본 결함 재현율 | 10 | **100.0%** | 10.00 |
| | 중복 탐지 F1 | 10 | **66.7%** | 6.67 |
| **D. 기능 동등성** | F 계층 실행 일치율 | 9 | **100.0%** (48/48) | 9.00 |
| | Api 계층 실행 일치율 | 6 | **0.0%** (0/9, 페이로드만 보면 9/9) | 0.00 |
| | 동등성 검증 커버리지 | 10 | **60.0%** (화면 3/5) | 6.00 |
| | | **합계** | | **80.86 / 100** |

**점수가 88.2에서 내려온 이유는 도구가 나빠져서가 아니다.** 안 재던 두 가지를 재기 시작했다.
① **Api(HTTP/직렬화) 계층**을 처음 측정했더니, 생성된 Api가 P 계층의 오케스트레이션(권한 게이트·
결과 메시지·레코드셋 선별)을 통째로 버리고 있었다 — 정적 검증은 전부 통과하는 코드였고, F 계층
100% 뒤에 완전히 가려져 있었다. ② **결정론 처리 비중의 분모가 틀렸다** — P 메서드를 "규칙으로
처리했다"고 세고 있었는데 실제로는 아무 것도 변환하지 않고 있었다. 실제 대상에 넣자 75% → 46%.
**측정 범위를 넓히면 점수는 내려간다. 그 방향이 맞다고 보고 되돌리지 않았다.**

**배점 근거**: A 30점(도구의 존재 이유 — 산출물이 안 나오거나 안 컴파일되면 나머지는 의미 없다) / B 25점(공수 절감의 대리 지표) / C 20점(정답키로 채점 가능한 부수 가치) / **D 25점("맞게 옮겼는가"라는 최종 질문)**.

**미측정은 0점이 아니라 분모에서 제외한다.** 못 잰 것을 0점으로 깎으면 "낮은 점수"가 되고, 만점으로 치면 거짓이 된다. 다만 **Api 계층 0%는 미측정이 아니라 측정된 실패**라 그대로 0점을 매겼다 — 남은 차이가 전부 "우리가 아직 정하지 못한 응답 규약" 때문이라 해도, 정하지 못했다는 이유로 후하게 주지 않는다.

**리뷰 대상 축소율을 스스로 깎은 기록**: 처음엔 "이슈가 귀속된 줄"만 세어 1,783줄 중 6줄, **축소율 99.7%** 가 나왔다. 이건 과장이다 — **LLM이 포팅한 메서드는 이슈가 없어도 사람이 전부 읽어야 한다**(우리 인수인계 문서도 그렇게 뽑아준다). LLM 포팅 라인을 리뷰 대상에 포함해 다시 재니 **71.8%** 가 됐고 그 항목 점수도 17.94 → **12.93**으로 내려갔다. 유리한 정의를 버리고 방어 가능한 정의를 택했다.

### 8.3 5화면 End-to-End 실행 (실 LLM)

| 항목 | 값 |
|---|---|
| 처리 화면 / 생성 파일 | 5건 / 25종 |
| LLM 포팅 호출 | **25건** (규칙 기반으로 **21건 회피**, 결정론 처리 46%) — F 계층 7건 + **Api 계층 18건**(P 오케스트레이션 포팅, 이번에 신설) |
| 자기 수정 라운드 | **1회 — 주입 결함을 실제로 해결** |
| 잔여 BLOCKER | 1건 (XSQL 태그 누락 — 규칙 기반 산출물이라 **의도적으로 수리 제외**) |
| 소요 | 약 30초 (Api 계층 포팅 18건이 추가되기 전에는 16초였다) |

**자기 수정이 실제로 동작한 사례**: 세트 B에 심어진 결함 중 하나는 존재하지 않는 데이터 메서드를 호출하는 것이다. 파이프라인이 이를 `UNRESOLVED_STORE_CALL` BLOCKER로 잡아 → 오류 메시지와 실재하는 메서드 목록을 프롬프트에 피드백 → **1라운드 만에 해결**했다. 반면 XSQL 태그 누락은 규칙 기반 산출물이라 수리 대상에서 제외하고 사람에게 넘겼다 — 에이전트가 **"내가 고칠 것"과 "사람이 봐야 할 것"을 구분**한다.

### 8.4a Api(HTTP/직렬화) 계층 — 재보니 P 계층이 통째로 빠져 있었다

L3 하네스는 AS-IS F ↔ TO-BE Service만 비교했다. 그 위층(nctRid 진입점)은 **아무도 검증하지
않았고**, 그래서 오래 "미검증"으로만 적어뒀다. 이번에 AS-IS P 메서드와 TO-BE Api 메서드를 같은
입력으로 실행해 비교했더니 **Api 계층 0/9**가 나왔다.

| 케이스 | AS-IS | TO-BE(수정 전) |
|---|---|---|
| `pPLA09601` (0행) | `@msg=W0024` (권한 없음) | `AUTH_YN=N` |
| `pPLA09601` (1행) | `@msg=I0016; MAIN_LIST#1` | `AUTH_YN=Y` |
| `pPLA09603` (1행) | `@msg=I0016; HIST_LIST#1` | `AUTH_LIST#1;CODE_LIST#1;DETAIL_LIST#1;HIST_LIST#1;MAIN_LIST#1` |

생성된 Api가 `return ResponseEntity.ok(service.fAuthCheck(request));` 한 줄이었다 — 본문에서
**처음 만나는 F 호출 하나만** 위임하고 나머지를 버린다. 권한 게이트도, 결과 메시지도,
"어느 레코드셋을 돌려줄지"도 전부 사라진 상태였고, **정적 검증은 전부 통과했다.** AlphaTrans가
보고한 문법 96.4% vs 기능 25.1%의 간극이 우리 파이프라인에서 그대로 재현된 것이다.

**원인은 표본 1건짜리 가정이었다.** `docs/02-architecture.md`에 "P는 순수 위임"이라고 적혀 있었고,
그 근거는 PLA047 한 화면이었다. 코퍼스 30화면을 전수 확인하니 **30/30이 권한 게이트를 갖고 있고**
`setOkResultMessage` 호출이 195건, `getRecordSet` 선별이 165건이었다. 가정이 코퍼스 전체에서
거짓이었다.

**고친 방법**: `detect_p_orchestration()`이 P 메서드를 "순수 위임"과 "오케스트레이션 보유"로
가른다. 전자는 지금처럼 규칙 기반 한 줄, 후자는 Api를 PORT 스텁으로 만들고 **Api 전용 프롬프트**로
LLM 포팅한다(포팅 레인이 Service.java로 하드코딩돼 있던 것을 대상 파일 기준으로 일반화했다).

**결과: 페이로드 0/9 → 9/9(100%).** 권한 게이트가 살아났고 레코드셋 누수가 사라졌다.
**엄격 일치는 여전히 0/9이고, 이건 의도한 상태다** — 남은 차이가 전부 결과 메시지 코드
(`@msg=I0016`)인데 이걸 TO-BE 응답에 어떤 키로 실을지는 아직 확정되지 않은 공통 규약이다.
규약 없이 키를 지어내는 건 CLAUDE.md가 금지한 바로 그것이라, 생성기가 그 자리에
`// TODO(응답 규약 미확정)` 주석만 남기고 `RESPONSE_MESSAGE_CONVENTION_UNDEFINED` BLOCKER를
올린다. 하네스도 **페이로드 일치와 메시지 일치를 나눠 보고**해서 "우리가 못 옮긴 것"과
"아직 아무도 정하지 않은 것"이 한 칸에 섞이지 않게 했다.

> **부수 성과 — 미확정 규약 하나를 근거로 좁혔다.** `docs/09`의 열린 질문 2번은 "W/I 코드가
> 예외로 던져지는지, 안내 메시지인지 실사용 사례가 없어 확인 불가"였다. 이번에 찾았다:
> `responseData.setOkResultMessage("W0024", ...)` 뒤에 **던지지 않고 그대로 `return`** 한다.
> 메서드 이름부터 `setOk...`다. **W/I는 예외가 아니라 성공 응답의 안내 메시지**이며, 30/30
> 화면에서 이 패턴을 쓴다. 담을 자리를 정하는 건 여전히 사람 몫이지만, 무엇을 담아야 하는지는
> 이제 추측이 아니다.

**이 층을 열자 같이 드러난 결함 3건**(전부 실행 전엔 아무도 못 봤다):
1. 생성된 Api에 `BizRuntimeException`/`HashMap`/`List` import가 없었다 — Service가 겪었던 것과
   같은 누락인데, Api는 여태 컴파일된 적이 없어 드러나지 않았다.
2. TO-BE 공통 `BizRuntimeException`에 `(String, String[], Throwable)` 생성자가 없었다.
   `docs/09`는 "실사용 패턴은 `(코드, 원인)` 하나뿐"이라고 적어뒀는데 — 이것도 PLA047 1건
   기준이었다. 코퍼스에서는 3-인자 형태가 **60개 파일에서 105회** 쓰인다.
3. **화면 5개가 전부 `/01`, `/02`, `/03`을 엔드포인트로 주장하고 있었다.** PLA093과 PLA096은
   패키지까지 같아 Spring이 기동 시점에 죽는다. slug가 메서드명에서 화면 ID를 떼어내고 있었는데,
   화면 ID야말로 그걸 유일하게 만드는 부분이었다. 화면 하나씩만 보는 정적 검증기로는 원리적으로
   못 보는 결함이라 `cross_analysis.find_endpoint_conflicts()`를 신설했다(화면을 나란히 놓는
   유일한 자리다). 수정 후 충돌 4건 → 0건.

### 8.4b 사람 리뷰 — 측정만 있고 절차가 없었다

멘토 §H가 "가장 중요한 대리 지표"로 꼽은 사람 수정 라인 비율은 측정 함수는 있었지만
**«현재 파일»이 어디서 오는지 관리하는 주체가 없었다.** `tracking/reviewed/`는 손으로 채운
폴더였고, 파이프라인을 다시 돌리면 옛 리뷰본과 새 생성물을 비교해 **엉뚱한 값**이 나왔다
(실제로 4.34% → 15.3% → 4.34%로 오갔고, 원인을 찾는 데 시간을 썼다).

`agents/review.py`가 그 절차다 — `status` / `open` / `measure` / `accept` 네 단계뿐이고 LLM을
쓰지 않는다. `open`이 생성 스냅샷을 작업본으로 펼치면서 **파일별 해시를 기준선으로 박아두고**,
이후 생성분이 바뀌면 `measure`가 그 화면을 **미측정**으로 표시한다. 기준선 기록이 아예 없는
리뷰본도 미측정이다. **"안 고쳤다" / "못 쟀다" / "낡은 기준으로 쟀다"는 서로 다른 상태이고,
보고서가 어느 쪽인지 말한다.** `accept`는 낡은 리뷰를 완료로 찍는 것을 거부한다.

실제로 5화면을 한 바퀴 돌렸다: PLA096 Mapper의 닫는 태그를 보충(주입 결함 E8을 원본 그대로
옮긴 결과였다)했고, 리뷰 후 잔여 BLOCKER/WARNING **0건**, 수정 비율 **0.20%**.

> **이 0.20%를 "리뷰가 할 일이 거의 없었다"로 읽으면 안 된다.** 이번 리뷰가 찾은 결함 3건 중
> **2건(엔드포인트 충돌, 단순 위임의 레코드셋 누수)은 산출물이 아니라 생성기를 고쳐** 해소했다 —
> 그러면 수정 라인으로 잡히지 않는다. 지표가 리뷰의 가치를 과소평가하는 구조라는 걸 그대로
> 적어둔다.

### 8.4c 공통함수 — 30벌 복제를 어디까지 한 벌로 줄일 수 있나

화면 30개가 각자 `fAuthCheck`/`fCommonCodeQry`/`fHistoryQry`(+절반은 `fExcelDownQry`)와 대응
D 메서드, `S901`~`S904` SQL을 **똑같이** 갖고 있다. 그대로 옮기면 30벌 사본이 30벌 TO-BE 사본이
된다 — 멘토가 §2에서 경고한 "1,416화면에 1,416가지 변형"의 출발점이다.

**무엇이 공통인지는 추측하지 않고 측정했다.** `agents/common_methods.py`가 중복 탐지의 정규화
단계를 그대로 재사용해, 화면들 사이에서 본문이 **어느 단계에서 하나로 수렴하는지**를 본다.

| 수렴 단계 | 뜻 | 해당 |
|---|---|---|
| EXACT | 글자 그대로 같다 | D 계층 4종, S901/S902/S904 |
| SCREEN | 화면 ID만 치환하면 같다 | F 계층 3종 |
| 수렴 안 함 | 진짜로 다르다 | **공통화 대상 아님** |

이 안전선이 바로 값을 했다. **S903은 겉보기에 같지만 LITERAL 단계에서야 수렴한다** —
`A.DOMAIN_CD = 'QUL'`이 도메인마다 달라 5그룹으로 갈린다. 리터럴까지 지워야 같아지는 건 서로
다른 로직일 수 있어 자동 공통화에서 제외하도록 해뒀고, 정확히 그 규칙이 막았다.

**적용 범위(`config/common-methods.json`, status=CONFIRMED)**: `dAuthCheck`/`dCommonCodeQry`/
`dExcelDownQry` + `S901`/`S902`/`S904`를 `GscmCommonStore` 한 곳으로 모으고, 화면별 Store는
같은 이름의 메서드를 그대로 노출하되 본문만 위임한다(호출부·콜그래프·검증기 전부 그대로다).

**Service 계층은 일부러 미적용으로 뒀다.** `fAuthCheck`는 분기(권한 건수>0 → `AUTH_YN`)를 갖고
있어 공통화가 "공통 업무 로직을 어디에 둘 것인가"라는 설계 결정이 된다 — CLAUDE.md와 멘토 §2가
사람에게 맡기라고 못 박은 자리다. 레지스트리 파일에 그 판단과 **확정 시 절감분(화면마다 나가는
LLM 포팅 호출 30건 → 1건)** 을 같이 적어 사람이 바로 결정할 수 있게 했다.

**첫 적용에서 스스로 낸 오류와 그걸 막은 규칙**: `dHistoryQry`를 공통 목록에 넣었었다. 본문은
30화면 EXACT 동일하다(`dbSelect("S903")` 한 줄이니 당연하다). 그런데 그 S903이 도메인마다 다른
SQL이라, 메서드만 공통화하면 **5개 도메인이 하나의 쿼리를 쓰게 된다.** `check_registry()`가
"Store 메서드는 그 SQL까지 공통이어야 공통화할 수 있다"를 강제하도록 만들어 걸러냈다.

> **공통화 분석이 결함 탐지기 노릇도 했다.** `fCommonCodeQry`는 29화면이 한 덩어리인데 **PLA107
> 하나만 갈라진다** — 그 화면이 `lookupDataUnit` 대신 `lookupFunctionUnit`을 부르기 때문이다
> (컴파일은 통과하고 런타임에 실패하는 정답키 결함 E10). "이거 같은 함수 맞아?"라고 물었더니
> 결함이 나온 것이고, 별도 결함 탐지기가 같은 화면을 독립적으로 지목한다 — 두 관점이 서로를
> 교차 검증한다.

### 8.4d 측정 사각지대 하나 — "100%"의 분모가 3/5였다

위 작업을 검증하다 하네스가 AS-IS와 TO-BE 메서드를 **이름으로** 짝짓는다는 걸 다시 봤다. 그런데
규칙 기반 단순 위임은 생성 시 이름이 바뀐다(`fCommonCodeQry` → `commoncodeqry`). 그래서 그
메서드들이 **비교에서 통째로 빠지고 있었다.** PLA096은 F 메서드가 5개인데 3개만 재고 "F 계층
100%"라고 보고하고 있었다.

빠진 둘이 하필 문제 있는 쪽이었다. 개명을 풀어 짝지어 재보니:

```
fCommonCodeQry  AS-IS  CODE_LIST#1
                TO-BE  AUTH_LIST#1;CODE_LIST#1;DETAIL_LIST#1;HIST_LIST#1;MAIN_LIST#1
```

`detect_simple_delegation`이 `return store.dXXX(request);`를 만드는데, 원본은
`getRecordSet("CODE_LIST")`로 **그 키 하나만** 꺼낸다. 결과 Map을 통째로 되돌려주니 원본이
반환하지 않던 레코드셋이 전부 새어 나갔다. **"규칙 기반이라 안전하다"고 말해 온 경로에서 나온
결함**이라 더 뼈아프다. 탐지기는 이미 레코드셋 이름을 알고 있었고 그냥 버리고 있었다 —
이제 그 키만 담는다.

**F 계층 27/27(메서드 3/5) → 48/48(메서드 5/5).** 같은 100%지만 분모가 진짜다. 하네스는 이제
짝짓지 못한 메서드 수도 함께 보고한다.

### 8.4 L3 기능 동등성 — 최소 실행 환경으로 직접 측정

"포팅된 Service를 실행할 수단이 없다"는 전제로 L3를 오래 미측정으로 뒀는데, **그 전제가 틀렸다.** 필요한 건 애플리케이션 기동이 아니라 F 계층 메서드를 호출할 최소 환경이고, AS-IS가 실제로 쓰는 프레임워크 API는 **10개 남짓의 닫힌 집합**이었다.

**설계**: D 계층(SQL)을 양쪽 **동일한 캔드 데이터**로 고정한다. 그러면 두 실행 결과의 차이는 오직 F 계층 포팅 차이에서만 나온다. 각 메서드를 0행/1행/3행으로 돌려 분기 경로를 훑는다.

| 화면 | 결과 |
|---|---|
| PLA089 / PLA096 / PLA100 | **일치 9/9 (100%)** |
| PLA087 | 실행 불가 — AS-IS가 존재하지 않는 메서드 호출(주입 결함) |
| PLA093 | 실행 불가 — AS-IS 세미콜론 누락(주입 결함) |
| **합계** | **화면 3/5 실행 · F 계층 48/48 일치 (100%)** |

**하네스가 잡아낸 실제 결함 4건** — 여태 아무도 생성된 Service를 컴파일해본 적이 없어 드러나지 않았다:

| # | 결함 | 성격 |
|---|---|---|
| 1 | Service가 Store를 **import 없이** 참조(다른 패키지) | 컴파일 불가 |
| 2 | 위임 메서드가 **생성되지 않는 DTO 클래스** 참조 | 컴파일 불가 |
| 3 | 포팅 본문이 예외 클래스를 **import 없이** 사용 | 컴파일 불가 |
| 4 | **배관 규칙이 Store 반환값을 통째로 담음** — 원본은 레코드셋을 꺼내서 담음 | **의미 불일치** |

4번은 컴파일도 정적 검증도 통과하는 **진짜 기능 차이**였고, 고치자 33% → **100%**가 됐다. 이게 L3가 존재하는 이유이며 H3 반증의 직접 증거다.

**범위 한계**: 캔드 데이터는 합성값이라 운영 데이터 분포를 대표하지 않는다. SQL 정확성은 별개 층(차등 테스트)이 담당하고, **HTTP/직렬화 계층은 아직 아무도 검증하지 않았다.**

## 11. 한계와 다음 단계

### 한계 (숨기지 않는 것)

| # | 한계 | 사유 |
|---|---|---|
| L1 | **기능 동등성 미검증** | 포팅 코드를 **실행할 환경이 없다**. H3 반증의 근본 원인 |
| L2 | **사람 수정 라인 비율 미측정** | 리뷰·수정을 거친 화면 0건 — 측정 시점 미도래 |
| ~~L3~~ | ~~결함 탐지 5/10~~ → **10/10 해소** | 놓친 유형(파라미터명 누락·세미콜론·import 누락·계층 조회 오용)별로 탐지기를 추가해 전 분류 만점 |
| L4 | 중복 탐지 정밀도 | Type-2 정규화 시 오탐 48% — 신뢰 수준 구분 필요 |
| L5 | 조회 외 DB 동작 미지원 | 샘플이 없어 **추측으로 규칙을 만들지 않음** |
| L6 | 공통 응답 규약 미주입 | 규약 자체가 미확정 — 사람 결정 대기 |
| L7 | 화면↔트랜잭션 자동 추출 미완 | 프론트 스크립트 샘플 미확보 |

### 다음 단계 (우선순위)

| 순위 | 과제 | 왜 이 순서인가 |
|---|---|---|
| **1** | **포팅 결과를 실행할 수단 확보** | H3 반증의 근본 원인. 이것 없이는 L3가 영원히 미달이고, 다른 어떤 개선도 문법 층만 건드린다 |
| **2** | 유형별 대표 화면으로 파일럿 → **사람 수정 라인 비율 실측** | 공수 절감률의 가장 직접적인 대리 지표 |
| 3 | 결함 탐지 보강 (놓친 5건 유형) | 벤치마크가 목록을 이미 제공 |
| 4 | 중복 탐지 신뢰 수준 분리 (확실/후보) | 재현율↔정밀도 트레이드오프 대응 |
| 5 | 공통 응답 규약 확정 → 템플릿 주입 | 사람 결정 선행 |

> **1번을 1번으로 둔 이유**: 수리 루프를 아무리 고도화해도 개선되는 건 이미 높은 문법 층이다. 낮은 기능 층을 건드리려면 실행 수단이 있어야 한다. **가장 큰 병목에 자원을 쓴다.**
