이 영상이 증명할 것5가지
1. Agent가 스스로 계획을 세운다

2. 계획이 도구 호출을 지휘한다 — 모델이 고르지 않는다

  - 근거 화면 : STAGE 5  REFLECT / DECIDE

5. 결과가 정답과 맞는지 수치로 증명된다

  2) 유형별 대표 화면으로 파일럿 확대 → 사람 수정 라인 비율 실측
  3) 공통 응답 규약 확정 → 생성 템플릿에 주입
    - 사람 결정이 선행되어야 하는 항목. 확정되면 엄격 일치가 열린다
  4) 중복 탐지 신뢰 수준 분리 (확실 / 후보)
  5) 결과 건수 수정안 적용 — 이미 만든 선택 실행 제안을 파일럿에서 채택 검토

3. 향후 확장 — 전환을 "이관"이 아니라 "정비"로
  1) 축 1. 전환 속도·정확도
    - 이번 파이프라인을 유형별 레시피와 함께 확대 적용
    - 파일럿 산출물이 쌓이면 RAG 코퍼스로 전환해 유사 화면 few-shot 적용
  2) 축 2. 표준화 리뷰 (신규 제안)
    - 10년 이상 운영하며 개발자별로 이원화된 소스를
      전환 직후 LLM이 한 번 더 검토하게 한다
    - 대상은 코드 동작이 아니라 형식
      · 네이밍 규칙 — 클래스·메서드·변수·SQL statement id

향후 확장 — 표준화 리뷰 축을 왜 넣었나

전환 자동화만으로는 남는 문제

Agent로 빠르고 정확하게 옮기면, 10년치 비표준 네이밍과 개발자별 편차까지 정확하게 옮겨집니다. "확장성 제약으로 기능 추가에 한계가 있다"는 원래 문제가 새 프레임워크 위에서 그대로 재현됩니다. 그대로 옮기면 제약도 같이 옮겨집니다.

그래서 전환 파이프라인 뒤에 LLM 표준화 리뷰 단계를 둡니다. 전환 시점이 표준화를 적용할 수 있는 유일한 시점입니다 — 운영 중에는 "돌아가는 코드를 왜 건드리냐"가 항상 이깁니다.

재사용되는 것 — 새로 만들 게 거의 없다

  • AI 추천 패턴 — 제안만 하고 사람이 채택. 규칙 기반 파이프라인은 건드리지 않습니다. 이미 3회 인스턴스화해 실 LLM으로 검증했습니다.
  • 지어내면 차단하는 대조 검증 — 원본에 없는 필드나 호출을 만들면 BLOCKER로 자동 차단합니다.
  • 수렴 분석 — 무엇이 공통인지 추측하지 않고 측정합니다. 겉보기에 같던 함수가 도메인마다 다른 SQL을 쓴다는 걸 이 안전선이 실제로 잡아냈습니다.

전제 — 표준화 제안은 자동 적용하지 않는다

"무엇이 표준인가"는 조직이 정하는 것입니다. 이번 PoC 전체가 지켜온 원칙(사람 승인 게이트)이 여기에도 그대로 적용됩니다. Agent는 표준 위반 지점을 찾아 제시하고, 채택은 사람이 합니다.
