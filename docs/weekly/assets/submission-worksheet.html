로그 강화 — 모델의 판단을 콘솔에 되돌려 출력한다 (2026-09-10 구현)

"LLM이 생각하는 모드"를 지어내지 않고 보여줄 방법이 있었습니다. 포팅 프롬프트가 이미 모델에게 본문 첫 줄에 // AI 변경 요약: 한 줄을 남기라고 요구하고 있습니다. 그 문장은 우리가 쓴 해설이 아니라 모델 자신의 말이므로, 그대로 콘솔에 되돌려 출력하면 판단 과정이 진짜로 보입니다.

  • THINK 이벤트 신설 — 모델이 밝힌 근거를 따옴표로 인용해 출력합니다. 로그의 나머지가 "코드가 내린 결정"인 것과 시각적으로 구분됩니다. 모델이 스스로 남긴 FIXME/TODO도 함께 싣습니다.
  • 호출별 소요 시간 — 응답 수신 줄에 응답 길이와 초를 함께 찍습니다.
  • 계획 → 도구 호출 인과 — 1단계가 "도구 호출 계획"을 확정하고, 3단계가 그 계획을 참조해 호출한다는 것이 로그 두 줄로 드러납니다.
  • 녹화 중 인코딩 크래시 방어 — Windows 기본 코드페이지(cp949)에서 로그의 박스 문자가 UnicodeEncodeError를 내며 파이프라인 전체를 죽이는 걸 확인해 고쳤습니다. 표시용 로그가 실행을 멈추게 두지 않습니다.

핵심 구현 1 — 피호출자 계약 주입
문제
  LLM이 Store 메서드 이름을 추측해 지어내면 컴파일이 깨지고,
  수리 루프가 그걸 고치느라 호출을 낭비한다.

구현
  콜그래프에서 그 F 메서드가 실제로 호출하는 D 메서드 목록을 뽑아
  프롬프트에 명시적 JSON 계약 객체로 넣는다.

  {"name": "dPLA04606",
   "return_type": "Map<String, Object>",
   "cardinality_mismatch": true}

  name                  콜그래프에서 뽑은 실제 이름. 추측 금지
  return_type           DML은 int, 조회는 Map. 타입을 추측하다 나는
                        컴파일 에러와 수리 낭비를 사전에 막는다
  cardinality_mismatch  원본은 다건인데 Store는 단건 계약이다.
                        임의로 봉합하지 말고 FIXME만 남기라고 지시한다

단일 진실 공급원
  카디널리티 판정은 골격 생성기에서 한 번만 하고,
  워크플로는 그 결론을 읽기만 한다.
  처음엔 워크플로가 독립적으로 다시 판정했는데,
  DML 피호출자에까지 "Store가 Map을 반환한다"는 틀린 문구를 달 뻔했다.
  두 곳이 각자 판정하면 반드시 어긋난다.

실 LLM 검증
  LLM이 계약의 불일치를 인지해
  "FIXME(카디널리티 불일치, 사람 확인 필요)" 주석을 정확히 남겼고,
  같은 계약의 DML 피호출자 6건에는 이 주석을 달지 않았다.
핵심 구현 2 — 자기 수정 루프와 ToT 채점
루프 구조
  정적 검증 → 수리 게이트 → 재포팅 → 결합 → 정적 검증 (라운드 상한)

수리 대상 선별
  LLM이 포팅한 메서드에 귀속된 BLOCKER만 대상이다.
  규칙 기반 생성물은 제외한다 — LLM이 고칠 문제가 아니다.
  포팅 실패로 스텁이 남은 경우도 제외한다 —
  "포팅된 코드의 오류를 고쳐라"는 프롬프트에 스텁을 넣으면
  고칠 대상이 없어 무의미한 호출이 된다.

Tree-of-Thoughts 방식의 후보 채점
  일반적인 ToT의 약점은 모델이 자기 가지를 자기가 평가한다는 것이다.
  이 프로젝트에는 결정론적 검증기가 이미 있으므로 그 약점을 피할 수 있다.

  1. BLOCKER 1건마다 방침을 달리해 후보 N개를 병렬 생성 (최소수정 / 계약우선)
  2. 후보마다 실제로 splice한 사본을 만들어 검증기를 돌린다
  3. 잔여 BLOCKER 수로 채점, 동점이면 원본에서 덜 벗어난 쪽
  4. 채택·탈락 근거를 로그에 남긴다

  실측에서는 두 후보 모두 0건이라 결과가 바뀌지 않았다.
  가지치기가 이번엔 수정을 확인했을 뿐 개선하진 않았다.
  후보가 갈릴 때 효과가 나는 구조이며, 이 사실을 그대로 보고한다.

상한을 두는 이유
  무한 재시도는 자율 탐색형 에이전트가 되어버린다.
  예산을 넘기면 포기하고 사유를 남긴다.

구현

원칙 — 없는 추론을 지어내지 않는다
  로그 문구를 만들어내는 게 아니라 이미 코드가 내린 결정을 그대로 받아 적는다.
  호출부가 전부 실제 분기 지점에 있고, 인자는 그 시점의 실제 값이다.

모델의 판단을 콘솔에 되돌려 출력한다 — THINK 이벤트
  포팅 프롬프트가 모델에게 본문 첫 줄에 "// AI 변경 요약: ..." 한 줄을 요구한다.
  그 문장은 우리가 쓴 해설이 아니라 모델 자신의 말이므로,
  따옴표로 인용해 콘솔에 되돌려 출력한다.
  모델이 스스로 남긴 FIXME / TODO도 함께 싣는다 —
  "사람이 봐야 할 것"을 모델이 직접 표시한 것이기 때문이다.
  없으면 대신 문장을 지어내지 않고 아무것도 출력하지 않는다.

계획과 도구 호출의 인과를 로그에 드러낸다
  1단계가 "도구 호출 계획"을 확정하고,
  3단계가 "1단계 계획이 지목한 N건에만 호출한다"를 명시한다.
  모델이 무엇을 부를지 스스로 고르지 않는다는 것이 로그로 보인다.

녹화 환경 방어
  Windows 기본 코드페이지에서 로그의 박스 문자가 인코딩 오류를 내며
  파이프라인 전체를 죽이는 것을 확인해 고쳤다.
  표시용 로그가 실행을 멈추게 두지 않는다.

CLI 진입점

  UI와 동일한 함수를 부르고 저장은 하지 않는다(승인 게이트 앞에서 멈춤).
  --dry-run은 LLM을 호출하지 않아 키·네트워크 없이
  계획 → 규칙 기반 변환 → 검증 → 게이트 경로를 그대로 재현한다.

로그를 붙이자마자 드러난 실제 결함 2건

  2. 병렬 브랜치가 서로의 로그를 깨뜨렸다.
     이벤트 하나를 원자적으로 내보내도록 고쳤다.
핵심 구현 4 — MCP 읽기 전용 조회 서버
MCP는 Model Context Protocol이다.

도입 판단
  MCP의 핵심 가치는 모델이 도구를 동적으로 고르는 것인데,
  그건 "자율 탐색형 에이전트를 만들지 않는다"는 원칙과 정면으로 충돌한다.
  그래서 도입하되 표면을 갈랐다.

  변환 실행   노출하지 않음   승인 게이트를 우회할 경로를 열지 않는다
  분석 조회   노출함         부작용 없는 결정론적 그래프 조회.
                            답에 근거를 붙일 수 있다

노출 도구 4종 (전부 조회)
  영향도 역추적 / 미사용 함수 / 중복 함수 / 트랜잭션 매핑
  모든 응답에 한계 문구를 함께 실어 보낸다.

실제 MCP 클라이언트로 연결해 검증했다.
  stdio로 서버 프로세스를 띄우고 클라이언트 세션에서
  list_tools / call_tool을 프로토콜 너머로 주고받아 4종 전부 응답을 확인했다.
  이 과정에서 설치된 SDK 버전 차이로 서버가 뜨지도 않는다는 걸 발견해 고쳤다.
  "만들었다"와 "붙여봤다"는 다르다.

즉 MCP를 "에이전트에게 자율성을 준다"가 아니라
"사람이 쓰는 조회 창구를 표준 프로토콜로 연다"로 썼다.
AI 추천 — 파이프라인 바깥의 opt-in 제안
규칙 기반 변환기가 다루지 못하거나 다루지 않기로 판단한 경우,
LLM이 대안을 제안만 하고 사람이 검토해야만 채택되는 별도 산출물을 만든다.
기존 파이프라인은 전혀 건드리지 않는다.

응답 DTO 재설계
  응답 DTO를 프론트가 쓰기 편한 모양(타입·페이지네이션 래핑)으로 제안
  지어내면 차단: 원본에 없는 필드 → BLOCKER

D 계층 재구성
  D 메서드 하나가 statement를 2개 이상 순서대로/조건부로 실행하는 경우,
  그 오케스트레이션을 Service로 옮기는 안을 제안
  지어내면 차단: 존재하지 않는 Store 메서드 호출 → BLOCKER

카디널리티 수정
  Store를 단건에서 다건으로 바꾸고 그 위 Service까지 연쇄 반영하는 안을 제안
  지어내면 차단: 원본과 무관한 Store 호출 → BLOCKER

분리 원칙은 여기서도 유지된다.
이미 결정론적으로 아는 사실(어떤 statement가 있는지, 이 메서드가 다건인지)은
