로그 강화 — 모델의 판단을 콘솔에 되돌려 출력한다 (2026-09-10 구현)

"LLM이 생각하는 모드"를 지어내지 않고 보여줄 방법이 있었습니다. 포팅 프롬프트가 이미 모델에게 본문 첫 줄에 // AI 변경 요약: 한 줄을 남기라고 요구하고 있습니다. 그 문장은 우리가 쓴 해설이 아니라 모델 자신의 말이므로, 그대로 콘솔에 되돌려 출력하면 판단 과정이 진짜로 보입니다.

  • THINK 이벤트 신설 — 모델이 밝힌 근거를 따옴표로 인용해 출력합니다. 로그의 나머지가 "코드가 내린 결정"인 것과 시각적으로 구분됩니다. 모델이 스스로 남긴 FIXME/TODO도 함께 싣습니다.
  • 호출별 소요 시간 — 응답 수신 줄에 응답 길이와 초를 함께 찍습니다.
  • 계획 → 도구 호출 인과 — 1단계가 "도구 호출 계획"을 확정하고, 3단계가 그 계획을 참조해 호출한다는 것이 로그 두 줄로 드러납니다.
  • 녹화 중 인코딩 크래시 방어 — Windows 기본 코드페이지(cp949)에서 로그의 박스 문자가 UnicodeEncodeError를 내며 파이프라인 전체를 죽이는 걸 확인해 고쳤습니다. 표시용 로그가 실행을 멈추게 두지 않습니다.

4.1 RAG (검색 증강 생성) 전략 — 이번 PoC 미적용

  미적용 사유
    이 Agent가 필요로 하는 컨텍스트는 "어딘가에서 찾아와야 하는 지식"이 아니라
    "지금 이 소스에서 확정할 수 있는 사실"이다. 어떤 Store 메서드를 호출해야
    하는지는 유사 문서를 검색할 문제가 아니라 호출 관계도에서 확정되는 값이다.
    검색으로 근사하면 오히려 환각의 입구가 된다.
    RAG는 파일럿 산출물이 분석 대상 소스가 된 이후로 명시적으로 연기했다.

  대신 쓰는 컨텍스트 전략 — 검색이 아니라 정적 분석으로 확정해 주입한다
    ① 호출 대상 계약 주입
       호출 관계도에서 뽑은 실제 메서드명·반환 타입·결과 건수 불일치(단건/다건) 여부를
       JSON 계약으로 프롬프트에 명시한다. 모델이 이름을 추측할 여지를 없앤다.
       (AlphaTrans의 "구성 파일마다 콜러/콜리 메타데이터를 함께 전달" 원칙)
    ② 계획 파일 고정
       무엇을 어떤 도구로 처리할지 코드 생성 전에 파일로 확정한다.
    ③ 생성 식별자 대조
       모델이 계약에 없는 호출이나 원본에 없는 필드를 만들면 BLOCKER로 자동 차단한다.
       프롬프트 지시만 믿지 않는다.

구현 기능

동작 원리
  ① 정적 분석으로 호출 관계도(P→F→D)와 XSQL statement 매핑을 구축한다.
  ② 메서드마다 본문을 검사해 세 갈래로 나눈다.
       단순 위임(store 호출 1건)      → 규칙 기반 생성, LLM 호출 안 함
       계산·분기 존재                 → LLM 포팅 대상 (Service 계층)
       P가 권한 게이트·레코드셋 선별   → LLM 포팅 대상 (화면 요청 계층(Api))
  ③ 판정과 근거를 conversion-plan.json 으로 확정한다.
     이후 단계는 이 계획만 따르며, 실행 시점에 다시 판단하지 않는다.
  ④ LLM 대상은 메서드 단위로 병렬 배분(병렬 분배)하고, 결과를 대상 파일의
     표시 지점 위치에 결합(결과 합치기)한다. 결합은 여러 번 실행해도 결과가 같아 재수리해도 중복되지 않는다.
  ⑤ 검증 실패가 남으면 조건부로 자기 수정 루프에 진입한다(회차 상한 2).

  실측 — 포팅 대상 46건 중 21건(46%)이 규칙 경로로 빠져 LLM 호출 자체를 회피했다.

주요 기술

  계획 파일 영속화(conversion-plan.json)

미적용 사유
  이 Agent에 필요한 컨텍스트는 검색으로 찾아올 지식이 아니라, 지금 소스에서
  확정되는 사실이다. "어떤 Store 메서드를 부를까"는 유사 문서 검색 문제가
  아니라 호출 관계도에서 결정되는 값이며, 검색으로 근사하면 환각의 입구가 된다.
  RAG는 파일럿 산출물이 분석 대상 소스가 된 이후로 명시적으로 연기했다.

구현 기능 (같은 자리에 실제로 구현한 것)

동작 원리
  ① 프론트 진입점(트랜잭션 ID)에서 P BizUnit을 찾고, P→F→D 호출을 추적한 뒤
     D가 참조하는 XSQL statement까지 이어 하나의 그래프로 만든다.
  ② 한정자 없는 내부 호출까지 수집해 그래프 누락을 줄인다.
  ③ 파일·메서드·호출 엣지·이슈를 관계형 DB에 기록한다.
     이슈는 파일이 아니라 메서드 단위로 귀속시켜 "어디를 봐야 하는지"를 남긴다.
  ④ 이 그래프가 두 곳에 그대로 쓰인다.
       - 포팅 프롬프트의 호출 대상 계약 (1.2)
       - 영향도 역추적·미사용/중복 함수 조회 (MCP 읽기 전용)
  ⑤ 값의 출처(확정 / 파생)를 함께 저장해, 조회 결과를 확정으로 오독하지 않게 한다.

4. 운영 및 보안 고려 사항인증 / 권한 / 대응
· 소스 유출 방지: 코드가 외부로 나가지 않도록 사내 LLM Gateway만 사용.
                  외부 관측 SaaS를 붙이지 않고 로그를 로컬 콘솔로 한정했다.

· 자격증명 관리: DB 접속정보·게이트웨이 키는 환경 파일에만 두고 형상관리에서 제외.
                  문서·코드·커밋 메시지에 값을 적지 않는다.
                  생성물 전건에 하드코딩 자격증명 검사기를 돌려 유출 0건 확인.

· 권한 통제:      추적 DB는 도구 자체의 메타데이터만 담는다(업무 데이터 아님).
                  차등 테스트가 만드는 테스트 데이터는 식별 태그를 붙이고
                  finally에서 항상 삭제한 뒤 잔여 0건을 재확인한다.

· 반영 통제:      승인 게이트 — 사람이 누르기 전에는 산출물·DB에 아무것도 쓰지 않는다.
                  BLOCKER가 하나라도 있으면 저장 자체가 불가하다.
                  git 커밋과 배포는 여전히 사람이 직접 한다. 무인 자동 커밋 없음.

· 격리:           승인 전 검증은 임시 사본에서 수행하고 종료 시 항상 삭제.
                  실행 전후 실제 산출물 폴더가 동일함을 스냅샷으로 확인했다.

· 장애 대응:      LLM Gateway 장애 — 호출 실패는 코드 결함과 구분해 기록하고
                  파이프라인을 중단시키지 않는다. 키·네트워크 없이 계획~검증 구간을
                  그대로 재현하는 실행 모드를 별도로 둔다.
                  동작 일치 검증 실패 — 내부 예외가 전체를 막지 않도록 감싸고
                  경고로 기록한 뒤 다음 단계로 진행한다.
                  표시용 로그 실패 — 실행을 멈추지 않는다.

· 원본 보호:      AS-IS 원본은 읽기 전용으로만 다룬다. 결함이 있어도 고치지 않고
                  보존·표시한다.

향후 확장 — 표준화 리뷰 축을 왜 넣었나

전환 자동화만으로는 남는 문제

Agent로 빠르고 정확하게 옮기면, 10년치 비표준 네이밍과 개발자별 편차까지 정확하게 옮겨집니다. "확장성 제약으로 기능 추가에 한계가 있다"는 원래 문제가 새 프레임워크 위에서 그대로 재현됩니다. 그대로 옮기면 제약도 같이 옮겨집니다.

그래서 전환 파이프라인 뒤에 LLM 표준화 리뷰 단계를 둡니다. 전환 시점이 표준화를 적용할 수 있는 유일한 시점입니다 — 운영 중에는 "돌아가는 코드를 왜 건드리냐"가 항상 이깁니다.

재사용되는 것 — 새로 만들 게 거의 없다

  • AI 추천 패턴 — 제안만 하고 사람이 채택. 규칙 기반 파이프라인은 건드리지 않습니다. 이미 3회 인스턴스화해 실 LLM으로 검증했습니다.
  • 지어내면 차단하는 대조 검증 — 원본에 없는 필드나 호출을 만들면 BLOCKER로 자동 차단합니다.
  • 수렴 분석 — 무엇이 공통인지 추측하지 않고 측정합니다. 겉보기에 같던 함수가 도메인마다 다른 SQL을 쓴다는 걸 이 안전선이 실제로 잡아냈습니다.

전제 — 표준화 제안은 자동 적용하지 않는다

"무엇이 표준인가"는 조직이 정하는 것입니다. 이번 PoC 전체가 지켜온 원칙(사람 승인 게이트)이 여기에도 그대로 적용됩니다. Agent는 표준 위반 지점을 찾아 제시하고, 채택은 사람이 합니다.
