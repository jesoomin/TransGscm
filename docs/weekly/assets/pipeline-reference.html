G-SCM 서버 전환 파이프라인

화면 하나를 계획 → 변환 → 검증 → 저장까지 옮기는 8단계 자동 파이프라인. 굵은 항목은 오늘(2026-09-10) 새로 반영된 부분.

1단계 범위 · Java/XSQL → Spring/MyBatis

파이프라인 8단계

0
변환 계획 수립LLM 미사용
화면별 fragment·nctRid·예상 산출물을 conversion-plan.json으로 먼저 고정. 코드부터 짜지 않는다.
1
규칙 기반 변환LLM 미사용
iBatis→MyBatis 문법 치환, Controller/Service/Store/Dto 골격 생성.
2
LLM 포팅오늘 · 계약 객체 강화
F/P의 계산·분기·오케스트레이션을 이식. 콜리 이름·카디널리티 일치 여부·반환 타입(int/Map)을 JSON 계약으로 프롬프트에 명시 — 추측 대신 이미 확정된 사실을 준다.
3
정적 검증
컴파일 가능성·계층 간 참조 무결성 확인. BLOCKER면 수리 루프(최대 2라운드) 후 재검증.
4
기능 동등성 검증 (L3)오늘 신설
AS-IS/TO-BE를 실제로 javac/java로 컴파일·실행해 결과를 비교. 이전엔 사람이 따로 돌리는 opt-in 스크립트였고, 이제 매 실행마다 자동으로 돈다.
5
품질·취약점 스캔
SQL 인젝션 위험, 원본 결함(ORIGINAL_BUG) 등을 규칙 기반으로 탐지 — 검증기와 분리된 별도 스캐너.
6
AI 추천 (opt-in)오늘 2건 추가
규칙 기반 파이프라인 밖에서 LLM이 대안만 제안, 사람이 검토 후 채택. 오늘 추가: D계층 재구성(다중 statement 분리) · 카디널리티 수정(selectOne→selectList) 제안.
7
교차 분석
임시 사본에서 화면 간 중복·미사용 함수 탐지 — 실제 pilot/은 아직 안 건드림.
8
Maven 빌드 검증
같은 임시 사본을 mvn compile로 마지막 확인.
🔒 사람 승인 → 저장
여기까지는 전부 미리보기. "승인하고 저장"을 눌러야만 pilot/과 DB에 실제로 반영된다.

오늘의 핵심 발견

발견

Store 카디널리티 결함

모든 select문을 단건(selectOne)으로 생성하는데, 원본이 다건(recordset)으로 다루는 조회가 섞여 있었다. 실제 행이 2개 이상이면 런타임에 TooManyResultsException — PLA045~050 전 화면에서 재현(화면당 4~10건).

대응

계약을 JSON으로 명시

포팅 프롬프트에 콜리 이름만 주던 걸 {name, cardinality_mismatch, return_type} 구조로 확장. 불일치가 있으면 LLM이 임의로 봉합하지 않고 FIXME로 표시하도록 지시.

승격

동등성 검증 자동화

equivalence_test.py를 사람이 따로 돌리던 연구 스크립트에서 파이프라인 필수 단계로 승격. PLA048에서 15/24케이스(62.5%) 일치라는, 이전엔 아무도 자동으로 못 봤던 수치를 처음 확보.
