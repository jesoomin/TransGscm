## 1. 테스트 전략

이 도구의 출력은 **코드**다. "그럴듯한 답"과 "맞는 답"의 차이가 곧 장애로 이어지므로, 검증을 4개 층으로 나누고 **각 층의 통과를 다음 층의 통과로 오인하지 않는다.**

| 층 | 무엇을 검증하나 | 수단 | 현재 상태 |
|---|---|---|---|
| L1 구조 | 만들어야 할 산출물이 다 만들어졌나 | 계획 파일 vs 실제 생성물 대조 | **통과** |
| L2 문법 | 컴파일되나, 참조가 실제로 존재하나 | 정적 검증 + `mvn compile` | **통과** (예외 1건은 의도된 원본 버그) |
| L3 기능 | **같은 입력에 같은 값을 내나** | 차등 테스트(SQL) + **실행 하네스(F 로직)** | **부분** — F 계층 48/48 일치이나 화면 3/5만 실행 가능, Api 계층은 1화면만 측정 |
| L4 공수 | 사람이 얼마나 고쳤나 | 사람 수정 라인 비율 | **0.20%** (생성 2,007줄 중 4줄, AI 리뷰어 1차 기준 하한값) |

> **추가(2026-09-05)**: 정답키가 있는 30화면 세트를 확보해 **L1·L2 층의 탐지 성능을 수치로 측정**할 수 있게 됐다 — 원본 결함 탐지 **10/10**(오탐 0건, 보강 전 5/10), 중복 탐지 재현율 50%→100%(오탐 0%→48%). 상세는 종합 산출물 §8.

### L2 정적 검증 항목
Java 중괄호 균형(문자열·주석 인식) / 포팅 후 스텁 잔존 여부 / **계층 간 실제 호출 대상 존재 확인**(Api→Service, Service→Store, Store→Mapper statement) / Mapper XML well-formed·statement id 중복·바인드 표현식 짝.

### L3 차등 테스트 실측

실제 원본 SQL 6개 문장으로 실행한 결과:

| 문장 | 판정 | 내용 |
|---|---|---|
| S001 | **PASS** | 테스트 데이터를 자동 생성해(사람 개입 0) AS-IS/TO-BE 양쪽에서 **정확히 동일한 결과** 확인 — SQL 문법 변환이 의미를 바꾸지 않았다는 첫 실증 |
| S002~S004 | SKIPPED | 동적 조건 태그 미지원. **PASS로 집계하지 않음** |
| S005 | FAIL | 대상 테이블에 해당 컬럼이 없음 → **로컬 스키마가 운영과 다를 수 있다는 신호** |
| S006 | FAIL | **원본 SQL 자체의 문법 오류** (FROM 절에 조인·콤마 누락) → `ORIGINAL_BUG` |

> **S005·S006은 도구의 실패가 아니라 도구가 찾아낸 기존 결함이다.** 전환 도구의 부수 가치가 여기서 드러난다 — 전환하려고 열어보니 원본에 문제가 있었다.

**테스트 데이터 자동 생성**: 조건절의 단순 조건을 정적으로 읽어 그 조건을 만족하는 최소 행을 만들고, 같은 값으로 양쪽을 실행한 뒤 **`finally`에서 항상 삭제**한다. 생성 행에는 매번 새로 만드는 식별 태그를 붙여 실수로 남아도 즉시 식별 가능하게 했다. 테스트 후 잔여 행 0건을 직접 쿼리로 재확인했다.

**자동 생성 미지원 범위**: 다중 테이블 조인, 날짜 바인드, 범위/서브쿼리 조건 → 추측 데이터를 넣지 않고 SKIPPED.

## 2. 발견하고 고친 문제

### 대표 사례 4선 (문제 → 원인 → 해결 → 결과)

아래 절에 전체 목록이 있고, 그중 **기술적으로 가장 중요한 4건**을 먼저 요약한다.

#### 사례 1 — 표본 1건으로 세운 가정이 코퍼스 전체에서 거짓이었다 (화면 요청 계층 0/9)

1. **문제 상황** — 정적 검증을 전부 통과한 Api 코드가 실행에서는 AS-IS와 전혀 다른 값을 냈다. 실행 일치 **0/9**.
2. **원인** — 설계 문서의 *"진입점 계층은 순수 위임이다"* 가 **화면 1건만 보고 세운 가정**이었다. 생성기는 그 가정대로 본문의 첫 호출 하나만 위임하는 한 줄을 만들었고, 권한 게이트·결과 메시지·레코드셋 선별이 통째로 사라졌다.
3. **해결 방법** — 가정을 코퍼스 30화면으로 전수 검증했다. **30/30이 권한 게이트를 갖고 있었고** 결과 메시지 호출 195건, 레코드셋 선별 165건이 있었다. 진입점을 "순수 위임"과 "오케스트레이션 보유"로 분류하고, 후자는 전용 프롬프트로 LLM 포팅하도록 파이프라인을 갈랐다.
4. **결과** — 페이로드 일치 **0/9 → 9/9**. 권한 게이트가 살아났고 레코드셋 누수가 사라졌다. 이 층을 열자 컴파일조차 된 적 없던 결함 3건(임포트 누락, 생성자 시그니처 부재, **화면 5개의 엔드포인트 충돌**)이 함께 드러났다.

> 이 사례가 이 프로젝트의 방법론을 가장 잘 보여준다 — **표본 1건의 가정은 코퍼스로 검증하기 전까지 가설일 뿐이다.**

#### 사례 2 — 정적 검증을 통과한 코드가 실행에서 달랐다

1. **문제 상황** — 문법 검증은 전부 통과인데 실행 결과가 원본과 달라 동작 일치율이 **9/27 (33%)** 에 머물렀다.
2. **원인** — 배관 규칙이 데이터 계층 반환값을 **통째로** 담았다. 원본은 거기서 특정 레코드셋 하나만 꺼내 담는다. 컴파일도, 정적 검증도, 기존 하네스도 잡을 수 없는 **의미 차이**였다.
3. **해결 방법** — 최소 실행 Harness를 만들어 AS-IS/TO-BE에 같은 입력을 넣고 실행 결과를 비교했다. 데이터 계층을 양쪽 동일한 고정 데이터로 통제해 차이를 포팅 차이로 한정하고, 메서드마다 0행·1행·3행을 전수로 돌렸다.
4. **결과** — 원인을 코드에서 지목해 해당 키만 담도록 고쳤고 **33% → 100% (48/48)**. 선행 연구(AlphaTrans, FSE 2025)도 **문법 96.40% vs 동작 일치 25.14%** 로 같은 간극을 보고한다 — 우리 파이프라인에서 그 간극이 그대로 재현됐고, **실행 없이는 닫히지 않는다**는 것이 확인됐다.

#### 사례 3 — 없는 메서드를 지어내는 환각

1. **문제 상황** — LLM이 원본에 존재하지 않는 데이터 계층 메서드명을 만들어 컴파일 오류를 유발했다.
2. **원인** — 호출 대상 정보를 **자연어 문장으로만** 전달해 모델이 이름을 추측할 여지를 남겼다.
3. **해결 방법** — 콜그래프에서 실제 메서드명·반환 타입·결과 건수를 뽑아 **JSON 계약**으로 프롬프트에 주입하고, 생성된 식별자를 원본 목록과 **기계적으로 대조**하는 검증기를 별도로 뒀다(프롬프트 지시를 믿지 않고 결과를 검사한다).
4. **결과** — 지어낸 호출이 사전 차단됐고, 정답키가 있는 사례(TC-D05)에서 정상 메서드명으로 수렴했다. 같은 원리를 AI 추천 기능 전반에 적용해 **지어낸 식별자는 BLOCKER로 채택 자체를 막는다.**

#### 사례 4 — 성공할 수 없는 대상을 반복 호출하던 낭비

1. **문제 상황** — 규칙으로 이미 처리된 함수에까지 LLM 호출이 반복돼 비용과 시간이 늘었다. 화면당 유효 1건에 **호출 5건**.
2. **원인** — 규칙 기반으로 생성된 함수에는 포팅 마커가 없어 결과가 조용히 버려졌고, 버려지니 "미완료"로 남아 **재시도 회차마다 다시 호출**됐다. 단순 비효율이 아니라 성공이 불가능한 대상을 계속 재시도하던 결함이다.
3. **해결 방법** — 생성기가 스스로 남긴 판정(`LLM_PENDING`)만 배분 대상으로 삼도록 고쳤다. 같은 판정을 두 곳에서 다시 계산하지 않는다 — 두 곳이 각자 판정하면 반드시 어긋난다.
4. **결과** — 화면당 **5건 → 1건 (80% 감소)**. 여기에 규칙/LLM 경계를 계획 파일로 고정한 효과가 더해져 포팅 대상 46건 중 **21건(46%)** 은 LLM 호출 자체가 발생하지 않는다. 5화면 25건 포팅이 약 30초다.

### 2.1 [비용] LLM 호출 80% 낭비 — 재시도 루프가 성공 불가능한 대상을 반복 호출

**증상**: 계획 파일이 "포팅 호출 3건 중 1건만 반영됨"을 드러냈다.

**근본 원인** (추정보다 나빴다):
1. 포팅 대상 목록에 **F 함수를 전부** 담고 있었다
2. 그중 단순 위임 함수는 이미 **규칙 기반 코드로 생성 완료** → 포팅 마커가 없다
3. 마커가 없으니 LLM 결과가 결합 단계에서 **조용히 버려진다**
4. 버려지니 "완료" 목록에 영영 안 들어간다
5. 재시도 라우팅이 "아직 안 된 함수"로 보고 **라운드마다 또 호출한다**

**실측**: 유효 1건에 **LLM 호출 5건 (80% 낭비)**. 단순 위임 2건이 각각 2회씩 호출되고 있었다.

**이건 단순 비효율이 아니라 버그다** — 재시도 루프가 성공할 수 없는 대상을 무한히 재시도하는 구조였다.

**조치**: 포팅 대상을 생성기가 스스로 남긴 `LLM 포팅 필요` 표시가 있는 함수로만 한정. (판정 함수를 다시 호출하는 방식 대신 생성기의 기록을 신뢰 → 두 판정이 어긋날 위험 제거)

**결과**: **호출 5건 → 1건 (80% 감소).** 부수 효과로 재시도 판정과 수리 대상 필터도 정확해졌다(규칙 기반 생성물이 더 이상 후보로 안 잡힘).

### 2.2 [정확성] 수리 결과가 조용히 버려지던 문제

**증상**: 수리 루프를 만들었는데 수리 결과가 반영되지 않았다.

**원인**: 결합 함수가 포팅 마커를 **지워버려서**, 재결합할 자리가 사라졌다.

**조치**: 마커를 유지하도록 변경. "아직 포팅 안 됨" 판정 기준도 마커가 아니라 **스텁 본문 존재 여부**로 바꿨다.

### 2.3 [정확성] 중괄호 오류가 엉뚱한 함수에 귀속되던 문제

**증상**: 가장 흔한 BLOCKER인 중괄호 불일치가 수리 루프에 **아예 안 잡혔다**.

**원인**: 파일 전체를 하나의 스택으로 검사하는 방식이라, 중괄호가 하나 빠지면 뒤따르는 `}`들이 역할을 당겨 써서 **결국 클래스 여는 괄호가 미닫힘으로 남는다**. 어느 함수가 깨졌는지 구조적으로 알 수 없었다.

**조치**: 함수 조각별로 균형을 따로 보는 검사를 추가해 정확히 귀속시킨다.

### 2.4 [정확성] "오류 함수" 집계가 0건이던 문제

**증상**: 오류 함수 탐지를 만들었는데 실제로 돌리니 **0건**이 나왔다.

**원인 추적**: 이슈를 만드는 두 모듈이 대부분 **소속 함수를 채우지 않아서**, DB가 이슈를 함수에 연결할 방법이 없었다(줄번호는 있었다). 게다가 계층 간 참조 이슈를 기록하는 지점은 함수 매핑을 아예 넘기지 않고 있었다.

**조치**: 이슈 구조에 소속 함수 필드를 추가하고, 두 모듈에 **각자 독립적인**(변환기/검증기/스캐너 분리 원칙 유지) 줄번호→함수 역추정 헬퍼를 넣었다. 계층 간 참조 기록 지점도 함수 매핑을 넘기도록 수정.

### 2.5 [품질] 스캐너가 자기 자신이 만든 주석을 오탐

**증상**: 아직 포팅 안 된 스텁 함수마다 전부 가짜 WARNING이 떴다.

**원인**: 스캐너가 코드가 아니라 **골격 생성기가 남긴 안내 주석 안의 API 이름 언급**을 코드로 오인했다.

**조치**: 주석 줄을 건너뛰도록 수정.

> 이건 "의미 없는 탐지"의 실제 사례였다. 탐지 건수가 많은 게 좋은 게 아니라, **행동으로 이어지는 탐지**만 의미가 있다.

### 2.6 [정확성] 콜그래프가 불완전했던 문제

**증상**: 미사용 함수 후보가 실제보다 많이 나왔다.

**원인 2가지**:
1. **저장 경로의 콜그래프가 "단순 위임 1건"만 기록**하고 있었다. 계산·분기가 있어 여러 하위 함수를 호출하는 실제로 흔한 경우가 통째로 빠져 있었다. 별도 CLI 경로는 전체를 잡고 있었으나 **실제로 쓰는 경로는 그렇지 않았다** — "두 개의 병렬 구현, 하나는 불완전"
2. 같은 계층 내부 호출(한정자 없는 호출)이 콜그래프 어디에도 없었다

**조치**: 저장 경로에도 전체 호출 탐색을 추가하고, 한정자 없는 호출 탐지를 신설해 양쪽 경로에 적용.

**결과**: 실제 화면 기준 **콜그래프 간선 5개 → 9개**, 빠졌던 하위 함수 4개가 전부 채워짐.

### 2.7 [정확성] 잘못된 지침을 프롬프트에 넣었던 것 — 자기 정정

초기에는 프롬프트에 **"이 Map의 값은 전부 문자열로 담긴다"** 고 단정해서 넣었다.

**그건 AS-IS의 관례이지 TO-BE의 사실이 아니다.** TO-BE에서 이 Map은 출처마다 타입이 다르다 — 요청은 JSON 역직렬화라 숫자가 정수/실수형, DB 반환값은 매핑 결과라 별도 수치·시각 타입, AS-IS에서 그대로 온 값만 문자열이다.

방어적 변환을 시키려는 의도는 맞았지만 **LLM에게 틀린 데이터 모델을 가르치고 있었다.** "타입이 고정돼 있지 않다"는 사실만 남기고 방어적 변환 + null 처리를 요구하도록 정정했다.

## 3. LLM 출력 품질 평가

이 프로젝트의 LLM 출력은 자연어 답변이 아니라 **코드**다. 따라서 일반적인 자연어 품질 지표 대신 **검증 가능한 지표**로 평가한다.

| 평가 축 | 자연어 RAG의 대응 개념 | 이 프로젝트의 측정 방법 | 실측 |
|---|---|---|---|
| **환각 없음** | Faithfulness | 생성 결과에 **원본에 없는 식별자가 등장하는가**를 원본 목록과 기계적으로 대조 | **조작 필드 0건 / 3건 전수** |
| **문법 정확성** | — | 정적 검증 + `mvn compile` | 전 파일 통과 |
| **계약 준수** | Relevance | 주입한 피호출자 이름을 그대로 사용했는가 | 실제 실행에서 **주입 이름 그대로 사용 확인** |
| **설명 가능성** | — | 변경 사유 주석 생성 여부 | 생성 확인 |
| **응답 시간** | Latency | 호출당 소요 | 평균 **4.3초/건** (1회 측정) |

> **핵심**: "환각 없음"을 프롬프트 지시에만 맡기지 않고 **출력을 기계적으로 대조해 차단**한다. 원본에 없는 필드가 등장하면 BLOCKER로 자동 차단되고 그 제안은 반영되지 않는다. 지시는 어겨질 수 있지만 대조는 어겨질 수 없다.

## 4. 성능·비용 최적화

| 최적화 | 방법 | 효과 |
|---|---|---|
| **LLM 호출 대상 축소** | 결정론적으로 풀리는 변환은 LLM에 맡기지 않음 | 포팅 대상 46건 중 **21건을 규칙으로 회피(46%)** — 세트 B 5화면 |
| **낭비 호출 제거** | §2.1 버그 수정 | **화면당 5건 → 1건 (80% 감소)** |
| **병렬 디스패치** | 화면 × 함수 조합을 동시 처리 | 화면 수에 선형 비례하지 않음 |
| **opt-in 분리** | 참고용 대안 제안은 버튼을 눌러야만 호출 | 자동 배치에 포함하지 않아 화면 수만큼 누적되지 않음 |
| **재분석 억제** | 자율 탐색 없는 고정 파이프라인 | 탐색 호출 0건 |
| **캐싱** | 원본 해시 기반 재변환 스킵 | 동일 원본 재처리 방지 |

**비용 구조의 핵심**: 1,416화면 전체로 확장할 때 LLM 비용은 **화면 수 × 포팅 대상 함수 수**에 비례한다. 그래서 "결정론적 변환 비중을 높이는 것"이 곧 비용 최적화다. 이게 §2 결정론적/LLM 경계 설계가 성능 설계이기도 한 이유다.

## 6. H3 가설의 반증 — 이번 주의 가장 중요한 결과

> **H3: 정적 검증만으로 변환 정확성을 보증할 수 있다 → 반증됨**

### 왜 반증인가

수리 루프를 만든 뒤 **효용을 재평가한 결과**, 다음을 인정해야 했다:

1. **거의 안 걸린다.** 요즘 LLM은 중괄호를 거의 틀리지 않는다. 실제 실행에서는 첫 시도에 전부 통과했고, 테스트하려면 깨진 코드를 **일부러 주입해야** 했다.
2. **두 개선이 서로를 잡아먹는다.** 가장 현실적인 트리거였을 "호출 대상 미존재" 오류는, 같이 넣은 **피호출자 이름 주입이 예방해버린다.**
3. **무엇보다, 개선하는 층이 틀렸다.** 정적 검증만 피드백으로 쓰므로 AlphaTrans 기준 이미 96.40%였던 **문법** 쪽만 개선하고, 정작 문제인 **기능 동등성 25.14%** 쪽은 건드리지 못한다.

### 근본 원인 — 그리고 그 전제가 틀렸다는 후속 정정(2026-09-05)
당시엔 **"포팅된 Service를 실행할 수단이 없다"** 고 결론지었다. 그건 틀렸다 — 필요한 건 애플리케이션 기동이 아니라 F 계층 메서드를 호출할 최소 환경이었고, AS-IS가 쓰는 프레임워크 API는 10개 남짓의 닫힌 집합이라 스텁으로 재현할 수 있었다. 실행 하네스를 만들어 돌리자 **정적 검증을 전부 통과한 코드가 27건 중 9건만 일치(33%)** 했고, 원인(배관 규칙이 레코드셋 추출 단계를 빠뜨림)을 고쳐 100%가 됐다. **그리고 같은 일이 한 층 위에서 또 일어났다 — §5 참고.**

즉 H3 반증은 그대로 유지되되, **근거가 "측정할 수 없어서 모른다"에서 "측정해보니 실제로 달랐다"로 바뀌었다.**

AlphaTrans·ReCodeAgent가 **레포의 기존 테스트로** 검증하는 것과 갈리는 지점이 정확히 여기다. 우리에겐 그 테스트가 없다.

### 그래도 남은 순효과
수리 루프를 만드는 과정에서 **기존 코드의 실제 결함 2건**(§2.2 수리 결과가 버려지던 문제, §2.3 중괄호 오류 귀속 실패)을 찾아 고쳤다. 설계는 유지하되 **기대치를 정정**했다.

### 이 반증이 바꾼 것
- 성공 지표를 **L1~L4 4개 층**으로 분리하고, L2 통과를 완료로 인정하지 않기로 함
- 다음 단계 최우선 과제가 "수리 루프 고도화"가 아니라 **"포팅 결과를 실행할 수단 확보"** 로 바뀜 — 그리고 그 수단(최소 실행 Harness)을 실제로 만들어 F 48/48 · Api 페이로드 9/9를 측정했다. 지금 남은 과제는 실행 **범위**다
- 판정 체계에 `SKIPPED`를 두어 **검사 안 한 것을 통과로 집계하지 않도록** 함

## 5. 층을 하나 더 열었더니 같은 격차가 또 있었다 — Api 계층 (2026-09-05)

L3 하네스는 **AS-IS F ↔ TO-BE Service만** 비교했다. 그 위층(진입점)은 "아직 아무도 검증하지
않았다"고 적어두고 넘어갔던 자리다. 이번에 AS-IS P 함수와 TO-BE Api 함수를 같은 입력으로 실행해
비교했다.

### 실측 — Api 계층 0/9

| 케이스 | AS-IS | TO-BE(수정 전) |
|---|---|---|
| 목록 조회 (권한 없음) | `@msg=W0024` (조회권한 안내) | `AUTH_YN=N` |
| 목록 조회 (1행) | `@msg=I0016; MAIN_LIST#1` | `AUTH_YN=Y` |
| 이력 조회 (1행) | `@msg=I0016; HIST_LIST#1` | `AUTH_LIST#1;CODE_LIST#1;DETAIL_LIST#1;HIST_LIST#1;MAIN_LIST#1` |

생성된 Api가 `return ResponseEntity.ok(service.fAuthCheck(request));` 한 줄이었다 — 본문에서
**처음 만나는 F 호출 하나만** 위임하고 나머지를 버린다. 권한 게이트도, 결과 메시지도, 어느
레코드셋을 돌려줄지도 전부 사라진 상태였고, **정적 검증은 전부 통과했다.**

> **§4의 반증(H3)이 정확히 반복됐다.** "문법은 맞는데 동작이 다르다"가 F 계층에서 33%로
> 나타났고, Api 계층에서 0%로 다시 나타났다. 차이는 이번엔 **원인이 우리 가정에 있었다**는
> 점이다 — `docs/02`의 "P는 순수 위임"은 화면 1건을 보고 쓴 문장이었고, 30화면 전수 확인 결과
> **30/30에서 거짓**이었다(권한 게이트 30/30, `setOkResultMessage` 195건, 레코드셋 선별 165건).

### 고친 결과와, 일부러 안 고친 것

`detect_p_orchestration()`으로 P를 "순수 위임 / 오케스트레이션 보유"로 갈라 후자를 Api 포팅
대상에 넣었다. **페이로드(반환 레코드셋) 0/9 → 9/9(100%).**

**엄격 일치는 여전히 0/9이고, 이건 의도한 상태다.** 남은 차이가 전부 결과 메시지 코드인데,
이걸 TO-BE 응답에 어떤 키로 실을지는 **아직 확정되지 않은 공통 규약**이다. 규약 없이 키를
지어내는 건 멘토 §2와 CLAUDE.md가 금지한 바로 그것이라, 생성기가 그 자리를 비워두고
`RESPONSE_MESSAGE_CONVENTION_UNDEFINED` BLOCKER를 올린다. **하네스도 페이로드 일치와 메시지
일치를 나눠 보고**해서 "우리가 못 옮긴 것"과 "아직 아무도 정하지 않은 것"이 한 칸에 섞이지
않게 했다.

> **부수 성과 — 미확정 규약 하나를 근거로 좁혔다.** 공통 응답 규약의 열린 질문 중 "경고/안내
> 코드가 예외로 던져지는지, 안내 메시지인지"는 실사용 사례가 없어 확인 불가였다. 이번에
> 찾았다: 응답 객체에 메시지를 설정한 뒤 **던지지 않고 그대로 반환**하며, 메서드 이름부터
> `setOk...`다. **성공 응답에 실리는 안내 메시지**이고 30/30 화면이 이 패턴을 쓴다. 담을 자리를
> 정하는 건 여전히 사람 몫이지만, 무엇을 담아야 하는지는 이제 추측이 아니다.

### 이 층을 열자 같이 드러난 결함 3건

| # | 결함 | 왜 여태 안 보였나 |
|---|---|---|
| 1 | 생성된 Api에 예외·컬렉션 클래스 import 누락 | Api가 **한 번도 컴파일된 적이 없었다** |
| 2 | TO-BE 공통 예외 클래스에 AS-IS가 실제로 쓰는 3-인자 생성자가 없음(코퍼스 **60파일 105회** 사용) | 문서가 "실사용 패턴은 2-인자 하나뿐"이라고 적어뒀는데 그것도 **화면 1건 기준**이었다 |
| 3 | **화면 5개가 전부 `/01`, `/02`, `/03`을 엔드포인트로 주장** — 둘은 패키지까지 같아 기동 시 충돌 | 정적 검증기가 **화면을 하나씩만** 본다. 각 화면은 완벽히 유효하다 |

3번은 slug가 함수명에서 화면 ID를 떼어내고 있었던 것으로, **화면 ID야말로 그걸 유일하게 만드는
부분**이었다. 화면을 나란히 놓는 자리는 교차 분석뿐이라 거기에 탐지를 신설했다(4건 → 0건).

## 6. 측정 사각지대 — "100%"의 분모가 3/5였다

위 작업을 검증하다 하네스가 AS-IS와 TO-BE 함수를 **이름으로** 짝짓는다는 걸 다시 봤다. 그런데
규칙 기반 단순 위임은 생성 시 이름이 바뀐다. 그래서 그 함수들이 **비교에서 통째로 빠지고
있었다** — 한 화면은 F 함수가 5개인데 3개만 재고 "F 계층 100%"라고 보고하고 있었다.

**빠진 둘이 하필 문제 있는 쪽이었다.**

```
공통코드 조회   AS-IS  CODE_LIST#1
                TO-BE  AUTH_LIST#1;CODE_LIST#1;DETAIL_LIST#1;HIST_LIST#1;MAIN_LIST#1
```

단순 위임 생성기가 `return store.dXXX(request);`를 만드는데, 원본은 특정 레코드셋 **하나만**
꺼낸다. 결과를 통째로 되돌려주니 원본이 반환하지 않던 데이터가 전부 새어 나갔다.

> **"규칙 기반이라 안전하다"고 말해 온 경로에서 나온 결함**이라 더 뼈아프다. 탐지기는 이미
> 레코드셋 이름을 알고 있었고 그냥 버리고 있었다. 이제 그 키만 담는다.

**F 계층 27/27(함수 3/5) → 48/48(함수 5/5).** 같은 100%지만 분모가 진짜다. 하네스는 이제
짝짓지 못한 함수 수도 함께 보고한다 — **분모를 숨기면 100%가 무엇에 대한 100%인지 알 수 없다.**

## 7. 다른 코퍼스로 돌리자 드러난 변환기 결함 3건

지금까지 검증은 두 세트(A: 1화면 복제 50벌 / B: 5도메인 30화면)로 했다. **세 번째 소스 트리**로
6화면(PLA045~050)을 돌리자 그동안 안 보이던 결함이 한꺼번에 나왔다. 유형 다양성이 부족하다고
계속 적어온 한계가 실제로 무엇을 가리고 있었는지 보여주는 사례다.

### 7.1 속성 표기 하나에 규칙 전체가 무력화됐다

모든 태그 변환 규칙이 `property="x"`처럼 **등호에 공백이 없는** 형태만 매칭했다. 새 원본은
`compareValue = "Y"`로 쓴다 — XML 스펙상 완전히 유효한 표기다. 그래서 `<isEqual>`이 하나도
변환되지 않았다.

규칙 8개의 정규식을 각각 고치는 대신, **들어올 때 한 번 표기를 정규화**하도록 했다. 단
`<...>` **태그 선언 안쪽만** 바꾼다 — `WHERE COL = 'Y'` 같은 SQL 본문의 공백을 건드리면 이
변환기의 대원칙(SQL 자체는 건드리지 않는다)이 깨지기 때문이다.

### 7.2 변환 실패보다 나쁜 것 — 반쪽 변환이 XML을 깨뜨렸다

더 심각한 건 그 다음이었다. 닫는 태그 치환이 **"파일 안에 하나라도 변환된 게 있으면"** 실행되는
구조였다. 그래서 같은 파일에서 일부는 변환되고 일부는 안 되면:

```
<isEqual property="MEMO_GB" compareValue = "Y">   ← 안 바뀜(공백 때문)
    , PLN_MEMO_CTN = #{PLN_MEMO_CTN}
</if>                                              ← 바뀜  ⟹ 태그 짝 깨짐
```

결과는 파싱 불가 XML이다. **못 고치는 것과 망가뜨리는 것은 다르다** — 안 고치면 사람이 원본을
보고 옮기면 되지만, 망가뜨리면 원본이 무엇이었는지도 잃는다. 이제 **태그 쌍은 전부 바꾸거나
전부 그대로 둔다**. 일부만 바뀔 상황이면 되돌리고 경고를 남긴다(`PARTIAL_TAG_CONVERSION`).

> 이 프로젝트가 반복해서 택해 온 판단과 같은 계열이다 — 규칙이 확신할 수 없으면 **스스로
> 사양하고 사람에게 넘긴다**. 비중을 올리려고 반쯤 맞는 코드를 찍어내지 않는다.

### 7.3 정반대 태그에 규칙이 없었다

`<isEmpty property="X">`에는 규칙이 있는데 **정반대인 `<isNotEmpty property="X">`에는 없었다**.
`prepend`가 붙은 변형만 다루고 가장 단순한 형태를 빠뜨린 것이다(새 원본에서 11회 사용).
iBatis의 `isNotEmpty`는 "null도 아니고 빈 문자열도 아님"이라 MyBatis `<if>`로 정의가 1:1
대응한다 — 추측이 아니라 의미가 같아서 넣었다.

### 7.4 원본 결함을 파서 메시지 대신 줄 번호로 짚는다 → 자동 교정으로 발전

남은 파싱 오류는 우리 문제가 아니라 **원본 결함**이었다: `<insert id="I005 parameterClass="map">`
— 닫는 따옴표가 빠졌고, 같은 형태가 3건 있다. XML 파서는 `not well-formed`라고만 말해서 어디를
봐야 할지 알 수 없다. 이 형태를 따로 탐지해 **해당 줄 번호를 직접 짚어주도록** 했다.

> **2026-09-09 — 줄 번호 안내에서 자동 교정으로 올렸다.** 사용자가 "PLA046이 정적검증을 통과
> 못 하는 게 원본 문제인지 변환 오류인지" 물어서 재확인하다가, 이 패턴이 XML 파싱뿐 아니라
> Store 생성기(`extract_xsql_stmt_kinds`)도 독립적으로 깨뜨려 insert 3건을 "미지원"으로
> 오탐시키고 있는 걸 발견했다(§9 DML 절 참고). 이 모양(속성값 중간에 공백 뒤 `이름="`가
> 다시 나오는 건 다음 속성이 시작된 것 말고는 해석할 방법이 없음)은 해석이 모호하지 않아 -
> `repair_unterminated_attr_quotes()`를 추가해 **자동으로 따옴표를 채워 넣고**
> `ORIGINAL_XML_ATTR_QUOTE_FIXED` 경고로 남기도록 정정했다. "사람이 원본을 보고 고쳐야
> 하는 것"에서 "고쳐졌다는 사실만 검토하면 되는 것"으로 등급을 올린 셈이다.

### 7.5 보고가 남의 문제를 내 문제처럼 보이게 했다

6화면만 변환했는데 **"엔드포인트 44곳 충돌"** 이 떴다. 원인은 산출물 폴더가 *지금까지 승인·저장한
전부*를 담고 있고, 그중 44개가 경로 규칙을 고치기 **전에** 생성된 것이었기 때문이다. 이번 배치
6화면끼리는 충돌 0건이다.

수치는 맞았지만 **읽는 사람이 자기 변환의 문제로 오해하게 만드는 보고**였다. 이번 배치와 기존
저장분을 구분해 문구를 갈랐다.

> **측정과 보고는 다른 문제다.** 이 프로젝트는 "분모를 숨기지 않는다"를 여러 번 지켰는데,
> 여기서는 분모가 아니라 **범위**를 밝히지 않아 같은 종류의 오해를 만들었다.
