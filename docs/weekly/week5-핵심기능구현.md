# 5주차 — 핵심 기능 구현

**프로젝트**: G-SCM 차세대 전환 Agent
**범위**: 전환 프로그램 **1단계 = 서버(Java/XSQL → Spring/MyBatis) 전환**

## 1. 구현 현황 요약

착수 순서는 멘토 코멘트 §J의 우선순위를 그대로 따랐다. **1~4번이 성패의 80%이고 LLM은 6번에서야 등장한다.**

| 순서 | 항목 | 상태 | 비고 |
|---|---|---|---|
| 1 | nctRid 매핑 그래프 | **완료** | 실데이터 적재·검증 완료 |
| 2 | 차등 테스트 하네스 | **부분 완료** | SQL 계층 실증. 상위 계층은 실행 환경 부재로 미착수 |
| 3 | 공통 응답/예외 규약 | **의도적 보류** | 초안만 작성. 사람 확정 전 생성기에 주입하지 않음 |
| 4 | 결정론적 변환기 | **완료** | 실제 빌드 통과로 검증 |
| 5 | 파일럿 20~30화면 | **미완료** | 현재 fixture는 단일 유형(§5 한계 참고) |
| 6 | LLM 파이프라인 | **완료** | 상태 그래프 기반 |
| 7 | 검증·수리 루프 | **완료** | 라운드 상한 있음 |

## 2. 매핑 그래프 구축 (H1 검증)

### 무엇을 만들었나
AS-IS 소스 폴더를 정적 분석해 **화면 ↔ 트랜잭션(nctRid) ↔ 함수 ↔ SQL** 의 전체 그래프를 DB에 적재한다. LLM을 전혀 쓰지 않는다.

4단계 파이프라인:
1. `.BIZUNIT` 메타에서 트랜잭션 ID 추출
2. Java 파싱으로 P → F → D 호출 관계 추적
3. D 함수의 DB 호출에서 SQL statement id 추출
4. 위를 결합해 화면 단위 그래프로 적재

### 실측 결과

| 항목 | 수치 |
|---|---|
| 대상 화면 | 50 |
| 파일 (`CONV_FILE`) | 200 |
| 함수 (`CONV_METHOD`) | 1,034 |
| 호출 관계 (`CONV_METHOD_CALL`) | 890 |
| 트랜잭션 매핑 (`NCTRID_MAP`) | 300 |
| **트랜잭션 자동 확정률** | **150 / 150 = 100%** (전부 메타데이터 기반 확정값) |

### 정직성 관련 기록 2건

**(1) 초기 실행이 불완전한 사본 기준이었음을 발견해 정정**
초기에는 "3건만 확정, 나머지 171건 미해결"이라는 결과가 나왔다. 원인은 도구가 아니라 **입력 데이터가 부분 사본**이었다는 것 — 화면 1개만 메타 파일을 갖고 나머지는 없었다. 완전한 사본으로 재실행해 150/150 확정을 얻었다.

**(2) 규칙 일치를 "검증"이라고 부르지 않음**
확정값에서 `함수명 → 트랜잭션ID` 변환 규칙이 150/150 일치했다. 그러나 **이 fixture 자체가 그 패턴을 복제해 만든 것**이므로, 이 일치는 생성기 설계의 재확인이지 실제 프레임워크 규칙의 독립적 검증이 아니다. 따라서 나머지 화면에 이 규칙을 추측 적용하지 않고 관찰 기록으로만 남겼다.

> 이 두 건이 이 프로젝트의 작업 방식을 보여준다. **수치가 좋아졌을 때 왜 좋아졌는지를 먼저 의심한다.**

## 3. 결정론적 변환기 (H2 검증)

### 구현 범위

| 변환기 | 입력 | 출력 | LLM |
|---|---|---|---|
| SQL 문법 변환기 | iBatis XSQL | MyBatis Mapper.xml | X |
| 골격 생성기 | P/F/D BizUnit | Api / Service(스텁) / Store | X |
| DTO 생성기 | `.BIZUNIT` 또는 코드 실사용값 | Dto | X |

### 골격 생성기의 설계 포인트
단순 이름 매칭이 아니라 **P 함수 본문에서 실제로 호출하는 F 함수를 찾아** Api → Service 연결을 맞춘다. D 함수는 DB 호출에서 statement id를 뽑아 Store가 참조하도록 생성한다.

Service 메서드 본문은 **항상 스텁**으로 남긴다 — 로직 포팅은 별도 LLM 단계의 몫이고, 골격 생성기가 로직을 추측하지 않는다.

### 실측 결과 — 실제 빌드 검증

`mvn compile` 실행 결과, 생성된 전체 트리(50화면 × Api/Service/Store/Dto/Mapper) 중 **실패는 `Pla047Service.java` 1건뿐**이었다.

그리고 **그 1건은 의도된 실패**다. 원본 F BizUnit 자체에 중괄호 누락 버그가 있고, "원본이 깨져 있어도 임의로 고치지 않고 보존한다"는 원칙에 따라 그대로 옮겼기 때문이다.

> **이것이 H2의 실증이다.** 규칙 기반 생성기가 만든 코드가 문법적으로 실제 유효하다는 것을, 주장이 아니라 컴파일러로 확인했다.

### DTO 역추출의 정직한 한계
`.BIZUNIT`의 필드 정의가 비어 있는 경우, 코드의 실사용 호출에서 필드를 역추출한다. 트랜잭션 1개는 15개 요청 필드를 전부 채웠지만, 나머지 2개는 F 함수가 필드 맵을 통째로 넘기는 구조라 개별 필드를 찾지 못했다. **추측으로 채우지 않고 WARNING + 사람 확인 필요로 표시**했다.

## 4. LLM 포팅 파이프라인

### 4.1 의존성 계약 주입 (AlphaTrans §A 적용)

AlphaTrans는 조각마다 **호출자/피호출자, 입출력 타입, 임포트, 상속 관계**를 메타데이터로 뽑아 콜그래프 역순으로 번역한다. 이 프로젝트는 5조각 분해·역순 변환·콜그래프를 **이미 갖고 있었고**, 빠져 있던 건 하나였다 — **그 메타데이터를 실제로 프롬프트에 넣는 것.**

그래서 포팅 프롬프트에 두 가지를 주입한다:

| 주입 항목 | 내용 | 효과 |
|---|---|---|
| **피호출자 계약** | 콜그래프에서 해당 함수가 실제 호출하는 하위 함수 목록(이미 생성된 이름 그대로) | LLM이 Store 함수 이름을 **추측하지 않는다** → 호출 대상 미존재 오류를 사전 차단 |
| **값 타입 주의사항** | 이 Map의 값은 런타임 타입이 하나로 고정돼 있지 않다 (요청은 JSON 역직렬화, DB 반환은 매핑 결과, AS-IS 경유는 문자열) | 특정 타입 직접 캐스팅으로 인한 런타임 예외 예방. 방어적 변환 + null 처리 요구 |

### 4.2 변경 사유 주석
포팅·수리 결과의 첫 줄에 `// AI 변경 요약:` 주석을 남기게 했다. 리뷰어가 **무엇을 왜 바꿨는지**를 코드 안에서 바로 보게 하기 위함이다.

### 4.3 검증-수리 루프 (MatchFixAgent/ACToR §D 적용)

```
정적 검증 → 수리 게이트 → (BLOCKER 있음) → 재포팅 → 결합 → 정적 검증 …
                        → (없음 / 예산 소진) → 품질 스캔
```

**설계 제약 3가지**
1. 대상은 **LLM이 포팅한 함수에 귀속된 BLOCKER만**. 규칙 기반 생성물은 제외한다 — LLM이 고칠 문제가 아니다.
2. 라운드 상한이 있다. 무한 재분석은 자율 탐색이 되어 버린다.
3. 예산을 소진하면 포기하고 **사유를 남긴다**. 조용히 성공한 척하지 않는다.

## 5. 영향도 분석

| 기능 | 방식 | 실측 |
|---|---|---|
| 미사용 함수 후보 | 콜그래프 정방향 도달성 분석 | 49건 후보 |
| 중복 함수 | 본문 해시 기준 화면 경계 넘는 비교 | 6건 |
| 오류 함수 | 함수에 귀속된 BLOCKER·원본버그 집계 | 위험도 점수로 정렬 |
| **역방향 영향도(blast radius)** | 콜그래프 **역방향 BFS** | 아래 참고 |

**역방향 영향도 검증**: 독립적으로 정답을 아는 사례로 대조했다. 특정 데이터 함수 → (1홉) 상위 업무 함수 → (2홉) 진입점 함수 및 그 트랜잭션까지 **정확히 도달**하는 것을 확인했다.

**LLM을 쓰지 않는다.** 이 질문은 그래프 순회로 정확한 답이 나오므로 추론을 섞을 이유가 없다. 결정론적 조회라 답에 근거를 그대로 붙일 수 있다.

**한계 표시**: 호출자가 0건으로 나오는 경우, 그것이 곧 미사용을 뜻하지 않는다는 한계를 결과와 함께 표시한다. 확정 판정이 아니라 **검토 후보**로만 취급하고, 자동 삭제는 하지 않는다.

## 6. 계획 파일 & 인수인계 문서

### 계획 파일 (ReCodeAgent §B, Copilot Modernization §E 적용)
코드 생성 **전에** 화면별 계획을 파일로 고정한다. LLM을 쓰지 않으므로 변환 결과에 의존하지 않고 변환 전에 존재할 수 있다.

담는 내용: 5조각 존재 여부·줄수·해시 / 트랜잭션 목록 / 예상 산출 파일과 변환 방식 / **LLM 포팅 대상 함수** / 규칙 기반 처리 함수 / 예상 LLM 호출 수 / 트랙 판단 근거 신호.

**트랙(구조보존/재설계)은 자동으로 정하지 않고 항상 `미정`으로 두며 판단 근거만 채운다** — 트랙 결정은 사람 몫이다.

> **계획 파일이 실제로 일한 사례**: 계획서가 "포팅 호출 3건 중 1건만 반영됨"을 드러냈고, 이를 추적해 80% 낭비 버그를 찾아냈다(6주차 문서 §2 참고).

### 인수인계 문서 (AlphaTrans §A "실패분 리포트" 적용)
**변환 실패를 예외가 아니라 정상 산출물로 취급한다.** 화면별로 "미변환 사유 + 수동 처리 가이드"를 자동 생성한다.

구성: ① 자동 변환을 신뢰하면 안 되는 이유 ② 원본이 컴파일 안 되는 상태 경고 ③ 포팅 실패로 스텁이 남은 함수 ④ BLOCKER ⑤ WARNING ⑥ INFO(접힘) ⑦ 산출물 표 ⑧ 반드시 사람 리뷰가 필요한 함수.

**새로 계산하는 값이 없다.** 판정을 다시 하지 않고 이미 나온 결과를 재배치만 한다. 이슈마다 **확인된 조치 방법**을 붙이되, 조치법이 정의되지 않은 유형에는 **없는 처리법을 지어내지 않고** 원본 메시지만 보여준다.

## 7. 조회 전용 가정의 조기 노출

변환 체인 전체가 **조회(SELECT)만** 가정하고 있었다. 확보한 원본이 조회 전용이라 등록/수정/삭제 경로는 한 번도 검증된 적이 없다.

**그런데 지원을 지금 만들지 않았다.** 샘플이 하나도 없는 상태에서 본 적 없는 패턴에 규칙을 짜는 건 "확인되지 않은 규칙을 추측으로 하드코딩하지 않는다"는 원칙 위반이기 때문이다.

대신 **미지원을 조기에, 이름 붙여 드러내도록** 했다:
- DB 호출 동사를 화이트리스트 없이 있는 그대로 수집해 조회가 아닌 것을 보고
- 해당 함수 위에 처리 안내 주석 + BLOCKER 이슈(함수 귀속)
- **변환 전** 계획 파일과 UI 경고로 노출

이전에는 이런 화면이 늦고 엉뚱한 메시지로만 걸렸다.
