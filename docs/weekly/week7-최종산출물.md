# 7주차 — 최종 산출물

**프로젝트**: G-SCM 차세대 전환 Agent
**범위**: 전환 프로그램 **1단계 = 서버(Java/XSQL → Spring/MyBatis) 전환**

---

## 1. 무엇을 만들었나 (한 문단)

Nexacro14 + NEXCORE로 구축된 G-SCM의 **서버 계층**(P/F/D BizUnit + XSQL)을 Spring/MyBatis 구조로 자동 전환하는 파이프라인을 만들었다. 폴더를 지정하면 **계획 수립 → 규칙 기반 변환 → LLM 포팅 → 정적 검증 → 수리 → 품질 스캔 → 교차 분석 → 빌드 검증**까지 자동 진행되고, **사람이 승인해야만** 결과가 반영된다. 핵심 설계는 "결정론적으로 풀리는 변환에는 LLM을 쓰지 않는다"이며, 그 결과 화면당 LLM 호출을 1건으로 억제하면서도 생성 코드가 실제 컴파일을 통과한다.

## 2. KPI — 계획 대비 실적

| 층 | 지표 | 목표 | **실적** | 판정 |
|---|---|---|---|---|
| L1 구조 | 트랜잭션 매핑 자동 확정률 | 80%+ | **100% (150/150)** — 세트 A | **초과 달성** |
| L1 구조 | 골격 생성 성공률 | 95%+ | 대상 화면 전건 생성 | **달성** |
| L2 문법 | 컴파일 통과율 | 95%+ | **실패 1건 외 전부 통과** (실패는 의도된 원본 버그 보존) | **달성** |
| L2 문법 | 정적 검증 통과율 | 90%+ | 5화면 25파일 중 잔여 BLOCKER 1건 | **달성** |
| L2 문법 | LLM 의존 최소화 | 포팅 대상 30% 이하 | 포팅 대상 46건 중 **21건을 규칙으로 회피(46%)** | 달성 |
| L2 문법 | **원본 결함 탐지** (신규) | — | **10/10 (100%), 오탐 0건** — 세트 B 정답키 대조 (보강 전 5/10) | 측정 완료 |
| L2 문법 | **중복 함수 탐지** (신규) | — | 재현율 **50%→100%**, 오탐 **0%→48%** — 세트 B | 측정 완료 |
| **L3 기능** | 실행 결과 일치율 (F 계층) | 기준 수립 | **48/48 일치(100%)** · 화면 3/5 실행 | **부분 달성** |
| **L3 기능** | 실행 결과 일치율 (Api 계층) | 기준 수립 | **페이로드 9/9(100%)** · 결과 메시지 0/9(응답 규약 미확정) · 화면 1/5 | **부분 달성** |
| **L4 공수** | **사람 수정 라인 비율** | 30% 이하 | **0.20%** (AI 리뷰어 1차 기준 하한값) | **달성(하한값)** |
| L4 공수 | 화면당 공수 절감률 | 65~70% | **미측정** (기준선 미실측) | **미달** |

### 미달 3건에 대한 정직한 설명

**L3 (기능 동등성)** — 원래 여기에 "포팅된 코드를 실행할 환경이 없어서"라고 적었는데 **그 전제가 틀렸다.** 필요한 건 애플리케이션 기동이 아니라 함수를 호출할 최소 환경이었고, AS-IS가 쓰는 프레임워크 API는 10개 남짓의 닫힌 집합이라 스텁으로 재현할 수 있었다. 지금은 F 계층과 Api 계층을 **실제로 실행해서** 비교한다.

남은 미달 사유는 셋으로 갈린다. ① **화면 3/5만 실행 가능** — 나머지 2화면은 AS-IS 원본에 주입 결함이 있어 컴파일되지 않는다(도구 문제가 아니다). ② **Api 계층은 1화면(9케이스)만 측정** — 배점이 표본 1건에 걸려 있어 신뢰구간이 넓다. ③ **결과 메시지 코드는 응답 규약이 확정되지 않아 비워뒀다** — 규약이 정해지면 닫히는 격차이지 변환 실패가 아니며, 그렇다고 후하게 채점하지도 않았다(엄격 일치로 0점). (6주차 §4~§6 참고)

**L4 (사람 수정 라인 비율 / 공수 절감률)** — 사람이 리뷰·수정한 화면이 아직 0건이라 **측정 시점이 오지 않았다.** 측정 컬럼과 산식은 준비돼 있다. 여기에 숫자를 채우려면 사람이 실제로 리뷰해야 하고, 그건 파일럿 단계의 일이다.

> 이 3건에 **추정치를 채워 넣지 않았다.** 측정하지 않은 값을 실적으로 보고하면 첫 파일럿에서 신뢰를 잃는다.

### 자체 벤치마크 신규 확보 (2026-09-05)

정답키가 있는 30화면 세트를 확보해 **탐지 성능을 처음으로 수치화**했다. 그동안은 "돌려보니 N건 나왔다"까지만 말할 수 있었다 — 정답을 몰라 그 N건이 맞는지, 놓친 게 몇 건인지 말할 수 없었다. 상세는 종합 산출물 §8.

## 3. 가설 검증 결과

| # | 가설 | 결과 | 근거 |
|---|---|---|---|
| **H1** | 매핑 그래프를 선행 구축하면 소스 추적 병목이 사라진다 | **검증됨** | 트랜잭션 150/150 자동 확정. 역방향 영향도 추적이 2홉까지 정확히 도달 |
| **H2** | 결정론적 변환이 대부분을 커버하고 LLM은 좁은 영역만 필요하다 | **검증됨** | 화면당 LLM 포팅 1건 / 규칙 기반 2건. 규칙 기반 생성물이 실제 `mvn compile` 통과 |
| **H3** | 정적 검증만으로 변환 정확성을 보증할 수 있다 | **반증됨** | 정적 검증은 문법 층만 개선. 기능 동등성은 실행 없이는 확인 불가 |

> **H3의 반증이 이 PoC의 가장 큰 성과다.** 8주 동안 가설이 하나 깨지고 그 원인까지 규명됐다는 건, 가설 검증 절차가 실제로 작동했다는 뜻이다. 반증되지 않았다면 "정적 검증 통과 = 전환 완료"라는 전제로 1,416화면에 확장했을 것이고, 그 오류는 운영에서 드러났을 것이다.

## 5. 데모 시나리오

| 단계 | 보여줄 것 | 강조점 |
|---|---|---|
| 1 | 폴더 지정 → 화면 선택 → 파이프라인 시작 | 단계별 진행률 (총 몇 건 중 몇 건 남음) |
| 2 | **계획 탭** — 코드 생성 전에 만들어진 계획 파일 | 무엇을 만들지, LLM을 몇 번 부를지가 **먼저** 고정됨 |
| 3 | 변환 결과 + **정적 검증 실패 항목 클릭** | AS-IS 원본과 TO-BE 결과를 나란히 비교, **문제 줄을 강조 표시** |
| 4 | 영향도 대시보드 | 미사용/오류 함수를 위험도순으로 |
| 5 | **영향도 질의 팝업** | 함수명 입력 → 영향받는 화면·트랜잭션 즉시 조회 |
| 6 | 교차 분석 + 빌드 검증 결과 | **승인 전인데 이미 빌드 검증까지 끝나 있음** (임시 사본 격리) |
| 7 | **"승인하고 저장"** 클릭 | 이때 처음으로 실제 반영 — 사람 없이는 아무것도 안 바뀜 |
| 8 | 인수인계 문서 | 자동으로 안 된 것 + 사람이 할 일 |

## 6. 프로젝트 가치

### 정량
- 화면별 소스 추적 작업을 **그래프 조회로 대체** (트랜잭션 자동 확정 100%)
- 규칙 기반 생성물이 **실제 컴파일 통과** — 골격·SQL·DTO 작업이 자동화 가능함을 실증
- LLM 호출을 화면당 **1건**으로 억제 → 1,416화면 확장 시 비용 예측 가능
- **부수 가치**: 전환 과정에서 AS-IS 기존 결함을 자동 검출 (컴파일 불가 코드, SQL 문법 오류, 스키마 불일치)

### 정성
- **재사용 자산**: 검증·수리 루프가 변환기와 분리돼 있어, 다른 SK 계열 전환 프로젝트에 **검증 자산만 이식** 가능
- **구조적 일관성**: 동일 템플릿·동일 검증기 적용으로 개발자별 편차 제거
- **안전한 자동화 모델**: "자동으로 다 하되 반영은 사람이 승인" 구조를 실제로 구현·검증

## 7. 한계 (숨기지 않는 것)

| # | 한계 | 사유 | 해소 조건 |
|---|---|---|---|
| **L1** | 파일럿 유형 다양성 — **부분 해소** | 세트 A(50화면)는 1화면 복제본. 세트 B로 5도메인 30화면 확보 | 세트 B에 메타 파일이 없어 nctRid 0건 — 지표는 세트를 병기해 보고 |
| **L2** | 기능 동등성 — **부분 측정** | F 계층 48/48, Api 계층 페이로드 9/9. 다만 **화면 3/5만 실행 가능**(Api는 1/5)하고, 서블릿/직렬화를 거치는 **진짜 HTTP 왕복은 여전히 미검증**(함수 호출 수준까지만 비교) | 나머지 화면의 AS-IS 결함 정정 + 실제 HTTP 하네스 |
| **L3** | 사람 수정 라인 비율 — **하한값만** | 0.20%로 측정됐으나 **AI 리뷰어 1차 리뷰 기준** | 사람 개발자 리뷰로 재측정 |
| **L4** | 조회 외 DB 동작(등록/수정/삭제) 미지원 | 해당 샘플이 하나도 없음 | 샘플 확보 후 규칙 작성 (**추측으로 만들지 않음**) |
| **L5** | 공통 응답/예외 규약 미주입 | 규약 자체가 미확정 (사람 결정 대기). **이것이 Api 계층 엄격 일치율이 0%인 유일한 원인**이다 — 결과 메시지 코드를 실을 자리가 없다 | 규약 확정 (무엇을 담아야 하는지는 이번에 근거로 확정: 성공 응답의 안내 메시지) |
| **L8** | 공통 함수 추출이 Store 계층까지만 | Service 계층 공통화는 "공통 업무 로직을 어디에 둘 것인가"라는 설계 결정 (사람 몫) | 확정 시 포팅 호출 30건 → 1건 |
| **L6** | 동적 SQL 조건 태그의 차등 테스트 미지원 | 조건식 평가 엔진 부재 | 미니 템플릿 엔진 구현 |
| **L7** | 화면↔트랜잭션 자동 추출 미완 | 프론트 스크립트 실제 샘플 미확보 | 샘플 확보 (**샘플 없이 정규식 규칙을 짜지 않음**) |

**세트를 반드시 병기하는 이유**: 세트 A(`legacy-u-pla001-050`)의 50화면은 1개 화면의 복제본이라 검증 폭이 **1유형**이고, 세트 B(`PLA081-110`)는 5도메인 30화면이지만 `.bizunit`이 없어 **nctRid가 0건**으로 잡힌다. 두 세트의 수치를 섞으면 잘못된 주장이 된다 — 모든 문서에서 어느 세트 기준인지 함께 표기한다.

## 8. 다음 단계 (우선순위)

| 순위 | 과제 | 왜 이 순서인가 |
|---|---|---|
| **1** | **포팅 결과를 실행할 수단 확보** (애플리케이션 기동 또는 테스트 동반 생성) | H3 반증의 근본 원인. **이것 없이는 L3가 영원히 미달**이고, 다른 어떤 개선도 문법 층만 건드린다 |
| **2** | 유형별 대표 화면 20~30개 확보 → 구조적 클러스터링 → 파일럿 | L1 해소. 이게 있어야 변환 레시피의 일반화 여부를 알 수 있고 유형별 실측 공수가 나온다 |
| **3** | 파일럿에서 **사람 수정 라인 비율** 실측 | L4 해소. 공수 절감률의 가장 직접적인 대리 지표 |
| **4** | 공통 응답/예외 규약 확정 → 생성 템플릿에 주입 | 사람 결정 선행. 확정 전 주입은 이원화 문제를 재현함 |
| 5 | 조회 외 DB 동작 지원 (샘플 확보 후) | 샘플 없이는 착수하지 않음 |
| 6 | 파일럿 결과물을 코퍼스로 한 유사 화면 검색(RAG) | 파일럿이 선행 조건 |
| 7 | 읽기 전용 조회 도구 외부 노출 (표준 도구 인터페이스) | 나중에 해도 비용이 0 — 분석 모듈이 이미 UI 의존 없는 순수 함수 |

> **1번을 1번으로 둔 이유**: 6주차에서 확인했듯 수리 루프를 아무리 고도화해도 개선되는 건 이미 96%인 문법 층이다. 25%인 기능 층을 건드리려면 실행 수단이 있어야 한다. **가장 큰 병목에 자원을 쓴다.**

## 반영 사항 (전 주차 피드백 대응 총괄)

| 주차 | 지적 | 반영 |
|---|---|---|
| 1주 | 범위가 넓다 | 8주 범위를 유형별 20~30화면 서버 전환으로 한정. 8주 vs 장기 비전 표 분리 |
| 1주 | 측정 방식 구체화 | 측정 규칙(유형 분류·샘플 수·작업 정의·사람 개입 시간 포함) 명문화 |
| 1주 | 기술 스택 우선순위 구분 | 필수/대안/있으면 좋은 것 3단계로 재작성 |
| 1주 | Python 역량 리스크 | 학습 항목을 "파싱→생성→검증" 최소 단위로 축소, 우선순위 부여 |
| 2주 | 문서 구조 재배치 | 제안 순서대로 전 문서 재구성 |
| 2주 | 핵심 가설 2~3개 명시 | H1/H2/H3 신설 → **7주차에 검증 결과까지 보고** |
| 2주 | **KPI 수치 충돌** | 공수 절감 수치를 **65~70% 하나로 통일**, 기준선이 미실측 가정임을 명시 |
| 2주 | 다층 성공 지표 | L1 구조 / L2 문법 / L3 기능 / L4 공수 4층으로 재구성 |
| 2주 | 리스크-대응 1:1 | R1~R7 1:1 표 + **상태(해소/부분/미해소)** 까지 표기 |
| 2주 | 산출물 선명화 | §4 산출물 목록 표 |
| 2주 | "반영 사항" 절을 만들어 달라 | 3주차부터 **전 주차 문서에 포함** |
| 3주 | 입력/기대출력/성공기준 누락 | 전 시나리오에 3항목 표로 채움 |
| 3주 | 내부 파일명 과다 노출 | 시나리오를 사용자 관점으로 재작성, 내부 모듈명은 설계 문서로 이동 |
| 3주 | 예외 흐름 부족 | 시나리오별 예외 흐름 표 신설 |
| 3주 | 판정 체계 표준화 | **PASS/WARNING/BLOCKER/FAIL/SKIPPED/APPROVED** 6종 정의 + 적용 규칙. 도구·DB·문서가 전부 이 용어만 사용 |
| 멘토 §3 | 문법 정확도 ≠ 기능 정확성 | H3 반증으로 **정면 대응**. 성공 지표를 층으로 분리하고 미달을 미달로 보고 |
| 멘토 §4 | 공수 추정 현실화, 90% 약속 금지 | 65~70%로 통일, 미측정은 미측정으로 보고 |
| 멘토 §A | 실패분 리포트를 정상 산출물로 | 화면별 인수인계 문서 자동 생성 |
| 멘토 §D | 검증·수리를 변환기와 분리 | 별도 모듈. 재사용 가능 자산으로 설계 |
| 멘토 §H | 사람 수정 라인 비율이 가장 중요 | 측정 준비 완료, **측정 시점 미도래를 사유와 함께 보고** |
| 멘토 §I | 자율 탐색 에이전트를 만들지 말 것 | 고정 파이프라인. 모델이 도구를 스스로 고르지 않음 |
| 멘토 §J | 우선순위 1~7 순서 준수 | 착수 순서 그대로 이행 (5주차 §1 현황표) |
