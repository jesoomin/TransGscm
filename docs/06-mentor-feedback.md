NEXCORE/Nexacro 조합은 사실 AlphaTrans/ReCodeAgent가 가정하는 것보다 자동화에 유리한 편입니다. 계층과 네이밍이 강제되어 있고, 화면 정의가 XML(.xfdl)이라 파싱이 되니까요. 다만 성패를 가르는 지점이 몇 군데 명확히 있습니다.

1. 가장 먼저 풀어야 할 것: nctRid 매핑 인덱스

말씀하신 "화면마다 소스 추적 필요"가 이 프로젝트 최대 리스크입니다. 화면당 10일 중 상당 부분이 여기서 소모될 텐데, 이건 LLM으로 풀 문제가 아니라 선행 정적 분석 과제로 분리해야 합니다.

.xjs 스크립트  →  transaction() 호출부 추출 → svcID / nctRid 문자열
                  (동적 문자열 조합이면 부분 평가/상수 전파 필요)
NEXCORE 설정   →  nctRid ─→ P BizUnit 클래스
JavaParser     →  P → F → D 콜그래프 추적
D BizUnit      →  XSQL namespace + queryId

이 네 단계를 붙여서 화면 ↔ API ↔ SQL 전체 그래프를 DB로 구축해야 합니다. 이게 없으면 에이전트가 매 화면마다 코드베이스를 헤매면서 환각을 냅니다. ReCodeAgent가 Planner를 따로 둔 이유가 정확히 이것 — 불필요한 탐색이 환각의 원인이라서죠.

문자열 규칙과 불일치하는 케이스는 자동 추출 실패로 뜰 텐데, 이 실패 목록만 사람이 채우면 됩니다. 경험적으로 전체의 10~20% 수준일 겁니다. 이 인덱스 하나만 만들어도 화면당 공수가 눈에 띄게 줄어듭니다.

2. 결정론적 변환 / LLM 변환의 경계선

여기를 잘못 그으면 비용은 비용대로 쓰고 품질은 안 나옵니다. 제안하는 분기:

100% 규칙 기반 (LLM 쓰지 말 것)

.xfdl 컴포넌트 트리 → IR → React 컴포넌트 스캐폴딩
Nexacro Grid formats 정의 → AG-Grid colDef[] (컬럼 폭·정렬·displaytype·edittype·마스크까지 결정론적 매핑 테이블로 가능)
Dataset 스키마 → TypeScript interface
iBatis → MyBatis: #var#→#{var}, $var$→${var}, <isNotEmpty>→<if>, <iterate>→<foreach>, <dynamic prepend="WHERE">→<where>
P/F/D BizUnit → REST Controller 시그니처 골격

LLM 필요

.xjs 이벤트 핸들러 내부 비즈니스 로직
Nexacro transaction() 콜백 패턴 → async/await + React Query 재작성
Dataset의 rowType/rowState 조작 → AG-Grid transaction API 또는 별도 상태 모델로 재해석
화면 간 공통 팝업/코드도우미 호출 규약 재설계

절대 자동화하지 말 것

공통 모듈(공통 그리드 래퍼, 공통 팝업, 코드 조회, 파일 업로드 등)은 사람이 먼저 손으로 잘 만들어야 합니다. 이걸 에이전트가 화면마다 제각각 생성하면 1,416개 화면에 1,416가지 변형이 생겨서 지금의 "개발자별 이원화" 문제가 그대로 재현됩니다. 공통 컴포넌트 라이브러리를 먼저 확정하고, 에이전트에겐 "이 라이브러리를 써라"를 강제 컨텍스트로 주입하는 순서가 맞습니다.
3. 검증 전략 — 여기서 신뢰가 결정됨

AlphaTrans가 문법 정확도 99.1%인데 기능적 정확성 검증은 25.8%였다는 숫자를 꼭 기억하셔야 합니다. "변환된다"와 "맞다"는 완전히 다른 문제이고, 대부분의 PoC가 여기서 무너집니다.

다행히 NEXCORE 구조가 검증에는 유리합니다. 단일 진입점(nctRid)에 Dataset 직렬화라는 고정 포맷이 있으니 차등 테스트(differential testing) 가 깔끔하게 성립합니다.

동일 입력 → [레거시 nctRid 호출] → Dataset 직렬화 응답 ┐
                                                        ├→ 정규화 후 diff
동일 입력 → [신규 REST API 호출] → JSON 응답          ┘

운영 트래픽을 섀도우로 흘려서 이 diff를 자동 수집하면, 백엔드 변환 정확도는 사실상 기계적으로 보증됩니다. 이 하네스를 파일럿보다 먼저 만드시길 권합니다. MatchFixAgent가 "검증·수리 전담 에이전트"를 변환기와 분리해서 재사용 가능하게 만든 것과 같은 발상입니다.

프론트는 완전 자동 검증이 어렵습니다. 렌더 스모크 테스트 + 핵심 시나리오 Playwright 정도로 잡고, 사람 리뷰를 전제로 공수 산정하셔야 합니다.

4. 공수 추정을 현실화하시길

제안서에 들어갈 숫자라면 조심스럽게 잡는 편이 낫습니다. 자동화 후 화면당 공수를 유형별로 차등하면:

화면 유형	비중(추정)	자동화 후
단순 조회/그리드	40~50%	1~2일 (리뷰 중심)
조회+상세+CRUD	30~40%	3~4일
복합 화면·리포트·특수 로직	15~20%	5~7일

평균 3일 수준이면 원래 10일 대비 약 65~70% 절감입니다. 여기에 도구 자체 개발 공수(팀 3~5명 × 4~6개월)와 공통 컴포넌트 라이브러리 구축을 ROI 계산에 반드시 포함시키세요. 90% 절감을 약속하는 제안서는 첫 파일럿에서 신뢰를 잃습니다. 반대로 65%를 약속하고 75%를 내면 그 다음 단계가 열립니다.

5. 파일럿 설계

1,416개를 대상으로 바로 가지 마시고:

전체 화면을 구조적으로 클러스터링 (컴포넌트 구성 + transaction 개수 + 그리드 유무 기준으로 자동 분류 가능합니다)
유형별 대표 화면 4~5개씩, 총 20~30개로 파일럿
이 과정에서 나온 변환 규칙·프롬프트·공통 컴포넌트를 자산화
유형별 실측 공수를 뽑아서 전체 계획 재산정

파일럿 목표는 "화면이 돌아간다"가 아니라 "화면 유형별 변환 레시피와 실측 공수를 확보한다" 로 잡는 게 맞습니다.

6. 놓치기 쉬운 리스크 두 가지

Dataset 상태 모델의 의미 손실 — Nexacro의 rowState(insert/update/delete 플래그)는 Dataset이 알아서 관리해주는 개념인데, React에는 대응물이 없습니다. AG-Grid로 옮길 때 이 dirty tracking을 어떻게 표현할지 아키텍처 결정을 선행하지 않으면, 에이전트가 화면마다 다른 방식으로 구현합니다. 여기가 가장 흔한 실패 지점입니다.

동기 트랜잭션 → 비동기 전환 — Nexacro의 transaction() 콜백 흐름을 그대로 async/await로 옮기면 순차 실행되던 것이 병렬화되거나 순서가 깨지는 케이스가 생깁니다. 콜백 체인 패턴을 미리 몇 가지로 분류해서 변환 규칙을 고정해두세요.

이 프로젝트에 직접 이식 가능한 것만 골라 정리했습니다.

A. AlphaTrans — 분해·순서·타입 매핑
원 패턴	Nexacro/NEXCORE 적용
프로그램 분석으로 fragment 분해	화면을 통째로 넣지 말고 .xfdl(레이아웃) / .xjs(로직) / Dataset 스키마 / BizUnit / XSQL 5개 fragment로 분리
콜그래프 역순 번역	XSQL → D BizUnit → F → P → API 스펙 → React 순으로 진행. 하위가 확정돼야 상위 시그니처가 안 흔들림
스켈레톤 우선 구성	화면 전체를 생성하지 말고 ① 컴포넌트 트리 + colDef + TS interface 골격을 규칙으로 먼저 확정 → ② LLM은 빈 함수 본문만 채움
Universal Type Mapping 축적	Nexacro displaytype/edittype/mask ↔ AG-Grid cellRenderer/cellEditor/valueFormatter 매핑 테이블을 프로젝트 자산으로 누적. 화면 처리할수록 LLM 호출량이 줄어듦
실패분 리포트 생성	변환 실패를 예외가 아닌 정상 산출물로 취급. "미변환 사유 + 수동 처리 가이드"를 화면별로 자동 생성

참고 수치: 문법 정확도 99.1% vs 기능 검증 통과 25.8%. 이 간극이 그대로 우리 리스크입니다.

B. ReCodeAgent — 4-에이전트 분업 구조

그대로 차용 가능한 골격입니다.

Analyzer — 화면·서비스·SQL 그래프 구축, 라이브러리 대응관계 결정 (Nexacro Grid→AG-Grid, Dataset→TanStack Query 등)
Planner — 화면 유형 분류 + 변환 단위(unit) 확정 + 스켈레톤 생성. 탐색 없이 실행되도록 구체적 스텝을 미리 못 박음
Translator — 코드와 테스트를 함께 생성
Validator — 실행 검증 전담 (Translator와 분리)

핵심 시사점 두 가지:

무거운 정적분석기 대신 경량 파서 조합 — CodeQL 대신 Tree-sitter를 쓴 것처럼, 우리도 .xfdl은 XML 파서, .xjs는 JS AST(babel/tree-sitter), BizUnit은 JavaParser로 충분합니다. 언어별 전용 도구 3개면 커버됩니다.
Planner가 계획을 파일로 고정 — 사전 계획을 산출물로 남기면 리뷰·재현·재실행이 가능해집니다.
C. RepoTransAgent — RAG + Reflection
컨텍스트 검색 에이전트 분리: 변환 대상 화면과 유사한 이미 변환 완료된 화면을 벡터 검색으로 3~5개 뽑아 few-shot으로 주입. 파일럿 30개를 먼저 만드는 이유가 여기 있습니다 — 그게 RAG 코퍼스가 됩니다.
동적 프롬프트: 화면 유형(단순조회 / CRUD / 복합)별로 프롬프트를 분기. 단일 프롬프트로 1,416개를 처리하려 하면 실패합니다.
Reflection 루프: 컴파일 에러 / tsc 에러 / ESLint를 피드백으로 재생성. 단, 재시도 상한(2~3회) 을 반드시 두세요.

Java-C# 기준 컴파일률 55%, 통과율 46%였다는 점 — 우리 쪽이 도메인이 훨씬 좁아 더 높게 나오겠지만, 첫 시도 통과를 전제로 계획 짜면 안 된다는 신호로 받으시면 됩니다.

D. MatchFixAgent / ACToR — 검증·수리를 변환기와 분리

이게 가장 중요한 차용 포인트입니다.

검증기를 변환기와 독립 모듈로 설계 → 나중에 변환기를 바꿔도 검증 자산이 살아남음
역할 분리: 의미분석 → 테스트작성 → 실행 → 실패시 수리 → 최종 판정 (판정자를 따로 두는 게 핵심)
ACToR의 시사점: 적대적 루프가 기저 변환기와 독립적이라 기존 변환기 위에 얹어서 추가 개선이 가능했습니다. 우리도 "1차 변환 파이프라인"과 "검증·개선 루프"를 별도 제품으로 만들면, 다른 SK 계열 전환 프로젝트에 검증 루프만 재활용할 수 있습니다.

구체 적용:

[레거시 nctRid] ─ 동일 입력 ─ [신규 REST API]
        ↓                            ↓
   Dataset 응답  ── 정규화 diff ──  JSON 응답
        ↓
   불일치 → 수리 에이전트 → 재검증 → 판정
E. GitHub Copilot Modernization — 오케스트레이션 실무 패턴

산업용 도구라 운영 관점에서 배울 게 많습니다.

plan.md + tasks.json으로 계획 영속화 → 우리도 화면별 conversion-plan.json 산출
작업 유형별 전문 실행기로 라우팅 → 그리드 변환기 / 이벤트 로직 변환기 / SQL 변환기 분리
마이그레이션 패턴 지식베이스 조회 → NEXCORE 관용구집(공통팝업 호출, 코드도우미, 파일업로드, 그리드 페이징)을 KB로 구축
작업 단위 커밋 자동 생성 → 리뷰 가능성 확보. 화면 하나가 거대 단일 커밋으로 나오면 아무도 리뷰 못 합니다
OpenRewrite 같은 결정론적 도구와 결합 → iBatis→MyBatis는 LLM이 아니라 룰 엔진으로
F. AWS Transform — Refactor vs Reimagine 이원화

1,416개를 한 가지 방식으로 처리하지 말라는 게 핵심 시사점입니다.

Refactor 트랙 (80%): 구조 보존, 1:1 변환, 자동화 극대화 — 단순조회/CRUD 화면
Reimagine 트랙 (20%): 업무 규칙만 추출하고 UI/API는 재설계 — 복합화면, 특수 리포트, 원래도 UX가 나빴던 화면

말씀하신 "확장성 제약으로 기능 추가 한계"는 Refactor로는 안 풀립니다. 그대로 옮기면 제약도 같이 옮겨집니다. 제안서에 이 이원화를 명시하면 "단순 이관이 아닌 현대화"라는 프레이밍이 생깁니다.

G. C2SaferRust / EvoC2Rust — 하이브리드 원칙
트랜스파일러 먼저, LLM은 나머지 — 결정론적으로 가능한 건 절대 LLM에 맡기지 않음
정적 분석 기반 오류 교정 — 컴파일러/타입체커 출력을 LLM 피드백으로 순환
점진적 변환 + 동작 가능 상태 유지 — 전체를 한 번에 바꾸지 않고 레거시와 신규가 공존하는 중간 상태를 허용. 우리도 Strangler Fig 패턴으로, 신규 React 화면이 당분간 기존 nctRid 백엔드를 그대로 호출하도록 설계하면 프론트/백엔드 전환을 분리할 수 있습니다 (리스크 대폭 감소)
H. 벤치마크 계열 — 자체 평가셋 구축

RepoTransBench/CRUST-Bench가 그랬듯, 내부 벤치마크를 먼저 만들어야 개선 여부를 측정할 수 있습니다.

화면 20~30개 + 정답 React 코드(사람이 작성) + 테스트
측정 지표: 컴파일 통과율 / 렌더 성공률 / API 응답 diff 일치율 / 사람 수정 라인 비율(가장 중요)
프롬프트나 모델을 바꿀 때마다 회귀 측정

"사람 수정 라인 비율"이 곧 실제 공수 절감률의 대리 지표라서, ROI 보고에 그대로 쓸 수 있습니다.

I. 이 프로젝트엔 안 맞는 것 (의도적으로 버릴 것)
TransCoder류 학습 기반 변환 — 병렬 데이터도 없고 규칙성이 높아서 굳이 모델을 학습시킬 이유가 없습니다
완전 자율 에이전트(SWE-agent류 자유 탐색) — 탐색 비용 대비 효용이 낮습니다. 1,416회 반복되는 작업이므로 파이프라인이 자율성보다 낫습니다
범용 다국어 지원 설계 — 언어 불가지론적 프레임워크를 흉내 낼 필요 없이 Nexacro→React 단일 쌍에 특화하는 게 훨씬 효율적입니다
J. 적용 우선순위
매핑 그래프 구축 (화면↔nctRid↔BizUnit↔XSQL) — 나머지 전부의 전제
차등 테스트 하네스 — 변환기보다 먼저
공통 컴포넌트 라이브러리 (사람이 작성) + 관용구 KB
결정론적 변환기 (xfdl→스켈레톤, colDef, iBatis→MyBatis)
파일럿 20~30화면 → 벤치마크 + RAG 코퍼스 확보
LLM 에이전트 파이프라인 (Planner/Translator/Validator)
Reflection·수리 루프 고도화

1~4번이 실제로는 이 프로젝트 성패의 80%이고, LLM은 6번에서야 등장합니다. 제안서에서도 이 순서를 그대로 보여주시면 "AI 마케팅"이 아니라 엔지니어링 계획으로 읽힙니다.
