# 화면·파일별 변환 검증 테이블 설계

## 목적
1,416개 화면(정확히는 그에 대응하는 AS-IS Java/XSQL/.BIZUNIT 파일 묶음)을 순차 변환하면서, **파일 단위로** "원본이 애초에 정상인가 → 어떻게 변환했는가 → 빌드가 되는가 → 기능이 맞는가 → 사람이 승인했는가"를 추적한다. PLA047 작업 중 실제로 겪은 문제(파일 자체가 파싱/컴파일 안 되는 경우, 대응 TO-BE 파일이 없는 경우)를 그대로 열로 반영했다 — 가상의 시나리오가 아니라 이번 세션에서 확인된 상태를 기준으로 설계했다.

행 = **AS-IS 파일 1개** (`.java`, `.xsql`, `.bizunit`). DTO나 메시지 프로퍼티처럼 특정 AS-IS 파일 하나에 대응하지 않고 여러 파일을 취합해서 만드는 TO-BE 산출물은 "AS-IS 계층"을 `(파생)`으로 표시하고 어떤 파일들을 참고했는지 비고에 적는다.

## 상태값 규칙
- **변환 상태가 `완료`가 되려면** TO-BE 빌드 검증이 `Pass`여야 한다 (CLAUDE.md: "빌드/린트 통과해야 완료로 인정"). 빌드 전이면 아무리 코드를 다 옮겼어도 `진행중`으로 둔다.
- **AS-IS 파싱/컴파일 상태가 `실패`인 파일은 변환 상태를 `보류`로 두고, 원본 재확보 전까지 `진행중`으로 올리지 않는다.** 깨진 원본 위에서 "그럴듯하게 지어낸" 변환은 CLAUDE.md 핵심 원칙 위반이다.
- **리뷰 상태는 빌드 통과와 별개다.** 빌드가 `Pass`여도 사람이 diff를 보고 `승인`하기 전까지는 커밋하지 않는다.

## 사용 방법
`/tracking/conversion-verification.csv`를 화면 작업할 때마다 갱신한다. 화면 1개 = 보통 7~9행(P/F/D의 .java·.bizunit + XSQL + 파생 DTO/메시지). 파일럿 20~30화면이 끝나면 이 CSV가 "화면 유형별 실측 커버리지"를 그대로 보여주는 산출물이 된다 (@docs/03-kickoff-plan.md Phase 3).
