# G-SCM 차세대 전환 Agent — 제안서

## 프로젝트 명
G-SCM 차세대 전환 Agent

## 전환 프로그램의 단계 구분 (범위의 전제)

G-SCM 차세대 전환은 **화면(UI)과 서버(백엔드)를 같은 시점에 바꾸지 않는다.** 두 계층은 교체 사유도, 확정 시점도, 검증 방법도 다르기 때문이다.

| 단계 | 대상 | 이번 Agent 범위 | 사유 |
|---|---|---|---|
| **1단계** | 서버 (Java/XSQL → Spring/MyBatis) | **O — 본 제안서 대상** | 업무 로직·SQL은 이미 검증된 자산이라 "재작성"이 아니라 "포팅"이 가능하다. 계층(P/F/D)과 네이밍이 강제돼 있어 정적 분석·템플릿화가 성립한다 |
| **2단계** | 화면 (Nexacro xfdl → React) | X — 별도 트랙 | UI는 추가 디자인 변경 가능성이 열려 있어 확정 시점이 서버보다 늦다. 확정되지 않은 디자인을 자동 변환하면 두 번 만들게 된다 |

**두 단계를 잇는 계약이 nctRid다.** 1단계는 기존 트랜잭션 계약(nctRid 1개 = REST 엔드포인트 1개)을 그대로 유지한 채 서버만 교체한다. 그래서 2단계에서 React 화면이 만들어질 때, 그 화면은 **1단계가 만들어 둔 API를 그대로 호출**하면 된다 — 백엔드를 다시 손대지 않는다.

이 순서는 Strangler Fig 패턴의 표준 적용이다. 레거시(NEXCORE)와 신규(Spring) API가 당분간 공존하는 상태를 정상으로 취급하고, 프론트 전환 리스크와 백엔드 전환 리스크를 분리한다.

> 본 제안서의 모든 KPI·산출물·검증 방법은 **1단계(서버 전환)** 기준이다. UI 전환 공수는 포함하지 않는다.

## 배경 및 문제 정의

### 현재 상황 (As-Is)
- 프론트: Nexacro14(Dataset 기반 UI) / 백엔드: NEXCORE(SK그룹 표준 Spring 프레임워크, BizUnit 단위 개발)
- 통신 구조: Nexacro Dataset ↔ UIAdapter 직렬화 → nctRid 단일 진입점 → P→F→D BizUnit 순차 호출 → D BizUnit이 XSQL(iBatis) 실행
- 규모: 화면 1,416개 및 그에 대응하는 P/F/D BizUnit + XSQL 파일군
- 화면-서비스 매핑(nctRid)이 문자열 규칙과 불일치 → **화면마다 소스를 사람이 추적해야 함**
- 솔루션(패키지 제품) 기반 프레임워크 종속 → 확장성 제약

### Pain Point

| 구분 | 내용 |
|---|---|
| 시간 | 서버 전환 시 화면마다 P/F/D/XSQL 4종 파일을 추적·분석하는 선행 작업이 반복 발생 |
| 비용 | 1,416개 화면 규모의 반복 작업 — 패턴이 동일한데도 자동화되어 있지 않음 |
| 품질 | 개발자별로 Controller 응답 형태·예외 처리·Mapper 작성 방식이 이원화 → 구조 편차 |
| 리스크 | AS-IS 원본 자체에 결함(컴파일 불가, XML 태그 불일치, SQL 문법 오류)이 섞여 있음 — 실제 확보한 PLA047 세트에서 확인됨 |

### 기회 요인 (AI로 해결 가능한 이유)
- P/F/D/XSQL의 **명확한 계층·네이밍 컨벤션** → 정적 분석으로 그래프 구축 가능
- iBatis → MyBatis는 **문법 치환** → 규칙 기반 100% 자동화 대상 (LLM 불필요)
- BizUnit 메서드 시그니처 → Controller/Service/Store 골격도 **결정론적 생성** 가능
- LLM이 필요한 영역은 **F BizUnit 내부 업무 로직 포팅**으로 좁게 한정됨 → 비용·환각 통제 가능
- nctRid 단일 진입점 + 고정 Dataset 포맷 → **차등 테스트(differential testing)가 깔끔하게 성립**

## 프로젝트 목표

### 정성적 목표
1. **반복 업무 자동화** — 화면별 소스 추적, 골격 생성, SQL 문법 변환 등 결정론적으로 풀리는 작업을 에이전트에 위임한다.
2. **의사결정 지원 및 검증** — 자동 생성 코드에 대해 정적 검증·품질 스캔·영향도 분석 리포트를 제공해 리뷰 시간을 단축한다. "변환됐다"와 "맞다"를 구분해서 보고한다.
3. **AI 기술 내재화** — LangGraph 기반 코드 마이그레이션 방법론을 사내 모더니제이션 자산으로 확보한다. 검증·수리 루프는 변환기와 분리해 다른 전환 프로젝트에 재사용 가능하게 만든다.

### 정량적 목표 (KPI)

KPI는 **측정이 이미 정의·수행된 지표(주 KPI)** 와 **파일럿 실측이 있어야 확정되는 지표(보조 KPI)** 로 나눈다. 파일럿 이전 단계에서 공격적 수치를 확정하지 않는다.

**주 KPI — 측정 방법이 정의되고 실제로 측정 중인 지표**

| 성과 지표 | 목표 | 측정 방법 | 현재 수준 |
|---|---|---|---|
| nctRid 매핑 자동 확정률 | 80% 이상 | `NCTRID_MAP.NCTRID_SOURCE`가 `CONFIRMED_BIZUNIT`인 행 / 전체 nctRid 행 | **100% (150/150)** — 파일럿 fixture 기준 |
| 규칙 기반 생성물 컴파일 통과율 | 95% 이상 | `mvn compile` 실행 결과 중 규칙 기반 생성 파일의 실패 건수 | **1건 외 전부 통과** (실패 1건은 AS-IS 원본 버그를 의도적으로 보존한 결과) |
| 정적 검증 통과율 | 90% 이상 | `CONV_FILE.BUILD_CHECK = PASS` 비율 | 측정 중 |
| LLM 의존 최소화율 | 포팅 대상 메서드 30% 이하 | `CONV_METHOD.CONVERSION_METHOD = LLM_PENDING` / 전체 F 메서드 | **33% (3건 중 1건)** — 나머지 2건은 규칙 기반 처리 |
| 사람 수정 라인 비율 | 30% 이하 | `CONV_FILE.HUMAN_EDIT_RATIO` — 자동 생성 라인 대비 리뷰 중 수정 라인 | **미측정** (사유: 사람 리뷰·수정을 거친 화면이 아직 0건. 파일럿 착수 시점부터 측정) |

**보조 KPI — 파일럿 실측 후 확정**

| 성과 지표 | 목표 | 측정 방법 | 현재 수준 |
|---|---|---|---|
| 화면당 서버 전환 공수 절감률 | **65~70%** | 파일럿 10~20건에 대해 개발자 실투입 시간 측정(사람 개입 시간 포함) | **미측정** — 기준선(수작업 공수) 자체가 미실측 가정 |
| 기능 동등성 (응답 일치율) | 파일럿에서 기준 수립 | 동일 입력을 AS-IS/TO-BE에 실행 후 정규화 diff | **SQL 계층 1건 PASS**, 상위 계층 미검증 (사유: 아래 리스크 R3) |

> **공수 절감률에 90% 이상을 약속하지 않는다.** 화면 유형별로 자동화 효과가 크게 다르며(단순 조회/그리드 vs 복합 리포트), 도구 자체 개발 공수와 공통 규약 확정 공수를 ROI에 포함해야 하기 때문이다. 65%를 약속하고 75%를 내는 편이 다음 단계를 연다.

## 핵심 가설

8주 안에 검증할 가설을 3개로 한정한다.

| # | 가설 | 검증 방법 | 결과 |
|---|---|---|---|
| **H1** | nctRid 매핑 그래프를 **선행 정적 분석**으로 구축하면, 화면별 소스 추적이라는 최대 병목이 사라진다 | 화면↔nctRid↔BizUnit↔XSQL 그래프를 DB로 구축하고, 임의 메서드에서 영향받는 화면·nctRid를 역추적해 정답과 대조 | **검증됨** — nctRid 150/150 확정, 역추적 2홉 정확 도달 |
| **H2** | 이 도메인은 **결정론적 변환이 대부분을 커버**하고, LLM은 좁은 영역(F 로직 포팅)에만 필요하다 | 화면당 LLM 호출 대상 메서드 수 및 규칙 기반 생성물의 실제 컴파일 통과 여부 측정 | **검증됨** — 화면당 LLM 포팅 1건 / 규칙 기반 2건, 골격은 `mvn compile` 통과 |
| **H3** | **정적 검증(컴파일·문법)만으로 변환 정확성을 보증할 수 있다** | 정적 검증 통과 코드에 대해 실제 실행 기반 동등성 검증 시도 | **반증됨** — 문법 통과와 기능 동등성은 별개. 근거는 아래 R3 |

H3의 반증은 이 프로젝트의 핵심 발견이다. 검증 전략 전체가 이 결과를 반영해 재설계됐다.

## 핵심 기능 정의

| # | 기능 | 방식 | 산출물 |
|---|---|---|---|
| 1 | **AS-IS 소스 분석기 / nctRid 매핑 그래프** | 규칙 기반 (LLM 미사용) | 화면↔nctRid↔BizUnit↔XSQL 그래프 (Oracle: `CONV_FILE`/`CONV_METHOD`/`CONV_METHOD_CALL`/`NCTRID_MAP`) |
| 2 | **변환 계획 수립 (Planner)** | 규칙 기반 | 화면별 `conversion-plan.json` — 대상 fragment, 예상 산출물, LLM 호출 대상, 트랙 판단 근거 |
| 3 | **결정론적 변환기** | 규칙 기반 | iBatis→MyBatis Mapper.xml, Api/Service/Store 골격, DTO |
| 4 | **LLM 포팅기 (Translator)** | LLM (좁은 범위) | F BizUnit 업무 로직 → Service 메서드 본문. 콜리 계약·타입 주의사항을 프롬프트에 주입 |
| 5 | **검증기 (Validator) — 변환기와 분리** | 규칙 기반 | 정적 검증, 품질·취약점 스캔, `mvn compile`, 차등 테스트 |
| 6 | **검증-수리 루프** | LLM (상한 있음) | 정적 검증 BLOCKER를 피드백으로 재생성. 라운드 상한 고정(무한 탐색 금지) |
| 7 | **영향도 분석 대시보드** | 규칙 기반 | 미사용 함수 후보, 중복 함수, 오류 함수, 위험도 점수, 역방향 영향도(blast radius) 질의 |
| 8 | **인수인계 문서 자동 생성** | 규칙 기반 | 화면별 `{화면}-handoff.md` — 미변환 사유 + 수동 처리 가이드 |

**절대 자동화하지 않는 것**: 공통 응답/예외 처리 규약, 공통 Mapper/Store 패턴. 이걸 화면마다 에이전트가 제각각 만들면 현재의 "개발자별 이원화" 문제가 그대로 재현된다. 사람이 먼저 확정하고, 에이전트에는 강제 컨텍스트로 주입하는 순서를 지킨다.

## 기대 효과

**근거**: 전면 재작성이 아니라 **NEXCORE 프레임워크 종속 계층만 교체**하고 검증된 업무 로직·SQL은 포팅한다. 교체 대상은 UIAdapter/nctRid 디스패처/P BizUnit(→ REST Controller)과 iBatis 문법(→ MyBatis)이며, F BizUnit의 계산·분기와 XSQL의 쿼리 로직 자체는 그대로 옮긴다.

| 구분 | 기대 효과 |
|---|---|
| 업무 효율화 | 화면별 소스 추적 작업 제거(그래프 조회로 대체), 골격·SQL·DTO 생성 자동화 |
| 품질 향상 | 동일 템플릿·동일 검증기 적용으로 개발자 간 구조 편차 감소. 원본 결함(컴파일 불가 코드, SQL 문법 오류)을 전환 전에 자동 검출 |
| 확장성 | nctRid 계약을 유지해 2단계 UI 트랙이 백엔드를 다시 손대지 않고 진행 가능 |
| 자산화 | 검증·수리 루프를 변환기와 분리 → 다른 SK 계열 전환 프로젝트에 검증 자산만 재사용 가능 |

## 범위 및 제약사항

### In Scope (1단계 — 서버 전환)
- P/F/D BizUnit(Java) → `{화면}Api` / `{화면}Service` / `{화면}Store`
- `.BIZUNIT` XML → `{화면}Dto` (비어 있으면 코드 실사용값에서 역추출)
- XSQL(iBatis) → `{화면}Mapper.xml` (MyBatis 문법 변환)
- 하드코딩 메시지 코드 → `errors.properties` 외부화
- 위 산출물에 대한 정적 검증 / 빌드 검증 / 차등 테스트 / 영향도 분석
- **nctRid 트랜잭션 계약 유지** (nctRid 1개 = REST 엔드포인트 1개)

### Out of Scope
- **화면(Nexacro xfdl → React) 전환** — 2단계 별도 트랙. 확정된 디자인으로 진행하며, 1단계가 만든 API를 그대로 호출한다
- DB 스키마 변경
- 신규 비즈니스 로직 추가
- 사람 리뷰 없는 자동 커밋/배포
- 화면에 묶이지 않은 공통·배치성 BizUnit(`DCOT998`류)

### 제약사항
- 사내 보안 정책상 레거시 소스의 외부 LLM 전송 가능 여부 확인 필요 → **사내 LLM Gateway 경유로 해소**
- P BizUnit에 화면 특화 검증 로직이 섞여 있을 경우 Controller 흡수 난이도 상승 (PLA047 1건은 순수 위임 확인, 표본 확대 필요)
- `.BIZUNIT` XML의 `<fields/>`가 비어 있는 경우가 많음 → 코드 실사용값 역추출 필요
- 공통 응답/예외 규약이 미확정 → 확정 전까지 생성 템플릿에 주입하지 않음

|---|---|---|---|---|
| R1 | 화면-nctRid 매핑을 자동 추출하지 못함 | 에이전트가 화면마다 코드베이스를 탐색하며 환각 | 선행 정적 분석으로 그래프를 DB에 구축. 자동 추출 실패분만 사람이 채움 | **해소** (150/150 확정) |
| R2 | AS-IS 원본 자체가 깨져 있음 (컴파일 불가, XML 태그 불일치, SQL 문법 오류) | 깨진 원본 위에 "그럴듯하게 지어낸" 변환이 생성됨 | 원본 결함을 정정하지 않고 **보존**하되, 변환 전 계획 단계에서 결함을 검출해 표시하고 해당 화면을 Reimagine 후보로 신호 | **대응 중** (검출 동작 확인) |
| R3 | 문법은 통과하지만 기능이 다름 | 전환 후 운영 장애. AlphaTrans(FSE 2025) 실측 기준 문법 96.40% vs 기능 동등성 25.14% | 차등 테스트(동일 입력 → AS-IS/TO-BE 응답 diff)를 변환기보다 먼저 구축. **단, 상위 계층 검증에는 실행 환경이 필요** | **부분 대응** — SQL 계층만 실증, 상위 계층은 미해소 (H3 반증) |
| R4 | LLM 호출 비용·시간이 화면 수에 비례해 폭증 | 1,416화면 확장 시 비현실적 비용 | 결정론적으로 풀리는 변환은 LLM에 맡기지 않음. 포팅 대상을 `LLM_PENDING` 메서드로만 한정 | **해소** (화면당 호출 5건 → 1건) |
| R5 | 에이전트가 화면마다 다른 공통 규약을 생성 | 현재의 "개발자별 이원화"가 그대로 재현 | 공통 응답/예외 규약은 사람이 먼저 확정. 확정 전까지 생성 템플릿에 주입하지 않음 | **의도적 보류** (사람 결정 대기) |
| R6 | 파일럿 화면 유형이 편중되어 규칙이 일반화되지 않음 | 다른 유형 화면에서 변환 품질 급락 | 구조적 클러스터링 후 유형별 대표 화면 4~5개씩 선정 | **미해소** — 현재 fixture는 단일 유형 |
| R7 | 자동 변환 결과가 검토 없이 반영됨 | 품질 사고 | 저장 전 승인 게이트 고정. 승인 전에는 산출물 트리에 파일을 쓰지 않음(임시 사본에서 검증) | **해소** (격리 검증 완료) |
